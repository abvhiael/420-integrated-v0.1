# Cloudflare Pages — wallet-independent BongGoggles account UI opt-in

The Pages project is **bonggoggles**, connected to GitHub
`abvhiael/420-integrated-v0.1` on branch `main`.

The existing Pages build settings remain unchanged:

- Root directory: `bong-goggles/web`
- Build command: `npm run build`
- Output directory: `dist`
- Automatic deployments: enabled on `main`

The ordinary build uses `runtime-config.example.json` to supply its complete
runtime configuration, including service URLs. It now recognizes one **text**
build environment variable:

`BG_ACCOUNT_SOCIAL_ACTIVATION=true`

Only the exact lowercase string `true` enables `features.accountSocial`,
`accountMessaging`, `accountGames` and `accountXP` in the generated
`dist/runtime-config.json`. `accountMonetization` is always false.
Missing or `false` keeps all five switches off; malformed values cause
a build failure, not a permissive default.

## Cloudflare operator steps

1. First verify the real same-origin health endpoint and approved 420ID
   sign-in, `/social-api/v1/me`, community feed, and SSO logout/revocation.
   Account Social is off-chain and independent of the wallet/indexer.
2. In **Cloudflare → Workers & Pages → bonggoggles (Pages) → Settings →
   Production → Variables and secrets**, add **Text** variable
   `BG_ACCOUNT_SOCIAL_ACTIVATION` with value `true`. This is not a
   420ID or proxy secret; do not edit `SOCIAL420_EDGE_SECRET`.
3. Review and merge the qualified opt-in build PR into `main`. The existing
   Pages connection automatically rebuilds `dist/` from the root above.
   If needed, explicitly redeploy the new commit from the Pages Deployments tab.
4. Open `https://bonggoggles.420integrated.org/runtime-config.json`
   and confirm the full config still includes environment, appOrigin, chainId,
   all service URLs, and `features` containing precisely the four new true
   account switches while accountMonetization remains false.
5. Hard-refresh `/social`, test profile, posts, messages, games, XP, logout,
   inaccessible sessions and moderator/abuse handling. These require
   real-browser acceptance; CI cannot certify them.

**Rollback:** change this Pages Text variable to `false` (or remove it)
and redeploy the same qualified commit, then verify the published feature
flags are all false. Do not disable 420ID or delete the social database.

**Important:** `bong-goggles/web/dist/runtime-config.json` and
`dist-deployment/runtime-config.json` committed in GitHub are not inputs to
`npm run build`. They are regenerated by the build process. A JSON file
containing only the five flags is not a valid complete runtime config.
Do not repoint Pages to `dist-deployment` or replace the complete config
with an uploaded fragment. The example service origins remain illustrative:
this opt-in is not a replacement for BG-19 deployment qualifications,
production readiness or full on-chain launch approvals.

## Automated evidence

The `Bong Goggles Web Verification` workflow runs the normal no-variable
build, checks that the generated JSON keeps the account features disabled,
then runs a second build with `BG_ACCOUNT_SOCIAL_ACTIVATION=true` and
asserts the full JSON changes only those four approved switches.
Unit tests also cover malformed, absent and explicit false values and
preservation of service URLs, unrelated feature switches and monetization
boundary. Real live Cloudflare configuration is not modified by the PR.

## BC-1.8 Git-controlled production opt-in when Cloudflare API credentials are unavailable

The authenticated production Render/Neon service and same-origin Worker are already healthy. The branch deployment attempt using the conventional `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` GitHub Actions secrets failed on November 22, 2026 because **both values were absent** in the runner; no Pages settings or deployment were changed. Because this Pages project already has automatic Git-integrated deployments from `main`, source-controlled restricted production opt-in is now used: `scripts/build.mjs` resolves the two Classic flags as the exact string `true` only when `CF_PAGES=1`, `CF_PAGES_BRANCH=main` and the preexisting `BG_ACCOUNT_SOCIAL_ACTIVATION=true`. Local builds, PR previews, missing account activation and other branches remain disabled by default. Explicit `BG_CLASSIC_ROOMS_ACTIVATION=false` or `BG_CLASSIC_COMMUNICATIONS_ACTIVATION=false` overrides this source default, allowing operator rollback without another code change. The original independent flag validator, server-side authorization, zero-wager boundary and unreleased catalogue state are unchanged. The verification workflow builds both default/off and main Pages production/on artifacts and checks the actual generated runtime config before accepting the change.

Source-controlled production opt-in requires merge to `main` to trigger the real linked Pages deployment. The link itself is a deployment mechanism, not evidence of successful production publication; verify `https://bonggoggles.420integrated.org/runtime-config.json` after merge and do not mark Cribbage **Playable** until the separate live game acceptance passes.
