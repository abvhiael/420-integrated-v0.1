# 420Bet unified lobby — BET-AUDIT-6.1

Standalone Vite browser shell for discovery, category filtering and immersive navigation. Run `npm install && npm run dev` from this directory, `npm test` for catalogue tests and `npm run build` for a production bundle.

The lobby does **not** implement game logic, authentication, wallet signing, funding, betting, odds or settlement. Original clients remain authoritative. The repository has a Vite Dice client (`clients/420bet-dice-v1`), a standalone fantasy browser build (`clients/420bet-fantasy/daily`) and a Python sportsbook client (`clients/420bet-sports`); no public production route is assumed for any of them.

For an operator-controlled same-origin deployment, set `window.BET_LOBBY_CONFIG = { routes: { dice: '/games/dice/' }, status: { dice: 'preview' } }` before `src/main.js` executes, by adding a configuration script to the host page. URLs must be same-origin root paths; no default routes are enabled. The status setting is a discovery/launch hint only, **not** wagering authorization. Deployment must independently authorize eligible sessions and validate all transactions server-/chain-side. Do not mark games available solely because a bundle exists.

Returning to the lobby removes the embedded game iframe. **Active funded game sessions must not be launched through this initial embedded integration until the respective game client implements and verifies safe exit/session recovery.** Later stages 6.2–6.11 own that wiring. This shell does not silently execute exits, refunds, settlements or wallet operations.

No prediction market catalogue entries. User decision: BET-AUDIT-6.9 cancelled; retain numbering. Artwork uses CSS placeholders, never substitutes for canonical uploaded game artwork.

## Browse-only previews
All 13 tiles open a full-screen, view-only preview even without a configured game route. These are labelled placeholder screens, **not** completed individual game interfaces. When an approved same-origin route is configured, the lobby embeds that existing client. Neither case enables wagering through the lobby. The Return to Lobby control always remains available. Full game-screen previews require the dedicated 6.3–6.8 interfaces to be connected or rendered safely in non-transactional mode.

## Current view-only source adaptations
The Dice tile now opens an offline layout adaptation of `clients/420bet-dice-v1/src/shell.ts` (wallet/session, bet controls, result and history), and Fantasy opens an offline adaptation of `clients/420bet-fantasy/daily/web/index.html` (lineup, standings and challenges). The presentations are **not the full running original clients**; their transactional scripts and RPC dependencies cannot safely run without a configured environment. Every input/action in these adaptations is disabled. Source implementation remains untouched. Other games retain explicit upcoming-screen placeholders pending frontend work in BET-AUDIT-6.3–6.8. The preview implementations must be revisited as the authentic client interfaces become safely embeddable. No tests have been dispatched for this update.

## 6.2 Wallet identity and player transaction history

The lobby can identify a connected EIP-1193 account and chain when a wallet is explicitly connected. It does not inspect wallets on page load. The Connect Wallet action requests `eth_requestAccounts` and subsequent scoped identity refreshes use `eth_accounts`; account/chain/disconnect events invalidate the previous identity. This is **not** wagering authorization, a deposit, a transaction signer, or an account-based authentication proof. Individual games retain their established capability, wallet signing, settlement, and testnet gating.

The lobby defaults to the **same-origin root-relative** `/api/420bet/player-history` route, backed by the optional scoped history server described below. Operators may override or disable this with `window.BET_LOBBY_CONFIG.historyEndpoint`. An unavailable backend shows an error rather than invented records. The browser sends GET with normalized account, decimal chain ID and selected game ID. A conforming service must use independently indexed, finalized or explicitly pending chain records, not browser-reported transaction status; it must validate account ownership/visibility and chain identity, independently authenticate access to any private records, return only scoped records, and apply authorization, privacy, pagination/rate limits and reorg handling. The display accepts at most 100 matching records of the form `{account,chainId,hash,status,game,timestamp}` with `status` in `pending|confirmed|failed|reverted`. No transaction data is available without the configured backend and approved chain/contract bindings; it does not fabricate records or fetch from third-party RPCs. Cross-chain, cross-account and cross-game records fail closed. The canonical 420GP query layer prohibits wallet-wide cross-game activity feeds; the interface queries exactly one selected game at a time.

The UI deliberately provides **no deposit, withdrawal, wager, transfer, or signing action**. Transaction creation/authorization remains with qualified individual game clients and canonical wallet services; a shared universal transaction writer is neither authorized nor implemented here. Without a verified history service and independent deployment configuration, account-linked history is not live and 6.2 cannot be considered end-to-end qualified.

### Scoped 420Indexer history service

`npm run serve:history` starts the Node HTTP service bound to `127.0.0.1:8787` by default (Vite proxies the same-origin history path to it in development). Required environment variables: `BET_HISTORY_INDEXER_URL` (HTTPS, or loopback HTTP for local testing), `BET_HISTORY_CHAIN_ID` (positive decimal chain ID), and `BET_HISTORY_GAME_CONTRACTS` (JSON object mapping **game catalogue IDs to arrays of unique game-specific contract addresses**). `BET_HISTORY_PORT` and `BET_HISTORY_HOST` optionally control the listener. Production hosting must map `/api/420bet/player-history` to this service on the same origin as the lobby; no public service is deployed by this change.

The server consumes existing 420Indexer `/v1/status`, `/v1/transactions`, `/v1/transactions/:hash/receipt` and `/v1/blocks/:id` routes. It returns public, indexed, safe-head transactions only when the wallet, chain, game-specific destination contract, receipt, block hash and timestamp agree. Duplicate or shared contract bindings are rejected to avoid cross-game leakage. These are **on-chain transaction receipts, not wagers or payout-settlement verdicts**. Shared-router transactions cannot be attributed to a game solely from the indexer's transaction DTO and are therefore omitted until product-specific authoritative attribution exists. The indexed data is non-authoritative; game engines and chain settlement contracts remain authoritative.

There are deliberately no invented live contract addresses or chain IDs, and no automatic testnet deployment. The service fails closed unless the operator provides genuine qualified chain/contract bindings. The public endpoint must not be repurposed to expose private account metadata; this is limited to publicly observable on-chain transactions.
