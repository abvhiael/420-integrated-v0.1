## 3. Remaining work — executable order and acceptance gates

### AI-RECOVERY-6.4.3.8 — close settlement authority and correctness gaps (NEXT)

1. Trace **every** full-provider, full-refund and partial-split entry point through `AIJobEscrow`, manager, funding adapter, settlement adapter, Vault authorization/accounting and actual beneficiary. Explicitly document whether full routes and split routes share the one escrow-bound adapter, and reject competing route calls; never assume tests of one route qualify another.
2. Add missing real-contract matrix cases: escrow-close/manager-callback failure after both claims; wrong job/chain/fundingRef/obligation/asset/payer/provider/beneficiary; zero, overfunded and mismatched partial amounts; stale/changed verification or dispute hold; cancellation after claim; competing full/partial settlement and deterministic operation replay. Verify all balance, original/new obligation, Vault accounting, escrow and manager states before/after *every* failing case. Add fuzz/invariant coverage for conservation and single terminal settlement across all routes.
3. Prove least-privilege deployment configuration: governance-bound, vault-scoped action grants, immutable beneficiary/route authority, no arbitrary withdrawals, one bound settlement adapter, explicit signer/owner/upgrade controls and pause/drain path. Evaluate reentrancy, callback gas, denial-of-service and event/receipt reference ambiguity. Repair any discovered contract gaps, then rerun dedicated provider-full, payer-refund, split, AI/Compute and required contract suites on one exact SHA.
4. **Done when:** route and authority matrix is documented; all new negative/fuzz tests are green; independent code/security review of the money-moving contracts is recorded. This closes the *implementation/security-test* subgate only, not testnet settlement.

### AI-RECOVERY-6.4.3.9 — canonical payout/refund reconciliation and safe retries

1. Extend `420-ai-provider` evidence readers to separately model **full provider claim**, **full payer refund** (original provider obligation CANCELLED, distinct payer obligation CLAIMED) and **partial split** (original cancelled and *both* replacement obligations CLAIMED); do not use the original-provider CLAIMED predicate to certify a payer refund. Bind each proof to exact chain/deployment/codehash, job, fundingRef, decision/settlementRef, recipient, amount, Vault operation, receipt and independently checked native balance delta.
2. Persist a privacy-safe, durable settlement state machine and idempotency key. Distinguish *submitted*, *mined but unfinalized*, *finalized*, *reverted*, and *unknown RPC outcome*. On restart or timeout, query canonical finalized operation/obligation states and escrow reference before taking any action; **never create another settlement decision or pay a second leg merely because an RPC response was lost**. Route conflicting/partial observations to operator reconciliation.
3. Exercise disconnected RPC, stale/forged logs, wrong emitter, duplicate or reordered events, chain switch, reorg, reverted second transfer, crash after mined payout and before local checkpoint, and concurrent worker retries.
4. **Done when:** unit/integration evidence tests and a restart/reorg fault matrix pass, with an auditable no-double-pay/no-false-paid rule. Real-chain evidence is a separate gate in 6.4.4/7.

### AI-RECOVERY-6.1/6.2 — qualified signer/executor, chain and identity trust

1. Replace the injected transaction-port assumption with an independently approved operator signer/executor: canonical authority lookup, exact target/calldata/chain/value/deadline constraints, simulation, explicit approval, nonce coordination, transaction submission and immutable hash/receipt capture. Provider keys must not enter browser code, logs or database plaintext.
2. Authenticate ProtocolRegistry and canonical AI/Compute/Vault deployment addresses, proxy implementation where relevant and runtime code hashes against signed/pinned manifests; specify confirmation/finality policy and verify receipts against the chosen canonical chain, not an untrusted `confirmed: true` field.
3. Make output-committed/receipt-submission-failed recovery durable and idempotent: resume the *same* commitment-bound receipt without rerunning inference; block duplicates, stale provider/operator authority and terminal-job resubmission. Test process restarts, nonce competition, transaction replacement, signer denial, malicious RPC and reorgs.
4. **Done when:** signer/executor and canonical reader are security-reviewed and exercise real approved testnet transactions with independently matched state/receipt/finality evidence. Existing `qualified-transactions.ts` and `canonical-rpc.ts` are foundations, not this signoff.

### AI-RECOVERY-6.3 — private payload and actual model serving

1. Integrate `private-payload.ts` with authenticated object storage and KMS/envelope key-release policy; implement Wallet/client-controlled encryption, short-lived provider-scoped access and authorized output retrieval, expiration/deletion and privacy-safe audit. Test unauthorized object access, replay, expired grants, invalid commitments, link/redirect abuse and secret leakage.
2. Resolve a signed provider endpoint/deployment manifest to immutable registry model/version, artifact digest, compatible execution profile and measured GPU/resource limits. Run a real provider worker/model (including bounded inference, cancellation, health, timeout, metering and resource exhaustion), not only a pluggable mock port.
3. Bind input/output commitments to the canonical AI and Compute jobs, result receipt and approved requester retrieval. Qualify one private request end to end on approved testnet, then negative and failure-recovery scenarios. **Done when:** independently authenticated private input → real inference → authorized output, correct commitments and secure key handling are demonstrated and documented.

### AI-RECOVERY-6.5 — independent verification, dispute and payout authorization

1. Specify and connect the authorized **420Trust/Compute verification route** for each applicable workload/policy; attest model/version, inputs/outputs or privacy-preserving commitments, provider/match, receipt and verifier identity. Provider signature or daemon self-report is attribution, **not independent verification**.
2. Add reviewer/challenge/dispute/appeal authority, deadlines, evidence availability, fail-closed settlement holds and explicit decision-to-provider-full/payer-refund/partial-split authorization. Test rejected, absent, contradictory or reorged verifier decisions, disputed jobs, malicious provider and double decision/replay.
3. **Done when:** authorized independently verified outcomes control the real settlement gates, with failure/refund and dispute evidence on approved testnet. Do not enable auto-pay before this workstream is complete.

### AI-RECOVERY-6.6 — user-facing 420AI and operations

1. Complete `ai/web/` wallet-confirmed request creation, model/version/profile selection, bounded spend/deadline/privacy disclosure, payer deposit+funding authorization and unambiguous confirmation/error states. Use approved chain/address manifest and explicit network switching; keep browser writes disabled until canonical executor/funding/verification gates qualify.
2. Connect the read API and Indexer to independently validated canonical hydration. Show separate **draft, awaiting approval, funded, matched, running, output committed, receipt pending, verifying, disputed, claimable, paid/refunded** states; never label an entitlement or submitted transaction as finalized payment. Provide provider/operator job, health, capacity, keys, failure/retry, funding and reconciliation dashboards without exposing sensitive payloads.
3. Deploy a controlled preview, test responsive/accessibility UX, Wallet rejection/network mismatch/expired consent, RPC outage/reorg, safe refresh/history and authorized output retrieval. Implement monitoring/alerts, incident/abuse response, service-level policies, secrets rotation, backup/restore, pause/drain and human reconciliation runbooks.
4. **Done when:** real user/operator acceptance tests pass with feature gates, independently verified requests, no privileged browser custody and reproducible deployments; public paid traffic remains off until phase 7 signoff.

### AI-RECOVERY-6.4.4 and 7 — approved live integration, audit, merge and release

1. Approve a specific testnet: chain ID, RPC trust/finality rules, Genesis/predeploy map, registry bindings, runtime bytecode/proxy hashes, governance grants, funded native asset and signed deployment/service manifests. 2. Independently check finality, event emitters, hashes, job/ref/amount/beneficiary, Vault ledgers and **actual payer/provider balances** before marking paid/refunded.
3. Repeat insufficient funds, duplicate/cross-job consent, wrong chain/address/asset/beneficiary, malicious or failed RPC/signer/storage/model, disputed/rejected result, receiver rejection, second-leg rollback, cancellation/expiry, lost-ack retry, process restart, nonce replacement, chain reorg and provider unavailability. Publish reproducible transaction IDs and signed evidence bundle plus operator recovery outcome; no real funds outside explicitly approved testnet scope.
4. Complete independent security review/audit of funds-moving contracts, keys, provider/storage/API/browser trust boundaries and governance; resolve critical/high findings and document accepted residual risks. Reconcile PR #348 against current `main`, rerun **all separately required** contract, provider, API, web, indexer, Wallet, docs and repository checks on one final SHA, update closeout record, obtain designated release approvals, then make the PR review-ready/merge per project policy.
5. **Overall definition of done:** the authenticated Wallet → paid/private AI service → independent outcome decision → *verified actual* claim/refund lifecycle works reproducibly under success and fault conditions, with pinned deployment/transaction evidence, operational recovery and release signoff. Until then: PR #348 stays draft as appropriate; production paid requests and automatic money movement are **OFF**. A CI-green documentation update does not satisfy these gates.
