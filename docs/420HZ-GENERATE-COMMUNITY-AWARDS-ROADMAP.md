# 420Hz Generate + Community + Awards Roadmap

Status: **PLANNED — new post-foundation 420Hz application phase**

This phase expands 420Hz from the existing music publishing/rights/streaming foundation into a complete AI-native music creation and community product. The user-facing product goal is a clear path from **Generate → refine → register rights/provenance → publish → discover/community → nominate/vote → awards** without creating duplicate authority for identity, rights, payments, compute, storage, governance or indexing.

The repository and current `main` remain authoritative. This roadmap does not claim that public testnet, production model providers, production inference capacity or live awards already exist.

## Product goals

420Hz must let a user:

1. open **Generate your own song** from the 420Hz home page;
2. create an AI-generated or AI-assisted song from a prompt, lyrics and production controls;
3. inspect generation provenance and AI disclosure before publishing;
4. save versions, regenerate sections and retain output artifacts/stems when providers support them;
5. register the resulting Work/Recording through the existing 420 Creative / 420Hz rights model;
6. publish to the 420Hz catalog and playback/discovery surfaces;
7. participate in social/community discovery around songs and artists;
8. enter eligible songs into governed award seasons/categories;
9. nominate and vote under explicit anti-Sybil/eligibility rules;
10. preserve permanent, auditable award results and badges.

## Non-goals / authority boundaries

420Hz is the product/application layer. It must not become a second authority for:

- identity: use 420Identity / Wallet identity where identity is required;
- rights/licensing: use the 420 Creative Protocol rights, authorization and license model;
- AI execution: route inference through 420AI / Compute Market or qualified provider adapters;
- custody/settlement: use 420Pay / canonical economic rails;
- storage: use canonical storage/resource interfaces;
- canonical discovery: use rebuildable 420Indexer/Search projections;
- governance: use 420Governance only where protocol/governed policy is required;
- moderation adjudication or disputes: use the appropriate canonical moderation/arbitration boundaries.

AI inference remains off-chain. On-chain state may commit identities, rights, immutable provenance commitments, award definitions/results and economically relevant settlement data where justified.

## Canonical generation lifecycle

`DRAFT → QUOTED → SUBMITTED → RUNNING → SUCCEEDED | FAILED | CANCELLED → REVIEWED → REGISTERED → PUBLISHED`

A generated artifact is not automatically a published Work or Recording. Publication requires explicit user review and the existing 420Hz rights/registration path.

## AI disclosure classes

Every published recording created through Generate must expose one stable disclosure class:

- **HUMAN** — no generative audio contribution claimed;
- **AI_ASSISTED** — human-authored work with generative assistance;
- **AI_GENERATED** — substantial audio/composition generated by an AI provider;
- **AI_DERIVATIVE** — transformation/remix of an existing source requiring authorization.

Disclosure must not be inferred from provider marketing text. It is explicit metadata bound to the published recording and provenance record.

# HZ-GCA roadmap

## HZ-GCA-1 — Scope, threat model and authority map

Define the complete Generate/Community/Awards product model, trust boundaries and invariants.

Required work:

- map 420Hz ↔ 420AI ↔ Compute Market ↔ Creative Protocol ↔ Identity ↔ Pay ↔ Storage ↔ Indexer/Search ↔ Notifications;
- define authoritative vs derived state;
- define generation, community and award object IDs;
- define privacy classes for prompts, lyrics, draft audio and public releases;
- define moderation/dispute boundaries;
- define retention/deletion behavior for unpublished generation inputs;
- document provider failure, retry and partial-output semantics.

**Exit:** normative architecture document + schemas + threat model; no unresolved authority duplication.

## HZ-GCA-2 — Generation job and provider abstraction

Implement a provider-neutral 420Hz generation job model.

Required capabilities:

- prompt and optional lyrics;
- genre/style/mood/instrumentation controls;
- duration and instrumental/vocal mode;
- optional reference audio only through explicitly permitted paths;
- deterministic client request ID / replay protection;
- quoted cost/capacity envelope;
- job lifecycle, cancellation and timeout;
- provider capability descriptors;
- provider/model version identity;
- output manifest supporting mix, stems, lyrics/timing and artwork references when available;
- provider-independent error taxonomy.

No provider may become canonical protocol authority.

**Exit:** provider abstraction + mocks + lifecycle tests + failure/retry tests.

## HZ-GCA-3 — 420AI / Compute Market execution adapter

Route generation execution through the canonical compute architecture.

Required work:

- 420AI job adapter for music-generation workloads;
- Compute Market worker/provider capability discovery;
- capacity-aware selection;
- price quote / escrow / settlement integration where applicable;
- idempotent submit/retry/cancel;
- result commitment and verification hooks;
- timeout/failure/refund behavior;
- provider reputation/SLA inputs as non-authoritative selection signals;
- a development adapter for deterministic local/mock qualification.

The adapter must support future third-party or first-party models without changing 420Hz publication semantics.

**Exit:** end-to-end test generation using a qualified non-production adapter and the same lifecycle used by real providers.

## HZ-GCA-4 — Provenance, consent and AI rights metadata

Add durable provenance for generated outputs without putting private prompts/audio on-chain.

Required work:

- generation manifest hash;
- provider/model/version identifier;
- creator identity/account binding;
- timestamp and request/result commitments;
- input/reference-content authorization references when applicable;
- AI disclosure class;
- transformation vs training permission separation;
- explicit voice/performer-model consent metadata when synthetic voice identity is claimed;
- source Work/Recording/License references for derivatives;
- immutable provenance versioning at publication;
- clear rule that private prompts/lyrics remain off-chain unless the creator publishes them.

**Exit:** provenance schemas, validation and adversarial tests preventing unauthorized derivative/voice claims.

## HZ-GCA-5 — Project workspace, versions, stems and storage

Implement the creator-side project model.

Required work:

- private generation projects;
- generation history/version tree;
- favorite/selected takes;
- stem/artifact manifests;
- lyrics and metadata drafts;
- delete/archive/export;
- storage integrity hashes;
- quota/resource accounting;
- no accidental public indexing of drafts;
- safe handling of incomplete/failed output sets.

**Exit:** deterministic project state model and storage integration tests.

## HZ-GCA-6 — 420Hz Generate Studio UX

Build the primary **Generate your own song** experience.

Required screens:

- Generate landing page;
- prompt/lyrics composer;
- advanced music controls;
- cost/capacity preview;
- generation progress;
- A/B take comparison;
- audio player and stem preview where available;
- provenance/disclosure panel;
- save/regenerate/remix controls;
- explicit **Register & Publish** handoff;
- failures/retry/refund state;
- responsive/mobile behavior and accessibility.

The home page must contain a prominent **Generate your own song** call to action.

**Exit:** fully navigable Generate workflow against qualified mock/dev execution.

## HZ-GCA-7 — Register & Publish integration

Connect generated outputs to existing 420Hz music primitives.

Required work:

- create or select Creator Profile;
- register Work;
- register Recording;
- contributor credits;
- rights split review/acceptance;
- derivative/source authorization checks;
- immutable generation-provenance commitment;
- AI disclosure publication;
- media manifest/storage publication;
- catalog release creation;
- rollback/failure handling so generation success never implies registration success.

**Exit:** one complete Generate → Work → Recording → Release flow on repository/local qualification infrastructure.

## HZ-GCA-8 — Community identity and social graph

Add non-custodial community features around artists and songs.

Initial V1 surfaces:

- follow/unfollow artists;
- like/favorite songs;
- save to playlists/collections;
- repost/share references;
- artist/community profile activity;
- optional comments/replies only if moderation/reporting is fully implemented;
- block/mute/report;
- privacy-aware notification preferences.

No raw social metric is canonical economic truth.

**Exit:** community APIs/store + abuse/authorization/privacy tests.

## HZ-GCA-9 — Charts, discovery and anti-gaming

Create transparent discovery and chart projections.

Required work:

- trending songs;
- new releases;
- generated/AI-assisted filters;
- genre/mood/category discovery;
- community favorites;
- bounded time-window charts;
- distinct listener/identity signals where privacy permits;
- anti-bot/rate-limit/duplicate-event controls;
- explicit separation between raw plays, qualified plays, likes and award votes;
- rebuildable indexer projections;
- explainable chart methodology/version.

**Exit:** deterministic replay-safe chart projection with adversarial anti-gaming fixtures.

## HZ-GCA-10 — Awards domain model

Implement a dedicated 420Hz Awards model.

Objects:

- Award Program;
- Season;
- Category;
- Eligibility Policy;
- Nomination;
- Ballot;
- Vote Commitment / qualified vote record;
- Result;
- Award Badge / historical recognition record.

Initial category framework should support, without hard-coding a permanent list:

- Song of the Year;
- Artist of the Year;
- Best AI-Generated Song;
- Best AI-Assisted Song;
- Best Remix / AI Derivative;
- Best Instrumental;
- Best Lyrics;
- Best Production;
- Community Choice;
- Breakthrough Artist.

Category definitions must be versioned per season.

**Exit:** award schemas/state machine + policy validation.

## HZ-GCA-11 — Eligibility, nominations and voting

Build the award participation rules.

Required work:

- eligibility windows;
- published-recording requirement;
- AI disclosure/category compatibility;
- nomination caps and duplicate prevention;
- creator self-nomination policy configurable per category;
- community nomination thresholds where used;
- ballot construction/freeze;
- Identity/Wallet eligibility proof where required;
- one-person/one-identity or other explicit voting policy per category;
- anti-Sybil protections without exposing unnecessary identity data;
- vote replay protection;
- abstention/invalid ballot handling;
- quorum/threshold/tie policy;
- deterministic close/finalize process;
- no retroactive mutation of a closed season.

**Exit:** complete nomination → ballot → vote → finalize lifecycle with adversarial tests.

## HZ-GCA-12 — Awards UX and permanent history

Build the public awards experience.

Required screens:

- Awards landing page;
- current season/countdown;
- category browser;
- eligibility rules;
- nomination UI;
- ballot/voting UI;
- live status without leaking secret/private ballot material;
- winners/results pages;
- artist/song award badges;
- permanent season archive;
- provenance links from winner → Recording → Work → creator/rights data.

**Exit:** complete usable awards flow against deterministic fixtures.

## HZ-GCA-13 — Rewards and prize settlement

Add optional award prizes without coupling award legitimacy to token rewards.

Required work:

- prize schedules per season/category;
- Treasury/Grants/Pay source-of-funds boundary;
- eligibility and sanctions/abuse checks where applicable;
- finalized-result commitment before payout;
- exact recipient/amount/purpose binding;
- replay-safe settlement;
- failed payout recovery;
- public accounting projection.

Awards may exist with zero financial prize.

**Exit:** representative zero-prize and funded-prize settlement paths with accounting conservation tests.

## HZ-GCA-14 — Notifications, Search, Analytics and Explorer integration

Integrate the new surfaces with the ecosystem.

Required events include:

- generation completed/failed;
- project ready for review;
- release published;
- follow/community activity;
- nomination received/accepted;
- voting opened/closing;
- award won;
- prize settlement status.

Search/discovery must understand AI disclosure and award metadata. Analytics must separate generated content, community engagement and award participation without turning derived metrics into protocol authority.

**Exit:** same-object cross-service integration tests and rebuild/replay qualification.

## HZ-GCA-15 — Moderation, abuse, privacy and adversarial hardening

Perform dedicated abuse/security qualification.

Coverage:

- prompt injection across provider/tool boundaries;
- malicious media/metadata;
- unauthorized reference audio;
- unconsented voice/persona claims;
- derivative-rights bypass;
- spam generation/resource exhaustion;
- wallet/session replay;
- vote stuffing/Sybil patterns;
- collusive nominations;
- chart manipulation;
- report/block/mute bypass;
- provider result spoofing;
- storage hash mismatch;
- stale/reorged derived state;
- private draft/prompt leakage;
- secrets/provider-token leakage;
- unsafe HTML/URL/media metadata.

**Exit:** documented threat-model closure with negative/adversarial tests.

Required home/navigation changes:

- primary **Generate** nav item;
- hero CTA **Generate your own song**;

- Charts;
- Awards;

The existing official 420Hz branding remains canonical.

**Exit:** website verifier covers all new product entry points and no unavailable live action is represented as active.

## HZ-GCA-17 — Repository phase qualification and closeout

Apply the project's three-level qualification model.

### Level 1 — per-step fast qualification

For HZ-GCA-1 through HZ-GCA-16, run only tests/builds/verifiers directly relevant to the changed surface. Do not rerun unrelated global qualification after every step.

### Level 2 — milestone qualification

Run broader integrated qualification at these milestones:

- **M1 Generate foundation:** HZ-GCA-1 through 7;
- **M2 Community:** HZ-GCA-8 through 9;
- **M3 Awards:** HZ-GCA-10 through 13;
- **M4 Product integration/hardening:** HZ-GCA-14 through 16.

### Level 3 — one phase closeout

After repository-side steps are complete, run one exact-head phase qualification covering all new Generate/Community/Awards surfaces and their directly affected dependencies. Commit durable evidence, reconcile with current `main`, and mark repository-side HZ-GCA complete.

Evidence-only closeout commits inherit the qualified SHA and do not require blind substantive reruns unless they change executable/configuration behavior.

**Exit:** repository-side phase COMPLETE with durable evidence.

# Definition of repository-side success

Before testnet, this phase is complete only when a user can exercise a deterministic end-to-end non-production path:

**Generate song → review provenance/disclosure → register Work/Recording → publish release → discover/favorite/follow → nominate → vote → finalize award → show permanent badge/history**

using qualified local/dev providers and fixtures, with live-only actions still fail-closed where public infrastructure is unavailable.
