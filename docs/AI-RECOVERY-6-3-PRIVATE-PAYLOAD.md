# AI-RECOVERY-6.3 — private payload transport

Status: **PARTIAL — encrypted job-scoped adapter implemented; production service and model serving pending**.

`420-ai-provider/src/private-payload.ts` implements `PayloadPort420` for the existing provider runtime with job/provider-bound AES-256-GCM envelopes, random opaque 256-bit object identifiers, authenticated context (`420-ai-private-object-v1|jobId|providerId|objectId|purpose`), input plaintext Keccak-256 commitment comparison against the canonical Compute request, explicit access checks, short-lived capability expiry, and a maximum object size of 32 MiB. The `get` method accepts only `420ai:private:v1:<64 lowercase hex>` references; never HTTP URLs, paths, redirects, or remotely supplied object names. The service exposes separate `putOnce` and `get` opaque-object storage ports and an independently supplied key-release port. Output is encrypted before writing to object storage. `put` returns an opaque output reference; it does not itself publish or authorize release of output decryption keys.

**Production constraints:** Both the object-store service and key-release service MUST independently authenticate and authorize their callers using canonical chain state, provider/job identity, purpose, privacy policy, expiry, and storage ACLs. The injected `PayloadAccess420` callback is an additional application-layer guard, not a substitute for enforcement within those services. Do not use static job-independent keys, log plaintext or keys, or expose output key release before authorized result access. A client provisioning a private input must encrypt with purpose `input`, the exact job/provider/object context above, a unique 96-bit nonce and a 256-bit per-object key delivered to the qualified key-release service over an authenticated channel. The versioned envelope is: `0x01 || nonce[12] || authenticationTag[16] || ciphertext`. Private input bytes must have been committed in the canonical Compute request before provider processing. Neither object IDs nor commitments are authorization credentials.

The adapter implements only payload encryption/decryption and input integrity, with unit tests for tampering, access denial, expiry, commitment mismatch, opaque-reference validation, and encrypted output. It **does not implement** an authenticated storage server, key-management service, authorized output download, signed deployment/model manifest, concrete model-serving backend, or private end-to-end testnet flow. Model artifact/runtime-profile checks must be tied to immutable model-version registry state; do not enable paid inference or mark 6.3 production-qualified until these integrations are tested.
