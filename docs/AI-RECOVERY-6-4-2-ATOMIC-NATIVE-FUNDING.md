# AI-RECOVERY-6.4.2 — Atomic native job funding (implementation candidate)

`contracts/src/ai/AINativeVaultFundingAdapter420.sol` introduces a direct-payer, native-asset funding route. The payer signs one payable EVM transaction calling `fundNative(jobId, providerId, nonce)` with the exact deposit amount. Within that **same transaction**, the adapter validates canonical manager job requester, CREATED state, deadline, maximum spend and active/staked provider settlement beneficiary; deposits `msg.value` into the approved AssetVault; calls `AssetVault420.createObligation` for an exact, deterministic job- and payer-scoped obligation; checks the recorded obligation; then invokes the escrow's governance-bound `confirmVaultFunding`. All steps, including consumed-job and payer-nonce mappings, revert together if any call fails. The adapter does not retain funds, accept arbitrary ETH transfers, import earlier deposits or withdraw/settle/refund funds.

**Authority:** Governance must independently verify the AIJobManager, AIJobEscrow, AIProviderRegistry, Vault, VaultAccounting, VaultRegistry and VaultAuthorization deployment addresses, bytecode and registry entries. Governance must bind the escrow vault adapter and authorize this adapter for only the needed `ACTION_CREATE_OBLIGATION` capability on the single Vault. Do not grant general withdrawals, settlement or arbitrary beneficiary/asset routing. Registration of the Vault must be ACTIVE. Reject inconsistent or unapproved deployments before deployment or operator activation; constructor address checks alone are not deployment authentication.

**Separate historical preflight:** `420-ai-provider/src/vault-funding-intent.ts` is an EOA-only, read-only verifier for a *direct payer-to-Vault* deposit. It is **not** the authorization for `fundNative`, whose payer makes the external transaction to the adapter and whose Vault deposit is internal and emitted with the adapter as depositor. Do not treat either preflight as consumed user approval or use an off-chain deposit transaction to call escrow confirmation. The atomic adapter does not support relayers, EIP-712 offline signatures, ERC-1271 contract wallets or ERC-20 deposits. Those require independently implemented and qualified routes.

**Known deployment and security gates:** Integration tests with real VaultRegistry420, VaultAuthorization420, VaultAccounting420, AssetVault420, AIJobEscrow and canonical 0x0431 AIJobManager predeploy are still necessary: synthetic mocks cover local transaction atomicity but not governance capability checks or real escrow-manager callbacks. Test asset segregation, third-party deposits, duplicate job/nonce, failed deposits/obligation creation/escrow callbacks, contract-receiver reentrancy, expired/unfunded/cancelled jobs, provider status/beneficiary changes, wrong chain/address, and adversarial registry states. The `NativeJobFunded` event is an observation, not itself proof of chain finality. A confirmed transaction receipt must prove the deposit, obligation and escrow transitions at approved addresses and verified block history. Run full Forge build/tests and production configuration review before treating this code as CI-qualified.

**Still blocked:** Actual testnet deployment, independently established chain finality, Wallet UI transaction confirmation, provider claim, separate payer refund/cancellation and partial-charge accounting, independent 420Trust outcome verification, and full paid-job E2E. Paid AI and privileged browser writes stay disabled. Phase 6.4.2 is not production-complete on a mocked unit test alone.
