# AI-RECOVERY-6.4.2 — Signed native funding preflight (partial)

`420-ai-provider/src/vault-funding-intent.ts` adds a **read-only, EOA-only** EIP-712 funding intent verifier. It verifies an EOA payer signature over chain-specific Vault domain, job/provider IDs, payer, beneficiary, Vault ID and address, funding reference, unique intended obligation, deposit transaction hash, exact native amount, nonce and expiry. It reuses the confirmation-pinned native deposit evidence reader and requires a still-unfunded escrow plus a dedicated RESERVED native-asset obligation with the matching Vault ID, funding reference, beneficiary and amount. Tests include tampered job/payer/domain, expiry, mismatched reservation and reorganized/incorrect deposits.

**Not a payment authorization or readiness certificate:** The signed message is not currently consumed by an on-chain funding adapter; its nonce, deposit transaction hash and obligation ID are not durably claimed or made unique across jobs. The same real deposit could therefore appear in multiple off-chain preflights. A RESERVED obligation with a matching arbitrary source reference does not independently establish its provenance from that deposit, the payer's ownership of deposited funds, a per-job balance reservation, or uniqueness. An EOA signature does not prove an actual Wallet UI confirmation; ERC-1271 smart-contract wallets and ERC-20 deposits are unsupported. An externally supplied RPC/reader could lie, and confirmation depth is not independent consensus finality. No service should treat this helper's return as permission to call `AIJobEscrow.confirmVaultFunding`.

**Next gates:** Implement and audit a governance-authorized on-chain adapter that verifies a chain/domain-scoped user approval, consumes the nonce/deposit/obligation atomically, enforces unique job binding and exact per-job collateral from independently proven deposit+accounting evidence, and invokes escrow confirmation only after all custody rules pass. Bind independently approved deployments, signer authority, registry and finality policy. Add ERC-1271 and ERC-20 only through distinct qualified paths. Exercise duplicate/depleted deposit, cross-job, cancellation, rollback and reorg scenarios on testnet before enabling paid AI or declaring phase 6.4 complete.
