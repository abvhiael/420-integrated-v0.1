# AI-RECOVERY-6.4.3.4 — partial settlement and retry safety

**Status: in progress; partial payouts are NOT implemented, deployable or enabled.** The code in `contracts/src/ai/AINativePartialSettlementPlan420.sol` is a deterministic non-custodial planner. It creates no obligations and sends no funds. The provider-full and payer-full paths remain distinct.

## Verified design constraint

The 6.4.3.2 native funding adapter creates a single immutable, RESERVED provider-beneficiary obligation for the entire funded amount. `AssetVault420.releaseObligation` does not split amounts; it changes the entire obligation to CLAIMABLE. `cancelObligation` frees a reservation without paying anyone. `AIJobEscrow.release` and `refund` each close the escrow and announce the **full** original amount, so neither may be called to report a partially paid job. `AIJobManager.confirmSettlement` currently allows only VERIFIED -> SETTLED; partial-provider earnings must require a separately approved decision and must not be inferred from the VERIFIED state alone.

## Required implementation beyond the planner

1. Introduce an escrow-authorized `markSplitClaimable` / `closeSplit` transition with an explicit provider amount, payer amount, and paired Vault claim/operation identifiers. Preserve existing `EscrowState` numeric values by appending any new state. Do not reuse the full `Released` or `Refunded` event, because that would falsely report the original full amount for one leg. Confirm the manager's terminal state only after **both** actual claims succeed.
2. Add one approved on-chain split operation to the **single escrow-bound** combined adapter. Bind chain, adapter, job, fundingRef, original obligation, decision, payer, original beneficiary and both amounts. Revalidate that the original obligation is RESERVED and equals the escrow's full amount. Disallow splitting a released/claimed/cancelled obligation, a job with an active dispute, an already terminal escrow, a zero leg, or a provider amount exceeding funding.
3. Within one EVM transaction, cancel the original reservation and create two distinct immutable native obligations using the plan IDs, for the exact provider-earned and payer-unused amounts. Confirm both reservations and the conservation equation before any external recipient calls. This replacement's free-balance gap is only within a reverting, non-reentrant transaction; no intermediate claim/withdraw/escrow closure is permitted. Restrict the adapter's Vault capabilities to the specific approved vault/actions via governance, not blanket withdrawal.
4. Release and claim **both** new obligations and verify each independently: recipient, asset, source fundingRef, vault, amount, CLAIMED state, exact native balance delta, and executed Vault claim operation. The two recipient callbacks can revert; any failure must revert *all* preceding cancellations, reservations, releases and transfers. Only then close the escrow with accurate split-specific events and manager callback. Prevent provider/refund route concurrency and replay through original-reservation state, terminal escrow state, per-job terminal marker and deterministic action IDs.
5. For an already-mined transaction, retry logic MUST read canonical finalized Vault operation and both immutable obligation states and compare the escrow terminal reference; a timeout or RPC failure is **unknown**, not a failed transfer. Never submit a fresh payment with a new decision reference merely because a claim response timed out. Re-submit the same deterministic transaction only after the original transaction is confirmed absent under the approved finality/replacement policy and no leg has been claimed. A partial or ambiguous chain observation must go to manual reconciliation, not automatic replay.
6. The legacy provider runtime `VaultReconciliation420.verifyPaid(..., 'refund')` is insufficient for refunds: it demands CLAIMED state of the **original provider** obligation, whereas the actual full refund cancels that obligation and claims a **new payer** obligation. Do not use that method to certify refunds or retry a payout. A 6.4.3.3 full-refund verifier must check original CANCELLED, distinct payer CLAIMED, payer receipt and the exact settlementRef on the canonical chain; partial reconciliation must verify both split obligations, not either alone.

## Qualification gate

- Current `AINativePartialSettlementPlan420.t.sol` is **planner-only** coverage: conservation, positive legs, identity-bound deterministic operation IDs, and invalid inputs. It is not a payout test.
- Before declaring 6.4.3.4 complete: mock and real-contract adversarial tests for both successful native transfers, exact ledger deltas, lack of generic withdrawal, wrong payer/provider, mismatched funding, all callbacks, replay/competing full settlement, dispute hold and receipt ambiguity. Run all earlier AI/Compute, provider-full and payer-full tests against the final **single escrow-bound** adapter. Prove full VaultRegistry/VaultAuthorization/VaultAccounting/AssetVault/escrow/manager integration and separately approved testnet finality before enabling live transfers.

**Do not describe the planner as implemented partial settlement, and do not enable partial charges or automatic retries while these gates remain open.**
