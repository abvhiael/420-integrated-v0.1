## Actual call graphs

| Path | Preconditions in adapter | Escrow operations | Vault operations | Terminal manager operation | Payout beneficiary |
| --- | --- | --- | --- | --- | --- |
| Full provider: `AINativeSplitSettlement420.payProvider` (inherited from `AINativeProviderSettlement420`) | governance caller; exact bound adapter; consumed funding; VERIFIED; escrow FUNDED, no settlementRef; matching payer/providerId/vaultRef/fundingRef/amount and original RESERVED native provider obligation | `markClaimable` then `release` | release original, claim original | `confirmSettlement` => SETTLED | immutable original provider beneficiary |
| Full payer: `AINativeSplitSettlement420.refundPayer` (inherited from `AINativeSettlementWithRefund420`) | governance caller; exact bound adapter; consumed funding; FUNDED/EXPIRED/FAILED; escrow FUNDED and matching original RESERVED obligation | `markRefundable` then `refund` | cancel original, create payer obligation, release payer obligation, claim payer obligation | `confirmRefund` => REFUNDED (subject to manager transition) | original escrow payer |
| Partial split: `AINativeSplitSettlement420.settleSplit` | governance caller; exact bound adapter; consumed funding; VERIFIED; escrow FUNDED; provider != payer; original RESERVED; 0 < providerAmount < original amount | `markSplitClaimable` then `closeSplit` | cancel original, create two distinct obligations, release both, claim each | `confirmSettlement` => SETTLED | immutable escrow provider and payer |

All operations occur within one EVM transaction; failure during the second claim or terminal manager callback should revert earlier transfers, operation IDs, obligation mutations and escrow state. `AIJobEscrow.bindSettlementAdapter` permits one one-time binding, and all three adapter functions require `escrow.settlementAdapter() == address(this)`. Do not bind the provider-only or refund-only parent instead of the intended split adapter. Full/partial routes have separate route-specific flags; terminal manager, escrow state and obligation state, not a unified per-job flag, provide cross-route exclusion. The new `AINativeSettlementRoutes420.t.sol` tests exercise representative cross-route cases; additional fault injection and independent security review remain necessary.

## Authority and permissions — requested deployment policy, NOT attested deployed grants

| Principal | Vault capability | Scope and justification |
| --- | --- | --- |
| Native funding adapter | `ACTION_CREATE_OBLIGATION` | ONLY the selected `vaultRef`, original native funding reservation. No release/cancel/claim/withdraw. |
| Single escrow-bound split settlement adapter | `ACTION_CANCEL_OBLIGATION`, `ACTION_CREATE_OBLIGATION`, `ACTION_RELEASE_OBLIGATION`, `ACTION_CLAIM` | ONLY the selected `vaultRef`, to replace an original obligation with payer/provider entitlements and execute claims. No `ACTION_WITHDRAW`, no Vault administration, no unrelated vault grants. |
| Governance/decision executor | no direct Vault payout capability for this path | May call adapter entry points only after independently approved decision; forbid broad Vault grants that could bypass escrow or alter unrelated obligations. |
| Provider/payer | no privileged Vault action grant | May receive via exact immutable obligation beneficiary. A beneficiary's general ability to claim its own *already released* obligation is distinct from authority to release/cancel/create it. |

`VaultAuthorization420.isAuthorized` supplies **vault-scoped action capabilities**, not an obligation-id, job-id, or immutable-beneficiary scope for cancel/create/release/claim. `AssetVault420` enforces those action grants but is agnostic to 420AI job identity. Consequently a compromised *other* principal with release+claim or cancel+create+release+claim grants over the same vault may bypass the adapter's job-level checks. A vault-scoped CREATE grant also permits creation of arbitrary obligation parameters at the Vault entry point; it is the adapter code and constrained grant principal—not VaultAuthorization alone—that limits this to native, job-bound beneficiaries. Confirm there are no other conflicting grants in the approved deployed CapabilityRegistry and no competing operators or privileged paths. If exclusive job-level protection is required against unrelated holders of valid Vault grants, use a dedicated 420AI Vault or strengthen the authorization model with obligation/job-scoped policy; do not describe existing vault-scoped grants as obligation-scoped.

`governance` is an immutable direct caller check. `decisionRef != 0` is not an on-chain signature, 420Trust validation, unique decision registry, dispute-epoch attestation or proof of approval; the separately planned 6.5 verification/dispute authority and 6.1/6.2 signer/executor gates remain necessary. A previously approved reference cannot by itself establish that dispute status or verification authority stayed unchanged when the transaction was submitted. The live deployment must authenticate governance signer/timelock and ownership, manager/escrow/funding/Vault/accounting addresses, CapabilityRegistry grant state, codehashes and pause/winding-down behavior. Claims remain possible only while Vault is not CLOSED; create requires ACTIVE, and release/cancel allow ACTIVE or WINDING_DOWN, so a mid-settlement transition to WINDING_DOWN blocks refund/split creation and safely reverts, but operational recovery must be planned.

`AssetVault420.claim` calls the native beneficiary and uses its non-reentrant lock; the route adapters have separate route-specific locks. The escrow's intermediate CLAIMABLE/REFUNDABLE/SPLIT_CLAIMABLE state prevents a competing route during a recipient callback. Examine gas-exhaustion/nonpayable recipients and external callback effects in security review. A revert of the last manager callback must also revert both native transfers; add explicit real-contract fault injection rather than inferring this solely from second-recipient rejection.
