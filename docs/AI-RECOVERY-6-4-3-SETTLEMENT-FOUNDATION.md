# AI-RECOVERY-6.4.3 — settlement and refund authority reconciliation

Status: **design and contract-gap analysis only; no payout or refund enabled**. The 6.4.2 scoped Foundry build and nine tests passed on PR #348 at commit `4ad0c58c8cdf34b874d3c8a3638819160cbf3365` (run 35479476314). That run does not qualify on-chain settlement or a live deployment.

## Existing, independently observable behavior

- `AINativeVaultFundingAdapter420.fundNative` creates one **native, RESERVED (state 1)** Vault obligation for the provider's settlement account. The obligation ID is `keccak256(abi.encode("420AI_NATIVE_OBLIGATION_V1", fundingRef))`; `fundingRef` binds chain, funding adapter address, job, payer and nonce. Funding is atomic through `AIJobEscrow.confirmVaultFunding`.
- `AIJobEscrow.markClaimable` / `markRefundable` only update escrow entitlement; `release` / `refund` only close escrow and call manager callbacks. **None of those methods invokes the Vault or transfers native value.** Calling `release` before a proven Vault claim would create a false paid status.
- `AssetVault420.releaseObligation` changes an existing obligation from RESERVED to CLAIMABLE, retaining its **immutable beneficiary**. `AssetVault420.claim` pays that beneficiary and records CLAIMED (state 3) atomically. `cancelObligation` instead moves RESERVED to CANCELLED (state 4), releases its reservation, and does **not** pay the payer. A cancelled provider obligation cannot be changed into a payer obligation or claimed by the payer.
- `AssetVault420.withdraw` of formerly reserved native value requires a recipient/asset/action-bound route authorization (or a direct self-withdrawal), distinct from `ACTION_CREATE_OBLIGATION`. `VaultAccounting420.recordWithdrawal` enforces free balance but has no job-level refund entitlement. Consequently **cancelling the provider obligation and calling `withdraw` is not, by itself, sufficient proof of an authorized job refund**.

## Required 6.4.3 architecture

1. **Provider-claim route:** a separately governance-bound settlement adapter verifies the exact escrow job, original funding reference, Vault ID, provider beneficiary, asset, amount and matching RESERVED obligation. A settlement authorization must bind the approved result/verification policy and prevent settlement during a dispute or active hold. It may then release that same obligation to CLAIMABLE. The provider can execute `AssetVault420.claim` as the recorded beneficiary; an independent receipt/balance check must prove the CLAIMED obligation and exact native transfer *before* any escrow `release` or manager settlement callback. There must be no generic arbitrary-recipient withdrawal capability.
2. **Payer-refund route:** require a distinct, authorized cancellation/refund decision bound to the same job and original funding reference. Atomically cancel the provider's RESERVED obligation and create a **new, distinct payer-beneficiary obligation** for the exact refundable amount before marking the escrow REFUNDABLE. Reserve its amount for that job rather than sending the newly free balance through a generic withdraw. Release the payer obligation, permit its immutable payer beneficiary to claim, and prove CLAIMED state and exact receipt/balance transfer before escrow `refund` and manager refund callback. Provider and payer entitlement must never be simultaneously claimable.
3. **Partial charge:** 6.4.2's single immutable provider obligation cannot be split. Add a separately reviewed, authorized, atomic reservation-replacement route creating *two* job-bound obligations (provider-earned amount and payer-unused amount), with total never exceeding original funding and no intermediate externally withdrawable unreserved balance. Do not implement partial charges by assuming `releaseObligation` transfers only a portion; it releases the entire immutable amount.
4. **Replay and failure:** bind unique operation IDs to chain, settlement adapter, job, fundingRef, action and claim/refund leg. Keep explicit on-chain per-job terminal state and prevent double release, cancellation, cross-job obligation reuse, beneficiary substitution and concurrent provider/refund claims. A failed claim, beneficiary callback, ledger update, or escrow-manager callback must not allow the escrow to report payment that did not occur. Record and reconcile pending/retry status without resending money after an already-confirmed transfer.
5. **Authority:** deploy against independently approved registry, codehash and governance bindings. Narrow Vault capabilities to exact action and asset/recipient/amount or immutable beneficiary as appropriate; avoid handing the funding adapter settlement, arbitrary-withdrawal or refund authority. An escrow adapter binding is not itself an authorization to move Vault assets.

## Implementation order and minimum qualification

- **6.4.3.1 — guard and evidence specification:** define typed on-chain payout/refund references, authority model, immutable operation/obligation IDs and strict state transitions. Add negative tests that verify escrow events and `CLOSED` state cannot be used as payment proof in isolation.
- **6.4.3.2 — full-amount provider claim:** implement and test separately authorized release and actual native Vault claim, followed by escrow/manager confirmation only on observed `CLAIMED` state. Test direct unauthorized callers, wrong job/provider/beneficiary, insufficient/incorrect obligation, claim receiver revert, replay and dispute hold.
- **6.4.3.3 — full payer refund:** implement and test a separate payer-beneficiary obligation and claim path, with cancellation authorization, exact amount and rollback/replay tests. Refund entitlement alone is not funds movement.
- **6.4.3.4 — partial charges and retries:** add atomic entitlement split and terminal reconciliation after security review, plus adversarial interleavings, duplicate transaction attempts and failed external callbacks.
- **6.4.3.5 — real integration:** run with real VaultRegistry, VaultAuthorization, VaultAccounting, AssetVault, escrow, manager and governance bindings. Prove exact beneficiary/payer native balance deltas and independently validated receipts/finality on the approved testnet. Keep paid AI and automatic settlement feature-gated off until verified.

**Do not mark 6.4.3 complete or enable production payout on the basis of this document, the 6.4.2 mocked unit tests, a `Released`/`Refunded` event, or an escrow `CLOSED` state.**
