# BG-19.19 — scoped social HTTP contract and outstanding launch evidence

**Repository increment:** `services/bong-goggles-indexer-v1/src/scopedSocialHttp.js` exports an opt-in, non-listening route adapter for GET `/v1/scoped/feed?feedClass=HOME|FRIENDS|FOLLOWING&limit=1..50&cursor=...` and GET `/v1/scoped/record?resource=profile|relationships|community&subject=...`. The service must provide `createScopedSocialRead` and `createScopedSocialPagination` instances with `configured === true`. The adapter does not instantiate listeners, accept an unverified browser wallet address, or enable public deployment. It expects an opaque credential supplied by a separately audited authenticated HTTP ingress. It never treats its callbacks' `configured` flag as proof of their implementation or independent qualification.

**Safety properties in repository:** exact versioned response envelope, bounded query and credential parameters, GET only, no-store and privacy headers, minimum record field allowlists, cursor shape validation, no unauthenticated result, no arbitrary projection DTO serialization, minimal redacted failures. For feed pagination, the signing key must be strong and operator managed; `readPage` must return exact snapshot-bound deterministic ordering with truthful `hasMore` and current per-record authorization. Existing `scopedSocialPagination.js` enforces signed per-viewer/session/chain/partition cursors, compares checkpoint hashes and rechecks sessions and canonicality after asynchronous reads. Existing `scopedSocialRead.js` provides a first-page record authorization guard. These are code boundaries, not credential or canonical-state providers.

**Unresolved blocking dependencies — do not claim BG-19.19 complete or release:**

1. Identify exact deployed 420Wallet/420Identity session verifier, signature/session chain binding, credential transport, revocation source, logout propagation and CSRF model. Inject `verifySession` from that verified provider; forbid a caller-specified viewer. A mock `verifySession` in unit tests is not an integration.
2. Connect `readCanonicalState`, `readProjection` and `readPage` to independently evidenced current canonical sources with block hash/finality/lag/reorg checks and stable snapshot-bound ordering. Connect `authorizeRecord` to real audience/relationship/member/block/mute/author/moderation policy; verify before each record and revalidate after policy change. No index-only audience check can grant access.
3. Implement a dedicated authenticated HTTP ingress, route-to-guard wiring, strict credential ownership and CSP/CORS/origin/cookie/CSRF/access-control/rate-limit/timeout controls appropriate to the selected session transport. This file is NOT that ingress, and it must never be mounted into the anonymous BG-19.17 public listener or share that listener's credential rejection behavior.
4. Provide separate authorized content/media delivery with current entitlement checks, and decide how HOME/FRIENDS/FOLLOWING DTOs include protected content without leaking it or restricting legitimate authenticated viewers. The current HTTP feed DTO is **PUBLIC POST only**, so it intentionally denies private-audience feed records even when a scoped policy guard authorizes them; it is not a functional finished HOME/FRIENDS feed.
5. Implement qualified public DISCOVER `hasMore` and cursor semantics separately; `publicFeedHttp.js` still returns a single bounded sample with `hasMore:false`. Its snapshot and content visibility requirements remain BG-19.16/17/18 deployment blockers.
6. Run actual service/browser integration tests with two separate Wallet accounts, private group and relationships, revoked and expired sessions, access and moderation withdrawals during pagination, canonical reorg and index lag, cross-account replay, over-limit requests, DNS/TLS/edge validation and zero private metadata leaks. Record environment, exact commit, chain, policy versions and external smoke outputs.
