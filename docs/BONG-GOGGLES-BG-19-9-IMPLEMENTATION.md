# BG-19.9 — games application and zero-wager boundary

Status: WEB MODEL AND PRESENTATION IMPLEMENTED; EXACT-HEAD CI QUALIFICATION AND LIVE INTEGRATION PENDING.

## Implemented

- `bong-goggles/web/core/games.js`: seven BG-15 qualified game types; canonical session normalization; viewer/participant, lifecycle and winner validation; incoming/outgoing invite, active and terminal-session partitions; state and current-policy-aware actions; zero-wager Wallet intent preparation; qualified-turn and move-number gating; deterministic canonical session links; no local session/winner/reward authority.
- `bong-goggles/web/core/games-ui.js`: responsive-compatible games hub and session-detail markup; incoming/outgoing challenges, active games, past games, qualified statistics/leaderboard presence, move-commitment history, turn/board unavailable states, and explicit zero-wager and deferred-reward notices. No wager/stake/escrow/odds/settlement UI.
- `bong-goggles/web/core/app-shell.js`: guarded `/games` route consumes optional `gamesProjection`, matching existing app-shell presentation injection.
- `bong-goggles/web/test/games.test.js`: verifies identity, lifecycle, deterministic categories, action eligibility, zero-wager rejection, sequence/turn safety, fail-closed states and route rendering.

## Authority and safety

`BongGogglesGameSessionRegistry420` owns session identity, game type, immutable ruleset hash, lifecycle, next move number, move commitment and terminal winner. BG-15 services supply current policy, verified ruleset/turn and qualified application history/stats. Presentation-only leaderboards, clocks and board views cannot authorize reward payouts or wagers. Game rewards remain deferred under BG-18; wagered play belongs in 420Bet.

## Remaining live integration gates

The BG-19 browser `app.js` does not yet load or pass a games projection from a deployed qualified BG-15 HTTP service. An interactive game engine/board, policy/ruleset revalidation, session deep-link resolution on refresh and reconnect, game notification deep links, invite/accept/decline/cancel/rematch handlers, move-commitment preparation/submission and final receipt reconciliation must be integrated before BG-19.9 can be called operational end-to-end. A disabled New challenge control is intentional until verified ruleset, recipient policy and Wallet transaction handling are available. The action metadata generated by `games.js` is *not* a signed transaction or permission grant.

BG-19.14 end-to-end product journeys and BG-19.15 release closeout must treat these outstanding gates as blockers; green unit/build CI alone is not evidence of live games usability.
