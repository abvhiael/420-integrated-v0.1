# BG-20.2 — privacy-safe observability and alerting

**Status: deterministic operator-side schema and alert decisions implemented; live collector, pager, staging fault injection and retention controls NOT verified.** This code does not alter public ingress, deployment flags, launch approval or user-facing application behavior. BG-19 remains unfinished.

## Repository implementation

`bong-goggles/web/core/operational-observability.js` exports `validateAggregateWindow` and `evaluateObservability`. It takes an exact, one-hour-or-shorter aggregate window bound to a named environment and release ID. Accepted numerical fields: requests, errors, p95 request latency, index lag, finality lag, authorization-denial count, moderation-policy failure count, privacy incident count, authorization-boundary failure count, and reorg-consistency failure count. Zero values are explicit; missing data are not interpreted as zero. A validated policy must bind the same release/environment, static operator team alias, 1–168 hour retention setting, max window age, min request sample, and defined SLO limits. Malformed policies/windows, impossible counts, future/stale windows and insufficient traffic fail closed. Privacy/auth-boundary/moderation/reorg failures generate critical fixed-code alerts, and latency/error/lag breaches produce warning fixed-code alerts. Normal authorization-denial volume is measured but is NOT intrinsically a security breach: separately authenticated security policy must define abuse analysis without recording viewer identifiers. No user IDs, wallet addresses, IPs, session tokens, route paths, conversation or post content, arbitrary metadata, resource IDs or free-form labels are accepted in the evaluator input or output.

`bong-goggles/web/test/operational-observability.test.js` covers normal behavior, forbidden identifiers, malformed windows and policies, stale metrics, privacy/moderation/auth/reorg incidents, SLO breaches and insufficient samples. A passing CI test demonstrates only these deterministic behaviors, not a functioning monitor or incident response.

## Mandatory live integrations before BG-20.2 closeout

1. A qualified **server-side collector** must enforce this allowlist at ingestion, prevent untrusted clients from submitting authoritative counts, aggregate events before export, prevent high-cardinality labels, restrict access, and implement retention/deletion in storage; `retentionHours` is a declaration and is not itself a deletion mechanism.
2. Provide independently authenticated source adapters for edge/API latency and errors, canonical index/finality lag, verified policy and auth-boundary failures, moderation incidents and reorg consistency. Distinguish routine authorization denials from boundary failures. Bind all windows to the measured release artifact and environment, with trusted timestamps and minimum sample checks. Source provenance and metric completeness must be reviewed.
3. Connect fixed-code alerts to an authorized, tested on-call pager with environment-specific owners, escalation paths, de-duplication, silence expiry, privacy-safe alert payloads and tested acknowledgement. This evaluator sends no alerts and cannot act on deployment controls.
4. Exercise staging fault injections for each alert type, missing/stale metrics, collector outage and late policy revocation. Record observed alert delivery latency, on-call receipt, recovery and retained artifact references. Never inject real private content.
5. Verify retention/deletion, least-privilege access, evidence authenticity and monitor behavior during rollback and outages. Require operator review before any canary decision; BG-20.1 remains fail-closed and cannot automatically promote traffic.
