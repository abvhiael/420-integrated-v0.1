# BG-20.4 — controlled staging/canary evidence gate

**Status:** preparatory code only. Not a staged deployment, completed canary, live collector, authenticated approval, traffic promotion or launch. BG-19 release closeout is outstanding. The intended eventual Cloudflare web origin is `https://bonggoggles.420integrated.org`; its existence, DNS, routing and deployment are not established by this document.

`bong-goggles/web/core/controlled-canary.js` is a pure operator-side evaluator. It rejects production inputs, missing BG-19 release approval, absent BG-20.3 recovery qualification, mismatched release/commit/artifact/config/policy versions, malformed collector windows, extra telemetry fields, time overlaps, self-attestation, insufficient samples, and missing observation evidence. It invokes BG-20.2 aggregate observability and BG-20.1 canary threshold logic; safety/SLO breaches return `rollback_required`. All outcomes set `trafficChangeAllowed: false`, `launchApproved: false`, `operatorActionRequired: true`. A clean recorded staging window returns `hold_for_operator`, **never approval**. This module does not write Cloudflare configuration or change any routing, traffic, ingress, feature flags or credentials.

## Requirements before a real staging trial

1. Close BG-19.19: authenticated Wallet/Identity session and revocation, canonical feed/projection and moderation/audience authorization, private-content delivery, secure ingress and denial/policy-withdrawal/reorg browser tests. Obtain independent BG-19 approval for the exact release and environment.
2. Deploy a pinned immutable build to a separately access-controlled staging origin, keeping private ingress and unqualified features disabled. Capture Git commit, artifact digest, configuration digest, policy digest, Cloudflare deployment ID, origin, operator and rollback target.
3. Connect an authenticated trusted server-side metrics collector. Reject personal data at collection, enforce retention, independently verify evidence source and signatures, document collector clock integrity, and make fixed-code paging reach an on-call owner. Evidence URLs and the `collectorId` string are untrusted claims unless separately verified. Capture sequential non-overlapping measurements for the *same* staged deployment and policy.
4. Actually conduct and independently review the BG-20.3 backup/rollback drills. Test policy outage, access revocation, chain reorg, database restore and media outage; confirm private routes remain disabled and account-level visibility is checked after restoration.
5. In a separately authorized operator runbook, evaluate all observations, stop the staged trial on blocked or rollback-required outcomes, and verify rollback by deployed release ID. A clean evaluation still needs independent human approval and a **separate** production release process, new evidence and environment-specific testing. Never reuse a staging decision as production authorization.

Regression tests cover clean hold, denied signoff, production inputs, release/digest mismatches, unknown personal-data fields, overlapping windows, self-attestation, boundary breach and missing drill/sample. Passing GitHub CI proves only deterministic evaluator behavior; it is not proof of any physical rollback, Cloudflare deployment, real monitoring, security review or successful canary.
