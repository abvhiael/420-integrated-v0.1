# 420 Developer Hub — DEVHUB-19 Production Launch Readiness

## Status

DEVHUB-19 begins the production-launch phase by introducing a developer-facing readiness gate that **consumes existing evidence** rather than creating a new source of truth.

The Developer Hub does not decide that the chain, contracts, wallets, services, or public testnet are production-ready merely because tooling exists. DEVHUB-19 requires explicit evidence from DEVHUB-18 and the repository's release-readiness pipeline.

## Required inputs

The initial launch gate consumes three independent inputs:

1. a DEVHUB-18 security/developer qualification report;
2. the DEVHUB-18 exact-head CI handoff for the same release candidate;
3. `release/readiness.json`, generated by the existing repository release-readiness process.

DEVHUB-19 does not replace `scripts/readiness.py`, formal release evidence, production dependency qualification, real-node tests, live Engine smoke, production partition/restart testing, or production soak evidence.

## Results

The bounded launch states are:

- `READY` — DEVHUB-18 qualification is PASS, exact-head CI evidence is ready, and the underlying release-readiness evidence is explicitly ready with no blocked or failed checks;
- `BLOCKED` — no required gate explicitly failed, but one or more required inputs are incomplete, blocked, stale, or not explicitly ready;
- `FAIL` — an explicit required gate failed.

`readyForProductionLaunch` is true only for `READY`.

## Existing release boundary

The current repository `release/readiness.json` remains authoritative for the repository release-readiness process. At the start of DEVHUB-19 it still reports `public_testnet_ready: false` with production gates blocked where explicit evidence is absent.

DEVHUB-19 must preserve that state. It cannot infer readiness from source files, successful local tests, the existence of production adapters, or Developer Hub qualification alone.

## CLI

`420-launch view` displays the production-readiness contract and required evidence inputs.

`420-launch check QUALIFICATION_JSON HANDOFF_JSON [RELEASE_READINESS_JSON]` evaluates the selected candidate. A valid non-READY report exits with code `3`; malformed evidence/runtime failures exit with code `1`.

The command never signs, deploys, publishes, grants capabilities, changes Registry state, or mutates release evidence.

## Security invariants

DEVHUB-INV-174 — DEVHUB-19 launch readiness declares `canonicalAuthority: false`.

DEVHUB-INV-175 — DEVHUB-19 launch readiness declares `securityCertification: false`.

DEVHUB-INV-176 — DEVHUB-18 qualification must explicitly PASS before a production candidate can be READY.

DEVHUB-INV-177 — DEVHUB-18 exact-head CI handoff must explicitly report release evidence ready before a production candidate can be READY.

DEVHUB-INV-178 — `release/readiness.json` remains an independent required input; Developer Hub tooling cannot override its blocked or failed state.

DEVHUB-INV-179 — Any explicit failed launch input yields overall `FAIL`.

DEVHUB-INV-180 — Missing, blocked, or incomplete required launch evidence yields `BLOCKED`, never implicit READY.

DEVHUB-INV-181 — `readyForProductionLaunch` is true only for overall `READY`.

DEVHUB-INV-182 — The existence of tooling, source adapters, manifests, workflows, or configuration files is never sufficient production-readiness evidence.

DEVHUB-INV-183 — Launch readiness cannot confer protocol authority, Registry legitimacy, Wallet capability, governance approval, audit status, finality, settlement, or public-testnet activation.

## Foundation exit gate

The DEVHUB-19 foundation slice is complete when the readiness runtime, hostile-state tests, `420-launch` CLI, and documentation qualify in CI.

## Next DEVHUB-19 slice

After the foundation qualifies, DEVHUB-19 will add redacted dashboard launch-readiness views and candidate/provenance binding suitable for final release-candidate closeout without introducing deployment or governance authority.
