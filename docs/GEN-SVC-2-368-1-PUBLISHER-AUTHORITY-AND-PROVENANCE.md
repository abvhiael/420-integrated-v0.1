## Authority matrix (do not collapse these roles)

| Actor | Allowed responsibility | Not permitted merely by its role |
| --- | --- | --- |
| External provider | Supply licensed source records, identifiers, corrections and removal notices under recorded terms. | Directly approve GEN-SVC-2 publication; assert business control, organizer identity or Registry/Verify attestation. |
| Direct submitter/organizer | Submit proposed event content and updates through an authenticated, separately qualified channel. | Write canonical snapshots or promote a generation. A submission is not approval. |
| Restricted 420 Integrated importer | Verify configured source identity, import entitlement, schema, source manifest, hashes and dedupe; produce candidate changes; preserve source provenance. | Set public status or bypass canonical Location/Events validation or service authorization. |
| Authorized publication operator | Review candidates, document approval/rejection/reason and scope; authorize precise mutations and withdrawal; sign or otherwise attest to an immutable generation. | Impersonate an organizer, silently invent ownership/verification status, ignore source withdrawal obligations. |
| Canonical Location/Events services | Enforce record validation, versioning, authorized lifecycle transitions and privacy. Add missing authorization-checked Location and recurrence-exception commands before publisher can use them. | Treat raw repository methods as authorization decisions. |
| Publisher process | Revalidate operator approvals and source policy, build compatible public-only place/event projection, bind a paired generation to approval and provenance evidence, then atomically promote it. | Expose an unauthenticated public write endpoint; alter canonical owner or organizer identities to make imports pass validation. |
| GEN-SVC-2 public service/Travel | Verify deployment-trusted publication evidence and consume the same pinned public generation; serve read-only public projections. | Publish, import, approve, or infer trust solely from `SVC2_PUBLICATION_SOURCE` or HTTP 200. |

There is **no designated real operator identity, trusted public key, source dataset licence, publisher credential, deployed writer, or Railway storage configuration approved by this document**. Until separately configured and verified, publication-verification state `V` is false/unknown, not true.

## Canonical ID and alias contract

- Preserve `Place.ID` and `Event.ID` as stable internal canonical identifiers. Never derive authorization or business ownership from external provider IDs. External place references belong in existing `Place.ProviderAliases` (`provider`, `id`) with collision checks; define an equivalent scoped event-alias mapping in the importer provenance ledger without changing the public Events v1 envelope.
- Normalize provider namespace plus its opaque source ID without dropping leading zeros or conflating providers; a cross-source duplicate is a review candidate, not an automatic overwrite. Use `FindByProviderAlias` only for exact source association. Preserve original provider IDs and source version separately for audit.
- A re-import of the same approved source revision must be idempotent. A change to source identity or source ID cannot hijack an existing canonical record. Place `Owner`, event `Organizer`, `CreatedAt` and canonical ID remain governed by their existing immutability and authorizer constraints.
- A duplicate suggestion must record both candidate IDs, evidence and a reviewer decision. Never delete/merge an existing record or reassign an alias solely on geographic proximity or identical names.

## Provenance and approval ledger (private, immutable revisions)

A candidate record must carry: canonical candidate ID, kind (`place`/`event`), source namespace and exact external record ID (or organizer submission ID), retrieval/submission timestamp, source revision and content digest, source manifest/terms and attribution references, permitted uses, geographic scope, original payload checksum, normalized payload checksum, import adapter version, and explicit source removal/correction indicators. Keep source payload/credentials and private coordinates outside public responses. Record source identity verification separately from a human-readable source label.

An approval record must bind: candidate digest, canonical target ID, action (`create`/`edit`/`publish`/`unpublish`/`cancel`/`withdraw`/`reject`), authorized operator identity and role, approval timestamp, policy version, intended public visibility/precision, reason, applicable source obligations, and expected prior canonical version. Rejection and withdrawal must remain represented in the audit ledger, not erased by a re-import. Approvals expire on material candidate edits, source licence revocation, or conflicting canonical version. An operator override must record its reason and must not override immutable owner/organizer or private-data constraints.

Use an append-only audit record or equivalent tamper-evident mechanism and restrict write/read permissions. Define deterministic serialization and cryptographic digest binding before a publication verifier is implemented. `SourceID` is descriptive metadata only; explicit trusted signer/key or independently authenticated publishing identity must be configured outside the source payload. Trust anchors and key rotation/revocation must not be imported from the untrusted manifest being verified.

## Publication decision and withdrawal policy

1. Default candidate state is `imported`/`pending_review`, **not public**. A rejected candidate cannot be published by merely running the import again. Distinguish source deletion from import omission due to temporary outage or extraction changes; do not withdraw records based solely on a partial failed batch.
2. A public place requires a distinct approval specifying visibility and public coordinate precision. Imported listing != verified owner or Registry/Verify attestation. Unlisted/private places and private-precision coordinates remain outside the public projection.
3. Event creation and whole-event transitions must pass existing organizer authorization and lifecycle constraints. For third-party imports without a verified organizer, introduce an explicit import-operator authority and policy that does **not** impersonate the organizer; do not call the current service with a fabricated `Organizer` authorization. An occurrence-specific cancellation needs an authorized canonical command and revision before it can be published.
4. A source removal request, local privacy withdrawal, mandatory correction or event cancellation must be entered as an auditable canonical action and applied through the active public generation. Keep a revocation floor/watermark so rollback cannot reintroduce a withdrawn record or occurrence.
5. Publication itself is a separate authorization step: bind all approved record revisions and source manifests to one immutable paired Location+Events generation. Failed approval, unsigned/untrusted provenance, missing source licence, partial datasets or a failed revocation check prevent promotion; preserve the last *still authorized and fresh* generation only under the documented release policy.

## Planned implementation boundaries and tests

- `genesis/svc2/publisher/` (proposed): source/candidate and approval interfaces, typed authority verifier, append-only audit access, deterministic generation preparation and gated promotion. Keep authorizer/clock/trust anchors injected and fail closed on nil or invalid dependencies. Do not write to the public HTTP API from this package.
- `location/service/` and `events/service/`: add only necessary authorization-checked canonical commands, preserving current model validators and lifecycle invariants; do not expose bare repository writes to untrusted importers. Define separation between source permission, organizer/place control, and publication approval.
- `genesis/svc2/deployment/`: later verify immutable publication evidence and active generation before setting `V=true`; keep `/readyz` unqualified until this exists. Phase 368.5 owns atomic cross-store generations and 368.7 owns health implementation.
- Deterministic tests must demonstrate: unapproved import not public; revoked source/approval rejected; unknown signer/source label alone rejected; changed candidate invalidates approval; alias collision and duplicate cannot steal canonical ownership; unverified organizer cannot authorize Events service; stale canonical expected version fails; cancelled occurrence and withdrawn place cannot reappear after re-import or rollback; records from two generation IDs never mix.
