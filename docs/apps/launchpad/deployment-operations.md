# 420 Launchpad deployment and Registry publication

`LAUNCHPAD-AUDIT-4` freezes the repository-side release materialization for the Launchpad protocol and its crowdfunding integration. It does not claim a live public-testnet deployment.

## Address policy

- `LaunchpadRouter420` remains `REGISTRY_RESOLVED_NO_FIXED_GENESIS_ADDRESS`.
- No new Genesis predeploy is introduced.
- No CREATE2 policy is invented.
- Historical candidate `0x000000000000000000000000000000000000045c` is superseded and must not be used as an active address.
- Canonical discovery is through `ProtocolRegistry` at the frozen Registry authority once a governed live deployment exists.

## Repository deployment sequence

1. deploy `LaunchpadAuthorization420(CapabilityRegistry420)`;
2. deploy `LaunchpadProjectRegistry420(GovernanceTimelock)`;
3. deploy `LaunchpadSaleRegistry420(GovernanceTimelock, LaunchpadProjectRegistry420)`;
4. deploy `LaunchpadAllocationRegistry420(LaunchpadAuthorization420, LaunchpadSaleRegistry420)`;
5. execute one-time `LaunchpadSaleRegistry420.setController(LaunchpadAllocationRegistry420)`;
6. deploy `LaunchpadCrowdfundingIntegration420(LaunchpadAllocationRegistry420, PaymentRegistry420, Identity420, ArbitrationCaseRegistry420, ArbitrationRulingRegistry420)`;
7. execute one-time `LaunchpadAllocationRegistry420.setCrowdfundingIntegration(LaunchpadCrowdfundingIntegration420)`;
8. deploy `LaunchpadRouter420(LaunchpadSaleRegistry420, LaunchpadAllocationRegistry420)`;
9. register the canonical `420/COMPONENT/LAUNCHPAD/V1` component to the exact router in ProtocolRegistry;
10. publish `420/service/launchpad/v1` with `publishRegisteredService`.

## Identity and verification

The exact build uses Solidity 0.8.24, Cancun EVM, optimizer 200 runs and via-IR. Qualification retains compiled artifact SHA-256, canonical ABI SHA-256, runtime-template SHA-256, local deployed EXTCODEHASH values, the Registry dependency root, manifest commitment and interface commitment.

The local deployment test proves the exact constructor graph, both one-shot post-initialization bindings, router smoke reads, ProtocolRegistry active service/component resolution and wrong-router visibility.

## Live boundary

Local Foundry addresses and runtime identities are repository qualification evidence only. Public-testnet chain identity, deployed addresses, deployment transactions, Registry publication transactions, live code hashes and constructor-binding receipts are owned by `LAUNCHPAD-AUDIT-6` and remain unset until that live step.

## Creator review queue and reporting (REC-3)

Configure `LAUNCHPAD_CREATOR_REQUEST_FILE` as an application-writable, persistent, restricted-permission JSONL ledger before accepting signed governance-review requests. Without it submissions fail closed. The service checks personal/EIP-1271 signatures against the canonical chain, reconstructs project/sale calldata and stores review receipts; no backend signing or automatic governance execution occurs. Optionally set `LAUNCHPAD_CREATOR_REPORT_FROM_BLOCK` to an exact deployment start block for bounded historical event scans; otherwise event totals are intentionally unavailable. Back up the review ledger and monitor its capacity; on-chain project status remains authoritative. See [Creator guide](creator-guide.md).

## Wallet, API and indexer hardening (REC-4)

The browser disables direct submissions without the connected account and chain ID, a reviewed exact selector, argument and target match, zero native value and current Registry-derived contract identities. Reviews expire after two minutes and are invalidated on changed input, account or network; just before Wallet approval the client requests a fresh exact transaction review, Registry graph and canonical sale position. Contract identity cannot be overridden by a service response that differs from an explicitly configured canonical runtime.

The service must use `LAUNCHPAD_RPC_URL` (HTTPS, or localhost HTTP for local development), `LAUNCHPAD_CHAIN_ID` and an absolute `LAUNCHPAD_PROJECTION_FILE`. Set `LAUNCHPAD_CORS_ORIGIN` to the exact HTTPS origin of the browser frontend even when it shares a hostname with the API; ordinary browser POSTs carry an `Origin` header. If unset, the API accepts only requests without an `Origin` header, such as trusted server-side local checks. The server enforces bounded JSON bodies, rate and concurrency limits, short RPC timeouts and rejects malformed JSON-RPC envelopes. No backend key custody, transaction signing or remote wallet broadcast exists.

**Indexer reconstruction (local, testnet not required):** Set `LAUNCHPAD_INDEX_FROM_BLOCK` to the exact deployment block (hex quantity) and run `npm --prefix launchpad/service run rebuild` in the repository checkout. The command scans bounded canonical `SaleCreated` events from the Registry-attested sale contract, checks each log's block-hash inclusion and sale/project/mode binding, and atomically replaces the projection file. It does not trust previously indexed entries: a reorg or restart reconstructs from chain history, dropping orphaned sales. The indexed snapshot includes chain ID, block height/hash, Registry-derived contract IDs and a maximum freshness window of 64 blocks; stale, malformed, orphaned or mismatched snapshots return an error rather than a campaign catalogue. Rebuild again from the deployment block following a reorg, missing/corrupt snapshot or prolonged downtime.

This local-only discovery index intentionally uses neutral on-chain-derived titles and generic summaries. Any editorial metadata must be validated independently before presentation; never substitute off-chain titles for canonical sale identities or outcomes. RPCs must provide `eth_getLogs`, canonical `eth_getBlockByNumber` results, contract reads, `eth_getCode` and `web3_sha3`. A bounded historical scan older than the configured maximum range must be split/rebuilt under an explicitly reviewed operational policy, not bypassed silently.

## Cross-system event consumers and local acceptance (REC-5)

Qualified local evidence: [LAUNCHPAD-REC-5](../../audit/LAUNCHPAD-REC-5-QUALIFICATION.md).
The production-style 420Indexer factory is `createLaunchpadIndexer420` in `420-indexer/src/launchpad-indexer.ts`. It requires a pre-approved `ChainSource420`, matching chain ID and genesis hash, trusted ProtocolRegistry deployment address, the retained real ABI artifacts for `LaunchpadProjectRegistry420`, `LaunchpadSaleRegistry420`, `LaunchpadAllocationRegistry420` and `LaunchpadCrowdfundingIntegration420`, and the existing durable SQL/indexer ingest options. Do not invent a Router predeploy: the factory derives and code-hash verifies every emitter from the active Registry service graph, checks canonical receipts and uses existing checkpoint/reorg recovery.

Launchpad events in the shared indexer are scoped to protocol `420Launchpad`. `NotificationPublished` and `ReputationEvidencePublished` are evidence for non-custodial downstream presentation/verification, **not** authorization to pay, grant rewards, execute rulings or mutate the campaign. Notifications must retain indexed chain/block/tx/log provenance with retraction and replay handling. Reputation must independently verify finality, profile/subject and the `CROWDFUNDING` domain. Explorer uses the same raw canonical logs for inspect-only links; its reported head or finality is not a substitute for the canonical Launchpad position and Pay settlement.

The Wallet service catalogue already contains `420/service/launchpad/v1` and restricts service discovery to active, codehash-matched ProtocolRegistry publications. Wallet navigation grants no implicit connection or spending permission. The Launchpad browser links a submitted transaction to 420Explorer only when `network.explorerUrl` is a configured exact HTTPS root and its chain ID matches the selected Wallet; otherwise no link is displayed.

For local acceptance, `.github/workflows/launchpad-rec-5-ecosystem.yml` deploys real Registry, Identity, Pay/Swap, Arbitration and Launchpad contracts with controlled shared Genesis mocks, tests an **exact** converted invoice settlement, claim, dispute and participant revocation, and runs the actual Wallet/service, 420Indexer, Reputation/Notifications and Explorer consumers. This is pre-testnet qualification only. Do not publish runtime addresses or activate these services from fixture values. Runtime deploy/reorg and end-to-end external delivery receipts remain testnet-gated under LAUNCHPAD-AUDIT-6.


## REC-6 — operator preflight, deterministic release and publication runbook

This is a **repository/local-EVM procedure**, not authority to execute a live deployment. The approved public-testnet release and its external transaction receipts belong exclusively to LAUNCHPAD-AUDIT-6. Use the exact deployment sequence above; do not deploy the superseded `0x045c` candidate, invent a CREATE2 salt, or replace Genesis protocol addresses.

1. **Freeze an exact candidate.** Record `git rev-parse HEAD`, the canonical branch, Foundry profile, six source paths, any currently active Registry service version and implementation, and the governance release approver. Do not use a mutable branch name as release identity. Confirm `contracts/config/launchpad/launchpad-audit-4-release-materialization.json` and `testnet/public-services/launchpad/readiness.json` agree on repository-only readiness.
2. **Reproduce compiled evidence in an isolated checkout:** run `python3 scripts/verify-launchpad-audit-4-release.py`, then `(cd contracts && FOUNDRY_PROFILE=pr forge build src/launchpad src/apps/ProtocolRegistry.sol src/system/CapabilityRegistry420.sol)`; run `python3 scripts/verify-launchpad-rec-6.py artifacts --sha "$(git rev-parse HEAD)" --output launchpad-rec6-artifacts.json`. A second clean build must emit byte-for-byte identical attestation JSON, as required by `.github/workflows/launchpad-rec-6-closeout.yml`. The artifact records canonical SHA-256 digests of compiled ABI, creation bytecode and **runtime template**; these are *not* deployed code hashes.
3. **Validate constructor authority before any transaction.** Check the six ABI constructor input sequences against the Audit-4 deployment-order manifest: Authorization(CapabilityRegistry); ProjectRegistry(GovernanceTimelock); SaleRegistry(GovernanceTimelock, Projects); AllocationRegistry(Authorization, Sales); CrowdfundingIntegration(Allocations, Pay PaymentRegistry, Identity, Arbitration cases, Arbitration rulings); Router(Sales, Allocations). The existing `LaunchpadDeploymentBinding420.t.sol` locally deploys the actual graph, verifies every immutable read, proves the two one-shot bindings and Router/ProtocolRegistry resolution, and rejects wrong-router substitution.
4. **Understand local Registry fixture commitments.** The Audit-4 Foundry test uses fixed domain-marker Keccak values for metadata, manifest and interface, not the hashes of approved release-document bytes. At a future live publication, the governing release must independently approve the canonical metadata document, machine-readable manifest, Router ABI/interface descriptor and dependency root; compute and retain their real commitments and the registry transaction receipts. Never publish the local marker constants as if they were live approval evidence.
5. **Prove runtime code on the actual candidate chain** *only once LAUNCHPAD-AUDIT-6 begins*: verify chain ID and genesis identity from two independently configured canonical sources, compare transaction deployment bytecode/constructor arguments and each `eth_getCode` runtime `EXTCODEHASH` against the recorded compiler/runtime and immutable materialization, and verify the one-shot controller/integration, Registry component, service version and status from live reads. Persist block hash/height and all deployment/publication receipt hashes. Abort on different hashes, stale RPC, unexpected implementation, missing contract code, or changed approved inputs.
6. **Build the standalone site without inventing a deployment:** from `launchpad/web`, run `npm run check && npm test && GITHUB_SHA="<exact Git SHA>" npm run build`, then at the repository root run `python3 scripts/verify-launchpad-rec-6.py web --sha "<exact Git SHA>"`. Deploy only the checked `dist/` static artifact. The shipped `runtime-config.json` intentionally has no chain ID, Router address, API URL or RPC endpoint and starts **execution disabled**. A future runtime configuration must be independently chain/Registry verified before enabling payments; no wallet key, merchant secret or API token belongs in the static bundle.
7. **Configure service only with verified runtime inputs.** Supply `LAUNCHPAD_RPC_URL` (approved HTTPS RPC, localhost HTTP only in local development), `LAUNCHPAD_CHAIN_ID`, a persistent absolute `LAUNCHPAD_PROJECTION_FILE`, and exact `LAUNCHPAD_CORS_ORIGIN`. Supply `LAUNCHPAD_INDEX_FROM_BLOCK` only for the deterministic rebuild command, using the approved SaleCreated deployment starting block (hex quantity). The optional `LAUNCHPAD_CREATOR_REQUEST_FILE` is a restricted-permission, persistent JSONL governance-review intake ledger, not an executable governance queue. Limit access and back it up; never copy that ledger into the public static site.
8. **Preflight before opening access.** From clean checkout qualify local deployment/Registry tests, 420Pay exact settlement/Identity revocation/Arbitration evidence, all `launchpad/web` and `launchpad/service` tests, Registry-attested 420Indexer, and the production build. Verify canonical API readiness, empty/unavailable-state presentation, wrong-chain and stale-Registry rejection, 420Pay settled invoice and distinct contribution record, claim/refund gating, and Wallet-only explicit reviewed submission. Disable interactions on any conflicting or incomplete result.

### Recovery and incident-response decision tree

**On any wrong chain, unknown Router, expired review, missing/ambiguous payment, malformed response, Registry rotation or stale local index:** stop new reviews/contributions and leave the client fail-closed. Do not substitute a manifest address, fabricate a funded transaction, or retry a payment from a notification or Explorer link. Capture UTC event time, exact commit/artifact attestation, chain ID, block number/hash, published Registry version and codehash, safe non-secret RPC/error excerpt, affected campaign IDs and payment/tx IDs. Never record keys, bearer tokens, sessions, private profile payloads or signed approvals in public logs.

**On projection corruption, stale block (over the configured 64-block bound), restart, or bounded reorg:** preserve a restricted copy of the current projection file and its checksum for forensics; stop the service if the canonical head/Registry identity is uncertain. Verify the configured `LAUNCHPAD_RPC_URL`, `LAUNCHPAD_CHAIN_ID` and exact `LAUNCHPAD_INDEX_FROM_BLOCK` against a trusted canonical chain source. Run `npm --prefix launchpad/service run rebuild` from the repository root, with `LAUNCHPAD_PROJECTION_FILE` pointing to the approved persistent location. Rebuild must atomically replace the projection with only canonical sale creation evidence and validated Registry graph; reject orphaned, wrong-chain, expired or corrupt results. Do not edit snapshot rows by hand or extend a stale-bound limit merely to make a page load. If the RPC cannot supply the approved range or stable block-hash evidence, keep discovery unavailable and escalate to chain/indexer operators. Separate Wallet contribution/claim/refund positions remain canonical contract reads.

**On creator-intake restart or ledger uncertainty:** preserve the restricted JSONL ledger and its backups, identify already acknowledged signed request IDs, and restore only from a verified integrity-checked copy. Governance requests are *intake records*, never authority to execute a project/sale transition; do not automatically replay, resubmit or execute governance calls while recovering. Missing or unwritable intake persistence must disable new submissions without affecting on-chain reads.

**On Pay settlement ambiguity, refund partiality, disputed claims or reorged transactions:** confirm an actual canonical receipt, finalized state if applicable, exact participant/merchant/settlement asset/amount, invoice/payment ID and campaign allocation; never infer settlement from quote preparation, Wallet submission, `NotificationPublished`, a Reputation event, or a derived Explorer view. Payment finality/partial refund belongs to Pay; disputes/rulings belong to Arbitration; Launchpad emits evidence but cannot move funds or execute remedies. Check already-recorded contribution/refund/delivery commitments for replay before any authorized retry.

**On release/runtime regression:** remove public application routing or disable transaction submission while investigating. Where a previous Registry implementation exists, do *not* silently rewrite it; any lifecycle deactivation/version restoration must follow the already-authorized governance/timelock controls and be verified by a new on-chain receipt and codehash. Immutable constructor bindings cannot be repaired in place: a replacement deployment, governed new Registry publication and independent chain-dependent validation are required. Keep old receipts/manifests and both version histories for forensic reconstruction. Do not assume that redeploying Cloudflare assets or restoring a projection file reverses an on-chain transfer.

**Monitoring and return-to-service:** alert on failed Registry resolution/codehash, wrong-chain RPC responses, bounded freshness/reorg errors, queue write failures, API CORS/rate-limit alarms, permission/capability failures, stale quotes and unresolved pending/reorged transactions. On a candidate live release, retain service health, safe/finalized heights where authoritative, runtime version, ABI/release fingerprint and independently confirmed 420Pay/Identity/Arbitration dependencies. After remediation, rerun only the affected targeted tests plus verified chain/Registry/payment state and exercise a safe read-only Wallet/Explorer page; resume reviewed transaction submission only after explicit release approval. Public-testnet end-to-end monitoring, real external delivery receipts and production rollback authority are **deferred to LAUNCHPAD-AUDIT-6 and the existing later release gates**, not claimed by REC-6.
