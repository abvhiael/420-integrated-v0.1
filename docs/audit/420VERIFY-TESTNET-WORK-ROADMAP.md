## Deferred work — execute once testnet infrastructure is available

- [ ] **Release and deployed identity:** reconcile 420Verify with the exact merged release SHA (including PR #1377 if accepted); build reproducible deployment artifacts, record image/binary digest, environment/config version, and deployed instance identity. Capture actual service origin rather than relying on historical CI runs.
- [ ] **Testnet chain prerequisites:** use approved canonical testnet RPC with the frozen chain ID and a genuinely deployed known contract for `VERIFY_READINESS_ADDRESS`. Verify canonical runtime bytecode and chain identity; wrong-chain, unavailable RPC, stale code and missing contract fail closed. Do not assume the sample `0x...0420` is deployed.
- [ ] **Trusted compiler provisioning:** provision allowlisted exact Solidity compiler versions and trusted binary SHA-256 entries in `VERIFY_COMPILER_CATALOG` and `VERIFY_COMPILER_CACHE`; verify provenance, checksum, isolation, timeout/resource caps, and explicit rejection of tampered/unallowlisted compilers.
- [ ] **Service/frontend deployment:** deploy the Go API and embedded same-origin UI, assign real backend/frontend HTTPS URL(s), validate TLS and security headers/CSP, and establish the intended proxy/ingress routing for `/healthz`, `/readyz`, `/v1/verify/*` and `/`. Preserve source-publication consent and secrets rejection. Do not publish placeholder domains as deployed.
- [ ] **Live API and UI workflows:** test address/network lookup, Solidity Standard JSON/multi-file source submission, compiler settings, explicit `publishSource: true`, exact runtime/creation matching and all FULL_MATCH/PARTIAL_MATCH/MISMATCH/UNVERIFIABLE diagnostics, source/history/evidence lookup, verification-is-not-audit wording, and Explorer navigation with genuine canonical witnesses.
- [ ] **Durable evidence and disaster recovery:** mount durable evidence storage; record independent evidence reproducibility, immutable backups, restart/rebuild, tamper/corruption rejection, disk failure behavior and safe restoration. Preserve chain/address/runtime-code-hash bindings and append-only history across canonical reorgs.
- [ ] **Proxy upgrades/currentness:** exercise real EIP-1167/EIP-1967 proxy/implementation observation and upgrade paths on testnet. A persisted relationship is historical/block-scoped; independently revalidate current canonical proxy state before showing it as current. Decide whether deployment needs continuous proxy monitoring or request-time revalidation; implement/qualify whichever actual consumer behavior is required, without transferring previous implementation verification.
- [ ] **Ecosystem consumer interoperability:** exercise 420Explorer, 420AppStore, Developer Hub and any actual Registry, SDK or indexer consumers against published reproducibility evidence. Verify source provenance and correct exact-chain/address/code-hash pinning; never grant Registry legitimacy, wallet permissions, governance authority, audit/safety status or implicit endorsement based on verification.
- [ ] **Monitoring and hostile/failure drills:** alert on RPC/chain mismatch, stale health/readiness, HTTP errors/429s, compiler failures, storage errors, disk pressure and restarts. Exercise network partitions, instance restart, recovery, tampered evidence, source-submission abuse, wrong-chain and compiler-checksum failures. Ensure Verify outage never blocks canonical chain, Registry or Wallet functionality.
- [ ] **Live acceptance evidence:** run public HTTPS/TLS/health/ready smoke against the exact deployed SHA, reproduce at least one known contract from source and compiler settings, independently compare deployed code/creation evidence, run restart and wrong-chain/checksum/reorg/proxy tests, archive sanitized run logs, receipts, provenance, timestamps and checksums. Re-run impacted repository CI if code/config changes; do not replace genuine live evidence with mocks.
- [ ] **Activation and readiness reconciliation:** replace `REPLACE` URLs with verified real URL(s) only after deployment; update `testnet/public-services/verify/readiness.json` with the actual chain, deployed artifact/SHA, live check results and statuses. Mark public endpoint deployment claimed only after all required checks pass.

## Exit criteria

420Verify testnet work is complete only when the qualified merged build is running at a verified HTTPS endpoint; `/healthz` and `/readyz` pass against the intended chain; an independently reproducible submission proves the full canonical evidence path; source consent, history, proxy freshness, failures and restart recovery have been exercised live; downstream integration preserves verification/authorization boundaries; and the readiness manifest references genuine deployment evidence. Otherwise keep **PUBLIC_TESTNET_DEPLOYMENT_PENDING**. Do not treat the historic eight-step code audit as a live deployment claim.
