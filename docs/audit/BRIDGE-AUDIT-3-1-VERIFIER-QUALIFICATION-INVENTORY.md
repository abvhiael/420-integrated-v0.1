# BRIDGE-AUDIT-3.1 — Production verifier inventory and trust boundaries

**Scope:** inventory and qualification classification only (BRIDGE-AUDIT-3.1). **Baseline:** `main` at `4b6ad48b6c231845f80aa48a5d8df80ca9ee447f` (merged BRIDGE-AUDIT-2). **Date:** 2026-11-13.

## Interpretation and status policy

* **INTERFACE PRESENT:** Solidity verifier-return schema exists; this is *not* evidence of consensus verification.
* **ORCHESTRATOR ONLY:** implementation composes external proof services, but does not itself validate the underlying consensus and message inclusion.
* **EXTERNAL IMPLEMENTATION NOT ESTABLISHED:** no independently qualified production implementation identified in the audited bridge source tree. This does **not** assert that no vendor implementation exists outside this repository.
* **UNQUALIFIED — DO NOT ACTIVATE:** no source-finality/inclusion, deployed-code, trust model or runtime qualification evidence establishes safety on this baseline. A verifier contract returning `finalized=true` (or analogous flags) is not sufficient.
* **FAIL-CLOSED STUB:** both inbound verification and outbound initiation unconditionally revert; not a production verifier.

The 12 named interfaces below are all under `contracts/src/interfaces/I<Family>FinalityVerifier420.sol`, and the matching 12 adapters are under `contracts/src/bridge/adapters/<Family>BridgeAdapter420.sol`. Each interface exposes `verifyFinalizedTransfer(bytes)`; each adapter delegates to a governance-set verifier, performs some local structural/network/allowlist/replay checks and constructs a `VerifiedTransfer`. All twelve are **UNQUALIFIED — DO NOT ACTIVATE** for real-value inbound traffic pending actual external-proof qualification; local adapter validations do not authenticate the source evidence.

## Source-code trust boundary assessment

1. **Proof-provider authority:** all 12 production-shaped adapters trust a configured verifier's returned `FinalizedTransfer`. Adapters check that returned fields are internally plausible, but do not independently validate raw signatures, consensus, chain-work, quorum or Merkle branches. A malicious or accidentally deployed mock verifier can return structurally valid, false evidence. Tests using programmable verifier mocks are unit tests, **not** production finality evidence.
2. **Registration:** the adapter `setVerifier` path is `onlyGovernance`, with nonzero-address and code-length checks. These prove contract presence, **not** correctness, identity, production acceptance or revocation across all route pathways. A privileged misconfiguration can point at an arbitrary contract. Verifier contract identity, code hash, qualified configuration and rotation are not enforced by the shared router on this baseline.
3. **Admission:** `GatewayRouter420.setAdapter` verifies `adapterId()` and code existence, while `BridgeRouteRegistry.setRoute` checks chain identity at activation but stores only a `verifierConfigHash` without authenticating the concrete verifier or its underlying proof system. An active route is therefore not proof of verifier qualification.
4. **State transition consequence:** `GatewayRouter420.acceptInbound` calls `verifyInbound`, then creates a transfer and marks source-finalized and verified using derived hashes. The authenticity of these evidence hashes is entirely downstream of the adapter/verifier return. A false positive at that trust boundary can propagate into on-chain VERIFIED state. The shared route, risk, health and replay checks do not cure false finality.
5. **Replay:** adapters track consumed message IDs (some also source outputs, tx hashes or shielded nullifiers) and the gateway checks a shared replay registry, but return-value uniqueness does not make an untrusted proof true. Cross-route/domain canonicalization, rotations and stale/conflicting evidence require further qualification.
6. **Ethereum orchestrator:** `EthereumFinalityVerifier420` checks nonzero envelope inputs and calls external finality and receipt verifiers for the same execution block and receipts root. Both components may be governance rotated, and their independent production correctness has not been established. This is not an end-to-end proof verifier on its own.
7. **Failure domain:** no source-deployed gateway, external chain contract, verifier deployment address, runtime hash, issuer permission, light-client trusted root, oracle quorum, attestation key, or live source-event qualification is established merely by these files. Deployment/testnet validation is separate from repository-side proof framework hardening.

## Evidence and negative classification

**Inspected on baseline:** 12 `I*FinalityVerifier420.sol` files and the 12 matching `*BridgeAdapter420.sol` files; `EthereumFinalityVerifier420.sol`; `IEthereumFinalityOracle420.sol` and `IEthereumGatewayMessageVerifier420.sol` reference surface; `IBridgeAdapter420.sol`; `GatewayRouter420.sol`; `BridgeRouteRegistry.sol`; `BridgeChainRegistry420.sol`; `VerifiedGateway420.sol`; four fail-closed adapters; `contracts/config/bridge/verification-policy.json`; retained `contracts/test/VerifierRotationHardening420.t.sol`. Current main's BRIDGE-AUDIT-2 PR #1153 qualifies shared-route lifecycle checks, **not** source-finality authenticity.

**Mock evidence:** `VerifierRotationHardening420.t.sol` defines `RotationEthereumVerifierMock420` and `RotationSolanaVerifierMock420` with mutable `nextTransfer`, demonstrating rotation wiring and unauthorized access rejection, not finality validity. Other adapter tests also use programmable verifier fixtures. Keep their test value distinct from production proof verification.

**Audit decision:** **3.1 inventory COMPLETE; production verifier qualification remains NOT ESTABLISHED for all 12 families and generic gateway.** Do not label any as production-ready on this evidence. This file is descriptive inventory, not executable activation enforcement. Actual production route/verifier trust enforcement, proof-envelope domain binding, rotation and fail-closed gating are expressly the subsequent BRIDGE-AUDIT-3.2 through 3.5 tasks, not falsely claimed here. No new deployment, contract mutation, CI run or live-testnet evidence is represented by this documentation-only inventory.
