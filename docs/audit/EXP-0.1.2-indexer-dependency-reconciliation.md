**Status:** SOURCE-INVENTORY COMPLETE; runtime and deployment qualification are separate EXP milestones.  
**Audited application/Indexer baseline:** `95a83a961286701b6e8c064de1deccad10f41fd7` (not mutable `main`).

## 1. Runtime composition and authority

`explorer/cmd/explorer420/main.go` (`cbb4225d680a37d946f93e80d43fc873a47131e5`) requires `EXPLORER_INDEXER_URL` and constructs `indexerclient.New` → `explorer/service.New` → `explorer/api.NewServer`. The HTTP client in `explorer/indexerclient/client.go` (`b8acb6e542800b31359494757bbd57b3ce4ad90a`) uses `http.MethodGet` and an Indexer URL; it does not import Indexer ingestion or store packages. The Explorer presentation service imports **types** from `indexer/api`, `indexer/model`, and `indexer/decoder`; this is a compile-time DTO dependency, distinct from a direct Indexer store or decoder-engine invocation. The configured chain is `420` by default; the runtime checks freshness and finality ordering derived from `/v1/health`.

`contracts/config/420explorer-genesis.json` (`b1fea479b0af04f9bd4ad96a47cb2b4c7b3873c0`) is the governing profile: Explorer is `GENESIS_USER_APP`, requires no Explorer-specific Genesis contract, is not canonical authority, and must use `420Indexer /v1` for indexed chain/protocol data. It prohibits independent RPC ingestion, checkpoint storage, reorg engines, and protocol decoder registries. The Indexer and its store remain **off-chain rebuildable projections**, not chain or protocol authority.

## 2. Exhaustive observed Explorer→Indexer operation matrix

The seven required `explorer/service/service.go` `IndexerReader` methods are **not the full runtime dependency**: six additional methods are selected by narrow interfaces in sibling view files. The 13 operations below exhaust the seven `explorer/indexerclient/*.go` production files present at the pinned commit (`address.go`, `assets.go`, `client.go`, `consensus.go`, `contract.go`, `registry.go`; `client_test.go` is a test, not a production client). Each path is a **420Indexer endpoint**, not an Explorer-hosted endpoint. `indexer/api/server.go` (`a978e82785b13b58430a79e3dc17597fd51bd77a`) registers all 13 corresponding GET handlers.

| # | Explorer reader method / owner | 420Indexer GET route | Indexer owner/DTO | Consumer and qualification significance |
|---|---|---|---|---|

**Core vs capability interface:** `explorer/service/service.go` (`442465bc15695180e10603e3039004de156d1c8d`) declares methods 1–7. `explorer/service/{addressviews,assetviews,contractviews,consensusviews,registryviews}.go` declare `addressIndexerReader`, `assetIndexerReader`, `contractReader`, `consensusIndexerReader`, and `registryIndexerReader`, which add methods 8–13. Each service view type-asserts the extra interface and returns an explicit unavailable error if it is absent; the production `*indexerclient.Client` implements all 13. This capability boundary must remain in subsequent test matrices: mocks that implement only the core reader cannot exercise all required Genesis views.

**Transport details:** `/v1/blocks/{number}` is a bare `model.BlockRecord`; the other direct object routes identified here use `ReadResponse[T]` wrappers with `canonicalAuthority:false`; paged block, address and asset responses include page metadata and are separately checked by their consumer. The client checks `CanonicalAuthority` on `Health`, wrapped reads, and address/asset page reads. Explorer also checks chain/snapshot and cross-record provenance in its service layer; the inventory must not mistake these for an independent canonical index. Absence of a per-object authority flag in a bare block DTO is a response-shape fact, not grounds to invent one.

## 3. Dependency ownership/classification — source files and directories

**Direct over HTTP: shared Indexer API.** `indexer/api/server.go` is the route dispatcher, `indexer/api/backend.go` defines the Go `Backend` and `StoreBackend` read bindings, `indexer/api/address.go` supplies the address query, `indexer/api/contracts.go` supplies the contract query, and `indexer/api/types.go` supplies shared wire DTOs. `indexer/api/cursor.go` owns Indexer cursor semantics. Explorer forwards or consumes opaque cursors, not its own checkpoint/reorg cursors. The Explorer HTTP client and presentation service do not directly open Indexer databases. The transport is `/v1`, not the separately hosted Explorer `/v1` presentation API.

**Direct at compile time, not engine ownership:** `indexer/model/{model,assets,contract,consensus}.go` contains block/transaction/receipt/log/asset/contract/consensus record types; `indexer/decoder/{catalog,registry}.go` and related type definitions supply `ServiceSummary` / `ServiceVersion`. Importing their DTO/type packages is not running `decoder.Catalog` or owning a decoder registry. The exact decoder package/type source should be traced more deeply under EXP-0.1.3 when contract, ABI and registry address dependencies are inventoried.

**Underlying shared Indexer infrastructure, *not* direct Explorer dependencies:** `indexer/store/**` (projection storage and checkpoint reads), `indexer/ingest/**` (ingestion/finality orchestration), `indexer/reorg/**` (rollback/replay), `indexer/rpc/**` (node/JSON-RPC source adapter), `indexer/core/**` (canonicalized projection orchestration), and `indexer/consensusview/**` (indexed consensus provider). These contribute to Indexer results through Indexer-owned boundaries; Explorer imports none of these packages in the inspected runtime composition. The `StoreBackend`'s `ReadStore` uses Checkpoint/Block/Transaction/Receipt/LogsByBlock; optional `assetReadStore`, `ConsensusProvider`, Registry catalog and address backend satisfy additional routes. Indexer ownership does **not** confer canonical on-chain authority on its records.

**Distinct shared implementation and verification:** `420-indexer/**` contains the TypeScript/SQL Indexer implementation and IDX qualification work. It is not a second Explorer-specific ingestion loop and is not a Go import of Explorer. `.github/workflows/420indexer.yml` tests both `indexer/**`, `420-indexer/**` and `explorer/**` and executes `scripts/verify-explorer-indexer-consumer.py`; this is shared CI, not evidence of a direct Explorer→TypeScript runtime import. `testnet/public-services/indexer/readiness.json` is the Indexer-owned readiness fixture consumed by that verifier. `contracts/config/420explorer-genesis.json` is Explorer-owned normative configuration. `config/420indexer-v1.json` and published IDX API specification belong to shared Indexer contract scope.

**Optional display dependencies, not canonical query dependencies:** 420 Names and 420 Identity are optional labels under the Genesis profile. No separate Names/Identity lookup is established by the 13 concrete methods in the inspected client. Do not declare those integrations implemented from specification text alone.

## 4. Architecture reconciliation against the profile

| Profile constraint | Observed source evidence | EXP-0.1.2 disposition |
|---|---|---|
| Only qualified 420Indexer `/v1` read API for chain-indexed data | Production executable constructs only `indexerclient.New` as its chain-index reader; all 13 methods issue GET requests to `/v1`. | Source-aligned; live deployment URL, actual service version and qualification are **not** established by this inventory. |
| No standalone Explorer ingestion or JSON-RPC crawl | Inspected executable, client and presentation service have no ingestor or direct JSON-RPC path. | No competing ingestion path observed in those runtime components; entire-binary negative assertion requires later architectural/runtime gate. |
| No independent checkpoint or reorg engine | Explorer reads snapshot/finality metadata; checkpoint/reorg operations are only on the Indexer backend/source side. | Correct ownership at observed interface. |
| No independent protocol decoder registry | Explorer consumes `decoder.Service*` DTOs via shared `/v1/services` and version routes. | Correct ownership at observed interface; detailed ABI/address mapping deferred to EXP-0.1.3. |
| Required seven `/v1` routes | All seven profile routes have client implementations and matching registered Indexer GET handlers. | Source-route matrix reconciled; deployment-time availability/testnet evidence not implied. |
| Required address, asset, contract, validator/epoch, Registry views | Additional six client methods and corresponding Indexer handlers exist; the service gates these through optional interfaces. | These **must** be included in future qualification even though not in `IndexerReader`. |
| Chain ID, freshness, snapshot and provenance | `service.NetworkStatus`, block/transaction/address/asset/contract/consensus view logic validates relevant chain and provenance fields. | Source checks documented, without claiming adversarial/live coverage. |

**Explicit follow-ups (not new EXP-0.1.2 implementation):** The core interface does not express the six extra capabilities as mandatory at construction time; preserve this fact for capability/test coverage under EXP-0.2 and subsequent runtime qualification. The shared `indexer/api/server.go` checks backend support dynamically for address/asset/consensus/registry; confirm actual deployed backend wiring and representative indexed data at the agreed runtime/testnet gate. The seven required routes alone are insufficient evidence for all Genesis views. A publicly reachable API does not establish source authority, chain correctness, stable deployed data or canonical protocol verification.
