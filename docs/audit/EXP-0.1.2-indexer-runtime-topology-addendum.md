# EXP-0.1.2 addendum — source reader vs deployed Indexer API

**Audited commit:** `95a83a961286701b6e8c064de1deccad10f41fd7`. This supplements `EXP-0.1.2-indexer-dependency-reconciliation.md` without altering EXP-0.1.2's inventory scope.

The route matrix proves that Explorer's **client code** calls 13 GET operations and that `indexer/api/server.go` registers matching handler patterns. That is not proof that a deployed Indexer process actually serves those 13 routes. In particular, the inspected `indexer/cmd/indexer420/main.go` (`e628af675076451a86cb096aebdc8f9e28c0e8dc`) constructs a file store, JSON-RPC client and ingestion engine, performs `CatchUp`, prints the resulting health and exits; it does **not** construct an `api.Server`, call `ListenAndServe`, or wire `StoreBackend` with an address/asset/registry/consensus provider in this entrypoint. `indexer/api/server.go` (`a978e82785b13b58430a79e3dc17597fd51bd77a`) and `indexer/api/backend.go` (`b6a0c5efc391215585d7788eba096ef90317cf6a`) establish source-available routes and backend interfaces, not live deployment. The separate `420-indexer/**` TypeScript service is shared Indexer infrastructure, not a direct import of Explorer's Go client; its deployed compatibility is likewise not established by this file inventory.

**Disposition:** The direct dependency and code ownership are mapped for EXP-0.1.2. Actual production/testnet server composition, end-to-end provider wiring, response schema/chain ID on the deployed URL, and data availability are explicit runtime qualification items for EXP-0.2 and the later prescribed testnet gate. Do not mark Explorer or the live Indexer consumer qualified on the basis of a route table or CI unit tests alone. No ingestion/serving implementation is introduced at the inventory step.

**Inventory precision:** `explorer/indexerclient/` has six production Go files at the pinned commit (`client.go`, `address.go`, `assets.go`, `contract.go`, `consensus.go`, `registry.go`) plus `client_test.go`. The main matrix's reference to seven files includes that test; it does not imply a seventh production client module. The source-level dependency count remains 13 methods: seven core plus six supplemental capability methods.
