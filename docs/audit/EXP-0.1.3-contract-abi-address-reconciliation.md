# EXP-0.1.3 — contract, ABI and address dependency reconciliation

**Audited immutable baseline:** `95a83a961286701b6e8c064de1deccad10f41fd7`. **Scope:** Explorer's actual contract-facing read paths, external contract/ABI owners, identifiers, and frozen-address inputs; source-level inventory only. **State:** the observations below are based on the pinned files; the milestone's automated gate must pass on the exact PR head before qualification is recorded. No Genesis address, Solidity implementation, production deployment, or Indexer runtime is modified here.

## 1. Ownership: no Explorer-specific on-chain contract

The authoritative `config/genesis-applications.json` entry `420 Explorer` says `GENESIS_USER_APP` and `contracts_required:false`; `contracts/config/genesis-dapp-contract-map.json` assigns `"contracts":[]`; `contracts/config/420explorer-genesis.json` says `contractsRequired:false`, `canonicalStateAuthority:false`, source `420Indexer /v1 read API`, and prohibits a local decoder registry, RPC ingestion, independent checkpoint store and reorg engine. The absence of an Explorer-specific Solidity deployment is **intentional**, not a missing Genesis contract. Explorer may display any indexed contract, but that does not make those contracts Explorer-owned. No Explorer operator custody, wallet authority, governance control or canonical-state write path is conferred by read-only inspection.

`contracts/src/libraries/ServiceIds420.sol` defines `EXPLORER = keccak256("420/service/explorer/v1")`. **Service ID is not a contract or implementation address**. If an Explorer service is registered, its published implementation/metadata must be established through an authorized live Registry record; the presence of the constant alone proves neither registration nor a deployed app contract.

## 3. Registry contract and ABI provenance: direct versus transitive

**Canonical contract, owned by 420Registry:** `contracts/src/apps/ProtocolRegistry.sol` defines the service/version/history/profile records and publishes `ServiceVersionPublished`, `ServiceRegistrationProfilePublished`, and `ServiceDeprecated`. Its historical `getServiceVersion`/`getRegistrationProfile` and active-service reads are on-chain authority; its `publish*`/`deprecateService` governance-controlled paths are **not** Explorer operations. `indexer/decoder/catalog.go` materializes `ServiceVersion` and `ServiceSummary` from normalized Registry events, including `implementation`, `codeHash`, `metadataHash`, optional `manifestHash`, `dependencyRoot`, `interfaceHash`, activation provenance and active/deprecated state. `indexer/decoder/registry.go` owns a separate Indexer-side decoder implementation registry; Explorer merely imports decoder DTO types and never constructs or owns that registry.

**ABI/event description, owned by 420Indexer:** `420-indexer/src/abi-manifest.ts` maps `ProtocolRegistry` to `420Registry` and derives event signatures/topics and typed descriptor fields from named compiled ABI artifacts and a predeploy plan; it fails when a required artifact is missing. This is the shared Indexer's descriptor-build dependency, **not a bundled Explorer ABI or a claim that an artifact-backed descriptor manifest has been deployed**. The Go Indexer Registry catalog uses normalized event records; its existence alone does not prove how live ABI artifacts and Registry log ingestion are wired together. That runtime seam must be tested in the applicable Indexer/testnet closeout.

**Generated build artifacts and verified-source boundary:** `contracts/out/ProtocolRegistry.sol/ProtocolRegistry.json` and `contracts/src/interfaces/IProtocolRegistry.sol` are candidate publication references; the EXP-0.1.3 script records their presence/absence in the immutable tree. Even if a generated file is available, source verification requires independently qualified deployed bytecode/compiler/build/chain provenance, not a `verified` label in a catalogue. No Explorer code path in the observed view matrix consumes these files at runtime. The lack of a generated ABI cannot be treated as an Explorer-specific missing contract or silently waived for later **Indexer descriptor/verified-source** qualification.

**Other contracts:** 420 Names, 420 Identity, 420 Stake/ValidatorRegistry, governance, tokens and other registry-published services are possible *display subjects* and upstream Indexer decoder/chain inputs, not direct Explorer contract imports. The Explorer Genesis profile calls Names/Identity optional **display enrichments**; the 13 Indexer client methods do not establish separate direct integrations. Do not invent fixed addresses, specific contract ABIs, or completed integrations from future-facing requirements.

## 4. Frozen address and network reconciliation

`config/system-addresses.json` and `contracts/config/system-addresses.json` are identical at the pinned commit (`420-system-addresses-v4`, `FROZEN_STEP6_2`); both reserve `0x0420`–`0x04ff` and freeze `0x0420`–`0x043c`. Both assign **ProtocolRegistry** `0x0000000000000000000000000000000000000434` and **ConsensusSystemCall420** `0x000000000000000000000000000000000000043c`. The latter is a separate consensus-to-execution gateway, **not Explorer, bridge or Registry**. An ordinary registered application implementation address is obtained from Registry/deployment evidence after authorized publication and must not be fabricated from unused slots in the reserved range. Explorer's configured chain ID is `420`, read from its executable's runtime configuration and checked against Indexer records; this is **network identity**, not an application contract address.

The static gate reconciles all pinned frozen assignments by address/name, verifies the two copies are identical, catches any Explorer-name fixed assignment, checks the contract-free Genesis app and dApp entries, inventories full literal EVM addresses in Explorer production sources, and records Git blob SHAs for every tracked Explorer file plus explicitly traced shared files. An observed log/address/implementation in a live Indexer response is a *variable chain datum*, not permission to hard-code it into an Explorer release. The full set of frozen assignments is retained in the two source maps; only the Registry and consensus gateway are direct named anchor examples needed to establish Explorer's boundary.

Record the exact run before declaring (7) satisfied.
