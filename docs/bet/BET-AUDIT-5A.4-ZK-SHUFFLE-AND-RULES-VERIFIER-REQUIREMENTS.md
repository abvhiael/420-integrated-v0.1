# BET-AUDIT-5A.4 — Privacy-preserving shuffle proof integration and NLHE independent verification

## Implemented, exact boundaries

`PokerPrivateShuffleGate420` is a fail-closed on-chain two-stage proof **integration interface**: each authorized provider has an ordered stage, distinct ciphertext-root commitments, a circuit/key/domain/chain/table/ruleset/seat-epoch/hand-transcript statement, and a nonempty proof checked by an immutable verifier contract. Invalid verifier results, stale sequence, unexpected root, repeated stages, and unauthorized or revoked providers revert. Stage completion is cryptographic only **if** an external, real, correctly configured and audited verifier enforces the statement's complete permutation/re-randomization relation. The included `ShuffleVerifierFixture54` is explicitly a *mock for testing contract plumbing only*; never deploy it as production verifier.

**DO NOT assert that a real privacy-preserving shuffle is implemented by this gate alone.** No proving circuit, verifying key, setup transcript or proof generator is included. The existing `confidential-deal.mjs` is an opened-seed deterministic shuffle, NOT a mixnet and NOT private against a dealer/combiner. Moreover, the current initial deck root in stage one is the 5A.4 hand transcript commitment, not an independently verified 52-card encrypted canonical deck; the missing initial ciphertext deck formation proof must be implemented before any shuffle proofs could be meaningful. An external verifier that merely returns `true` is unsound.

## Required cryptographic construction before closing 5A.4

1. Adopt and pin a concrete audited re-encryption mixnet implementation, e.g. threshold ElGamal over a reviewed prime-order curve with honest-device threshold decryption or a reviewed SNARK proof of correctly permuted and rerandomized 52 ciphertext pairs. The ciphertext group, point validity, subgroup/order and encoding rules and verifying key must be fixed, versioned, and independently reviewed.
2. Produce and verify a **canonical initial encrypted deck** representing each of exactly 52 distinct cards, under a threshold public key jointly generated by independent holders. Prove the ciphertext list is complete/unique without leaking card mappings; bind its root to a validated hand commitment. Current contract does **not** do this.
3. Shuffle prover A and shuffle prover B each generate fresh hidden permutations and rerandomization scalars, produce a noninteractive zero-knowledge proof bound to the input/output ciphertext roots and exact hand statement, and publish resulting ciphertexts using an authenticated, immutable data-availability channel. Proof verification must check actual cryptographic witness relations, not an arbitrary hash or signature.
4. Deliver each encrypted hole card to its intended authenticated recipient without giving either dealer unilateral access to the decryptable entire deck. Threshold holders release only narrowly scoped shares with proofs of correct partial decryption; require threshold authorization and per-seat receipt binding. Prevent a dealer majority from reconstructing all future hole cards.
5. Prove every flop/turn/river/reveal maps to the accepted ciphertext deck without duplication, early reveal or substituted card, while preserving hidden cards; implement withheld-share timeout, dispute recovery and revocation/rotation without permitting secret leakage.
6. Add negative/adversarial verification tests using real proofs for malformed points, invalid permutation, duplicate ciphertext, bad rerandomization, altered private delivery, swapped hand/seat, replay, withholding, equivocation and collusion. Independent security review and reproducible parameter/vk hashes remain mandatory.

## What independent Texas Hold'em verification requires

An independent rules verifier **must replay raw, authenticated inputs**, not accept controller-selected `stackChips`, `potChips`, `rakeChips` or a purported final-state hash. Build a deterministic, versioned NLHE rules/state transition function with the following inputs:

- Authoritative immutable table config and ruleset, seated player identities and actual initial escrow stacks, button/blind/ante order, hand nonce and finalized deck/recipient proof reference.
- Every player action (fold, check, call, bet, raise, all-in) signed or authenticated under a seat-specific authorization, with action nonce, betting street, expected state hash, chip quantity, chain/table/version/hand/seat domain and deadline.
- Complete ordered event transcript of blinds and bets with monotonically increasing nonce, including player disconnections, timeouts, folds and auto-actions.
- Cryptographically verified hole-card and board-card reveals referencing the same accepted encrypted deck and appropriately authorized showdowns.

Verifier must recompute, for every transition: the legal player-to-act and time limits; checked/called amounts; min bet and min raise; full versus short all-in raises and whether action reopens; chip debits, committed amounts and invariant conservation; legal street endings and board reveal timing; sorted contribution-tier side pots with eligibility excluding folded players; 5-of-7 poker rank evaluation with kickers, wheel straight, tie splits and deterministically allocated odd chips; uncalled-bet return, rake cap and rules on no-flop/no-drop; final stacks and funds flowing through the canonical escrow; receipt IDs and replay rejection.

**Independent evidence** requires a separate implementation (preferably in a distinct language and code owner), the same canonical test vectors, property/fuzz invariants, and differential comparisons. The verifier's acceptance hash must be the exact root attested by the two-adjudicator finality service. A controller cannot override discrepancies. A separately authorized challenge resolver must resolve invalid transcripts or missing reveals before any irreversible settlement, and the escrow must enforce the verified payouts itself.

Current `PokerHandAccountingProof420` only checks arithmetic conservation of caller-provided numbers; `PokerVerifiedTerminalGate420` only checks hash equality against that transcript. Neither independently validates actual legal poker actions or resulting hand strength. Thus these requirements remain *local unfinished implementation*, not testnet-only.

## Subsequent implementation — partial independent replay kernel (not final acceptance)

Added `clients/420bet-poker/crypto/nlhe-replay.mjs` and a dedicated Node test file. The separate-language verifier can calculate 5-of-7 hand rank with kicker and ace-low straight handling, create contribution-tier side pots with tied/odd-chip allocation, and independently validate initial preflop order, chip debits, initial blinds, raises, action sequence/nonce and stack conservation from raw action arrays rather than from a controller-supplied total. It is intentionally **not** wired to settlement.

**Security-critical remaining gaps:** This kernel does not yet advance flop/turn/river streets; does not implement reopening after full/short all-in raises, heads-up blind/button exception, action-cycle completion, side-pot uncalled excess refunds, showdown/proven-card inputs or disconnection/timeout rules; and has no externally authenticated player signatures, rake policy or cross-language differential vectors. It is only a bounded partial independent rules-verification component. Do not describe this as a complete NLHE rules engine or an acceptance gate.

A real ZK verifiable encrypted-deck permutation/re-randomization circuit, cryptographic proof generator and pinned production verifier/verifying key remain **unimplemented**. In particular, the mock proof-verifier fixture does not demonstrate privacy-preserving shuffle security or collusion resistance. Prior 5A.4 workflows qualify only their exact earlier SHA; this new code requires its own scoped test PASS.

## Further independent replay implementation (not final release)

The PR now includes `nlhe-betting.mjs` for four-street betting-state progression, heads-up blind/button distinction, antes, live player order, action nonces, full vs short-all-in raise handling and challengeable conservation; plus `nlhe-verify-hand.mjs` for **offline, post-opening** seat-specific Ed25519 action authentication, deterministic opened-deck validation using the two-seed SHA-256 commitments, independent 5-of-7 ranking, multi-contribution pot allocation and payout reconstruction. Adversarial tests cover out-of-order actions, short raise reopening, duplicate cards, tampered shuffle, forged signatures and spoofed payouts.

**Qualification boundaries remain:** An external system must authorize registered seat signing keys and bind public Ed25519 keys to current seat epochs; the existing on-chain fingerprint registry is for X25519 encryption and is not a signing-key registry. The offline hand verifier opens the entire deck and **cannot be invoked to reveal cards before independently authorized terminality**. Gameplay-rules completeness still needs short-stack/dry-side-pot re-opening verification, multiway table exits and re-seating protection, uncalled-bet refunds, authenticated street-reveal proofs, showdown/muck policy, rake/no-flop-no-drop, timeout policies, full action-to-canonical-chain state binding, and independent implementation differential tests. Current cryptographic shuffle has NO valid deployed ZK circuit or proof generator. Therefore this branch is a **partial implementation**, not successful 5A.4 completion.

## Experimental gnark proving backend introduced (not re-encryption security acceptance)

`clients/420bet-poker/zkshuffle` now contains a gnark BN254 Groth16 proof circuit asserting that the prover privately knows 52 distinct in-range cards and private salts, and that its hand-domain-separated MiMC commitments match 52 public output positions. The circuit rejects duplicate/out-of-range card indices and altered public commitments; the test exercises **actual Groth16.Setup, Prove and Verify**, not a return-true mock. The proving and verifying keys are generated in the test, not a frozen deployable verifying key. Pinning and reviewing the trusted setup, verified module checksums, actual generated Solidity verifier and hand-bound public inputs remain separate acceptance work.

**Critical distinction:** This circuit proves a sound *private 52-card permutation commitment*, but not that an existing **encrypted input deck** was correctly re-encrypted into the output deck, nor that either dealer lacks knowledge of the private card order, nor that card recipients alone can decrypt. Existing `PokerPrivateShuffleGate420` expects a proof of permutation plus ciphertext re-randomization between input and output roots; this experimental circuit is **NOT compatible with that relation** and MUST NOT be installed as the production verifier for that gate. A reviewed verifiable re-encryption mixnet or equivalent threshold privacy proof is still required before complete 5A.4 qualification.

The independent NLHE offline verifier includes signed Ed25519 actions and post-opening payouts, but canonical signer-key authority, deterministic settlement binding and full NLHE edge cases still require implementation and qualification.
