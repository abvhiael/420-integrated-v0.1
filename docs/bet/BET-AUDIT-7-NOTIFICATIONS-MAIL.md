## Canonical integration boundaries

A detected canonical reorganization freezes the private outbox before any new recipient delivery. It must establish subject/wallet/game-version ownership and tenant-scoped subscriptions; an event with a canonical account topic must match the resolved account. `checkConsent` is a separate required private subscription authority; it must verify exact tenant, subject, subscription, recipient, channel, current policy version, opt-in, no mute and no revocation at **enqueue and dispatch**. No browser-supplied recipient lists, raw email addresses, financial telemetry or message contents are trusted.
- **420Mail:** `create420MailProvider` calls the **existing** `POST /v1/outbox`, `POST /v1/outbox/{id}/process`, `GET /v1/outbox/{id}` and `POST /v1/outbox/{id}/cancel` APIs on `mail/http.go`. The source must be the actual frozen `420/service/mail/v1` and sender must be the independently authenticated Mail identity. The message is a harmless fixed phrase (no player address, event hashes, financial amount or bet details). The sender-scoped idempotency key is deterministic. The adapter verifies tenant/subscription/idempotency and provider receipts and rejects unknown/forged statuses. **It does not claim to call a nonexistent HTTP endpoint.** Establishing the service-native endpoint/provider integration and its production acceptance is still required before any live Notifications messages can be sent.

## Durable delivery state and lifecycle

`openBetDeliveryOutbox` creates a private filesystem-backed, atomic (fsync + rename), single-writer `0600` outbox, rejects group/world-writable parent directories, and refuses an existing writer lock. It bounds state and delivery batch sizes and allows only one writer. Operator recovery of an orphaned lock must be explicit, not an automatic second-writer takeover. Multi-replica operation requires a transactional shared outbox backend and cannot simply share a JSON file across instances.

State: `pending` → `dispatching` → `delivered`, `pending_receipt`, `retry` or `dead_letter`. An ambiguous remote status is **pending**, never a delivery success. Restarted in-flight items are requeued with the **same downstream idempotency key**. Failed deliveries retry with bounded exponential backoff and ultimately move to dead-letter. Provider diagnostic error bodies, credentials and private payloads are not retained.

`cancel(key)`, `revokeSubscription({tenant,userId,subscriptionId})` and `retractEvent(eventId)` preserve durable cancellation tombstones, call remote cancellation when a receipt exists and report remote cancellation as **unconfirmed** unless actually acknowledged. Already-delivered messages cannot be unsent: the original receipt is preserved and flagged `retracted:true`. A canonical reorg persists an outbox halt; `resumeAfterCanonicalReplay(verifyCanonicalRebuild)` requires a fresh trusted full replay decision. If a message has already arrived before an orphan was discovered, an additional compensating notice is necessary; source-only cancellation is not retroactive.

There are no funds, balances, stake amounts, payout verdicts, player wallet addresses, personal email addresses, private Messenger content, signing keys or Wallet transaction capabilities in an approved delivery envelope. Exact transaction and block identities are used only inside independent event-verification boundaries; the recipient-facing envelope contains a pseudonymous event digest, game label, chain and finalized block height.

## BET-AUDIT-7 — durable revocation feed handoff (2026-11-09)

The existing `notifications/betconsent` store now persists a **monotonically sequenced revocation log** on successful `/revoke` and on previously permitted subscriptions transitioning to muted, inactive, revoked or consent-withdrawn via `/apply`. `POST /v1/420bet/subscriptions/revocations` requires the private **read-only** service token; request `{"after":<last-acknowledged-sequence>,"limit":50}`, response `{"events":[...]}`. Events contain only scoped tenant, subject, subscription ID, revision and reason (no recipient PII or financial data). Atomic persistence means restarted service retains the feed; it does **not** guarantee that an external subscriber has already consumed it.

The 420Bet backend's `notifications-revocation-consumer.mjs` validates the authenticated response and consecutive sequence. `notifications-mail-runtime.mjs` synchronizes this feed **before each publish and drain**. The existing outbox persists its `revocationCursor` and a per-subscription tombstone **in the same atomic write** that marks queued deliveries cancelled; a failure or sequence gap does not advance the cursor. Repeated syncs and restarts cannot silently re-enable delivery, including if a stale consent provider reports opt-in. Matching pending/provider-receipt deliveries are cancelled locally; remote cancellation is attempted when a provider receipt exists, and unconfirmed status is surfaced. Already delivered messages are marked retracted; messages already handed to an external provider cannot be recalled with certainty.

**Updated:** The composed Node runtime now catches up on startup, polls continuously while active (one second by default; configurable `BET_REVOCATION_POLL_MS` between 250 and 60000), and checks again synchronously before publish/drain. It persists failed remote cancellation receipts and retries them on subsequent syncs. It remains a bounded-latency pull model rather than synchronous revocation delivery or proof that the service is deployed. A live approved polling SLA, monitoring and operational failover are outstanding. **Still pending:**  Race-free guarantees for a send already in flight, multi-instance transactional storage, independent opt-in authority and official/testnet provider receipts remain open under `TN-BET-7-CONSENT`. ## BET-AUDIT-7 operational delivery worker — scheduled lifecycle (2026-11-09)

`clients/420bet-lobby/server/delivery-worker.mjs` runs the server-only, single-writer operational loop: **(1)** reconcile the authenticated durable revocation feed, **(2)** verify/publish finalized Registry-bound Indexer events to the private outbox, **(3)** dispatch eligible Mail/Notifications deliveries and poll receipts, and **(4)** persist bounded monitoring checkpoints. The new Indexer reader `persistCheckpoint` method stores the canonical event cursor and event history only *after all selected deliveries are durably enqueued*. An interrupted checkpoint write replays idempotent outbox keys. A reorg halts the outbox and fails the worker cycle; resumption requires independent canonical replay approval, not a timer.

The worker has configurable no-overlap scheduling, bounded exponential retry between cycles, private (0600) atomic fsync/rename monitoring checkpoints, an exclusive single-instance writer lock, interrupted-run detection/recovery counters, restart-safe outbox replay (including persisted `dispatching` → `retry`), revocation/remote-cancellation replay, explicit signal-driven shutdown and credential-free health/status data. Its internal state contains cycle timings, counts, last sanitized error category, processed-block position and delivery counts, **not** token material, recipient identity, transaction payloads or message contents.

**Entrypoint:** `npm run worker:delivery` in `clients/420bet-lobby`. This is a **Node backend process**, not the Cloudflare static-asset Worker and not a browser route. Besides the validated BET-AUDIT-7 runtime variables, configure:

| Variable | Behavior |
| --- | --- |
| `BET_NOTIFICATIONS_PROVIDER_MODULE` | Absolute, operator-approved private module exporting `notifications` or default object with `deliverAuthenticated`, `readReceipt`, `cancelDelivery` callbacks. No fabricated Notifications HTTP endpoint or default credentials. |
| `BET_DELIVERY_WORKER_STATE_PATH` | Absolute private worker monitoring checkpoint path, distinct from outbox and Indexer checkpoint paths. |
| `BET_DELIVERY_INTERVAL_MS` | Default 5000; 100–3600000 ms. |
| `BET_DELIVERY_RETRY_MAX_MS` | Default 60000; retry backoff cap (must be at least interval). |
| `BET_DELIVERY_STALE_AFTER_MS` | Default 30000; must be at least interval. |
| `BET_DELIVERY_MAX_BLOCKS` / `BET_DELIVERY_DRAIN_LIMIT` | Defaults 64 / 20; bounded 1–64 blocks / 1–100 deliveries per cycle. |
| `BET_DELIVERY_MONITOR_HOST` / `BET_DELIVERY_MONITOR_PORT` | Loopback only (`127.0.0.1` default), port 8427 by default. |
| `BET_REVOCATION_POLL_MS` | Separate continuous consent polling interval; default 1000 ms. |

**Monitoring:** `GET /healthz` reports worker process and last cycle status, `GET /readyz` returns HTTP 503 if its successful cycle is stale, a cycle has failed, or revocation health failed; `GET /metrics` returns sanitized counters and outbox statuses without private delivery envelopes. The monitor only binds to loopback; expose it to infrastructure monitoring through a separately secured proxy, not a public route. Readiness does not substitute for underlying independent service authorization or canonical network proof.

**Crash recovery:** The outbox already persists retry state and cannot be opened by a second writer. Worker state records `inFlight` before processing and clears it after completion; an interrupted run is detected and its recovery counter incremented at next trusted startup. The same Indexer/outbox checkpoint prevents duplicate *logical* deliveries; downstream Mail/Notifications providers must honor idempotency keys for exactly-once external effects. An existing `.lock` is never stolen automatically: an operator must first establish that the old process is gone, then remove confirmed orphaned worker, outbox and Indexer lock files/directories if present. This fails closed instead of risking double dispatch. State files must reside on private, durable single-writer storage.

**Not yet live:** A concrete independently qualified 420Notifications transport callback module, actual deployed Mail credentials, verified ownership/consent authorities, system supervisor deployment, external alerts, realistic crash/reorg/credential-rotation exercises and official testnet acceptance remain open in the canonical roadmap. Local source and tests do not prove an operational deployment.


**Checkpoint-writer hardening:** the operational worker now acquires `BET_INDEXER_EVENT_CHECKPOINT.lock` for its lifetime, which excludes the separate standalone Indexer synchronization command from advancing the same cursor concurrently. The `BET_DELIVERY_WORKER_STATE_PATH`, `BET_DELIVERY_OUTBOX_PATH`, and `BET_INDEXER_EVENT_CHECKPOINT` must all be distinct. A recovered incomplete cycle starts not-ready until its next successful completed cycle. The loopback monitoring handler returns a controlled 503 on inaccessible outbox metrics. Never forcibly delete a live writer lock.


## Reorganization and cancellation recovery with compensating notices — 2026-11-09

A verified finalized-chain reorganization now invokes a **full bounded canonical replay** through the current signed 420Registry and 420Indexer reader. 420Bet requires the canonical scan to complete; an incomplete, inconsistent, unavailable or reorging authority leaves dispatch fail-closed. The replay reconstructs canonical event IDs using exact chain, approved game version, transaction/log, event kind and block hash. Existing outbox receipts are compared against that complete canonical set: orphaned queued deliveries are durably cancelled, orphaned delivered receipts remain visible as retracted, and a deterministic per-original-delivery correction is persistently enqueued.

Corrections are strictly privacy-minimized: “A previously delivered game update was affected by a chain reorganization. Please refer to current account records.” The correction uses the original tenant, verified owner, subscription, recipient and transport; a distinct deterministic idempotency key derives only from the original opaque delivery key. It contains no user financial data, wallet address or private chain hash. The delivery still requires current active consent; a consent withdrawal does **not** initiate another message to an opted-out recipient.

A `replayPending` flag is persisted before canonical reprojection. Normal dispatch refuses to proceed while either the halt or replay-pending state exists. The rebuilt Indexer checkpoint is persisted first while dispatch stays suspended; the qualified source publisher then reprojects the new canonical events idempotently into the outbox, and only a fully completed reprojection clears `replayPending`. A crash before the replay finishes causes the worker to re-enter verified replay on restart. The legacy boolean-only `resumeAfterCanonicalReplay` route no longer permits blindly clearing the halt.

Provider cancellations now retain durable retry markers for subscription withdrawal, explicit cancellation, direct event retraction and dispatch-time consent denial. If a pending provider receipt subsequently confirms a delivered orphaned notice, the recovery logic records the late delivery and queues its one correction. Unconfirmed provider cancellations stay open for retry; a prior delivered receipt is never represented as successfully unsent.

**Operational limitations:** The canonical replay is bounded (512 × 64 blocks per recovery attempt); an older/high-volume chain requiring more remains safely halted and needs approved chunked recovery. In-flight transport races and private account notification policies must be independently stress-tested against the actual Mail/Notifications deployments. Real live source/reorg evidence, credential provisioning, service deployment and signed release acceptance remain under the canonical testnet roadmap. These repository-side changes are not proof that a live notification provider has delivered a correction.
