# BNB-2.7 — Settlement, Refunds and Host Payouts

**Canonical roadmap title:** Settlement, Refunds and Host Payouts
**Scope:** canonical 420Pay-controlled disbursement, platform fees, developer compensation wallet, partial refunds, failed payments and payout reconciliation.
**Authority:** BNB-1.5 Payment and Settlement Architecture, current Pay deployment/Registry policy, current BNB-2.6 signed Pay finality integration. **Current PR:** #600. Repository truth overrides prior summaries.

## Implemented app-side interfaces

- `016_settlement_refund_payout.sql` stores only noncustodial Pay evidence. A `bnb_settlement_split` freezes the authorized canonical captured asset/chain/payment/beneficiaries and four disjoint allocations (host, platform, developer compensation, retained). Database CHECK prevents the sum differing from captured amount; monetary amounts are bounded integer strings converted to `numeric(78,0)`. No payable balances or self-issued wallet/custody addresses are created.
- `POST /v1/bnb/internal/pay/settlement-splits`: independently signed `pay-settlement-split` assertion with full payload hash; rejects absent Pay issuer, mismatched payment chain/asset/policy or unauthorized developer compensation address. Requires upstream FINALIZED intent/confirmed reservation and captured Pay amount matching the canonical split. First authoritative snapshot immutable; identical signed replay is read-only; conflicting split fails closed. Beneficiaries originate from Pay, **not** host profile or guest input.
- `POST /v1/bnb/internal/pay/disbursements`: separately Pay-authorized `pay-disbursement` events. Only a Pay-confirmed split can reserve a refund/host/platform/developer/retained share. Bound operation, event, issuer/JTI, asset/chain/policy, amount, beneficiary and canonical receipt disallow duplicate economic credit, event ID reuse or conflicting retransmission. A signed `reserved` event holds accounting liability; `finalized` requires independent Pay receipt assertion; `failed` releases a reservation for a new **different** Pay operation. Failed finalized operations cannot be reopened. Same-asset booked **refund reserves + finalized refunds + payout reserves + finalized payouts never exceed captured funds**; each payout category also respects the frozen split cap. Multiple partial refunds may coexist; a full-refund demand after reserved payouts is denied rather than overdrawing funds. Original payer refund destination must be independently attested by Pay.
- Host payout is additionally blocked until actual recorded checkout has passed and Pay attests fulfillment, completed dispute window and verified payout-controller authorization. The developer-compensation recipient and split require independent Pay approval; no invented address or client-side redirect is accepted.
- `POST /v1/bnb/internal/pay/failures`: independently signed Pay decline/provider outage/settlement-failure/reorg notification moves a nonfinalized payment into `recovery_required` for reconciliation, without local disbursement, invented refund or inventory resurrection. A confirmed payment cannot be downgraded via this endpoint.
- `GET /v1/bnb/reservations/{id}/settlement`: private authorized guest/host accounting projection of captured, reserved, finalized, remaining liability, refunded amounts and operation states. Never reports BnB custody.

## Security and conservation

Pay MerchantRegistry/InvoiceRegistry/PaymentRegistry/SettlementRouter/RefundManager remain canonical. The BnB database **mirrors** Pay-authorized assertions: it must never independently initiate a Pay payment, set or move actual wallet funds, create escrow, refund an address provided by a host, or assert finalized payout from a pending callback. Economic conservation is a single asset/chain, single finalized payment identity and revisioned immutable allocation. Unknown policy version, wrong beneficiary, replayed event, unfunded or early host payout, payout/refund collision, receipt reuse, or failed provider are fail closed.

Targeted PostgreSQL/HTTP adversarial tests include synthetic issuer authorization, split sum mismatch, split replay, staged partial refunds, developer-wallet inclusion, premature and excessive host payouts, wrong refund destination, simultaneous refund/payout accounting, finalized refund receipts, failed payout and new-operation retry, view privacy and failed-payment callback denial on finalized captures. Test signer is synthetic; it does **not** qualify a live Pay signing root.
