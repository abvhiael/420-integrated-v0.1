# C05.4 — DOOBr acceptance, pickup, dispatch and handover enforcement

C05.4 adds `AdvanceDOOBrStage`, a single server-side policy enforcement boundary for acceptance → pickup → dispatch → handover. Every normal API, alternate endpoint, mobile replay and operator entry supplies a tenant/order-bound request and is required to pass current `DOOBrStageAuthority.VerifyStage`. The authority must independently verify a fresh policy decision, stage credentials, retailer/carrier identity, order facts and operator role. No previous-stage receipt or offline cached decision alone authorizes the next transition.

The gate rejects unknown entry paths, cross-tenant/order mutation, omitted idempotency key and fact digest, stale revisions, repeats, skipped stages, missing verifier and cancelled requests. A monotonic revision and atomic compare-and-swap at the `DOOBrStageStore` boundary ensure competing retries cannot both pass. `MemoryDOOBrStageStore` is expressly a fixture, never a multi-instance durability substitute. The gate does not independently grant legal approval.

**Targeted tests**: `TestC054DOOBrStagesBypassAndReplay` exercises all four entry types, missing/denying authority, positive stage order with mock verifier, replay, stale mobile revision, skipped stage, cross-tenant/order, absent evidence, and 32-way concurrent acceptance race under Go's race detector.

**Outstanding production work**: Real DOOBr routes, worker queues, mobile offline sync handlers and operator consoles must be wired to the same gate and verified with actual partner authorization. The injected authority interface and memory CAS are not a deployed DOOBr integration.
