# C07.4 — Capacity and abuse controls

Canonical definition: capacity and abuse controls; load, soak, backpressure, rate limits and overload fail-closed behaviour. Qualification is Level 1. C07.10 owns the retained operational Level 2 milestone; C08.5 owns repository Level 3; C09.8 owns production-equivalent load/soak acceptance.

## Implementation and exit criteria

- Capacity: a fixed, role-bound tenant/publication scope has 16 shared work slots and two shared recovery slots using PostgreSQL transaction advisory locks. Each process also has the same bounded local slots and no waiting request queue. Transaction cancellation releases shared slots; handler return releases local slots. Handlers must honor their request context; an unresponsive process requires operator termination and cannot emit a late response through this wrapper.
- Abuse/rate limits: two preprovisioned counters per scope, 120 work admissions and 30 recovery admissions per database-clock fixed one-second window, atomically charged across instances. This is aggregate scope protection, not a per-user fairness guarantee. Request tenant, cookie rotation, source IP and forwarded headers cannot select counter identities. Missing state, primary/database/managed-identity outage, lock/pool timeout and rate exhaustion reject with generic 503 plus Retry-After: 1. A failed/ambiguous admission is never a success. Fixed windows may admit two bursts near a boundary; no sliding-window claim is made.
- Recovery: only POST to canonical operator halt and author/reviewer logout selects the reserve. The original session, CSRF, role, TLS, revocation and tenant checks still decide authority; the reserve grants none. A reserve can itself exhaust under abuse; no availability guarantee is claimed.
- HTTP bounds: 128 KiB incoming body including chunked input; 256 KiB buffered response; two-second operation context; one-second read-header timeout, two-second server read timeout, three-second write timeout, 15-second idle timeout and 16 KiB header ceiling. Buffer overflow/deadline emits no partial export or ALLOW. Slow network input is bounded by the server's transport deadlines, not just context cancellation.
- Durable backpressure: at most 1,024 active queued/leased jobs and 16 MiB serialized active payload per scope. Serialized admission and database triggers enforce concurrency safety. Existing job replay remains possible at capacity and still requires identical payload, kind, attempts and schedule. At most 2,048 unacknowledged impact rows; activation and fan-out roll back together at capacity. Halt, completion and acknowledgment retain their existing authority and recovery semantics. Historical storage still has C07.1's independent finite quota; completed jobs do not disappear or erase evidence.
- Production composition: OpenC074Production obtains managed C07.3 credentials and verifies restricted C07.1 schema/scope bindings, builds the caller's authenticated application handler around its canonical runtime and wraps it. Admission uses its own bounded 20-connection pool, separate from the canonical 16-connection storage pool, preventing admission holders from exhausting storage connections. Serve the returned Handler with NewC074Server and externally provisioned TLS; never deploy a bare application handler as the capacity-controlled endpoint. Migration seven adds rate state and queue triggers; migrations one through six retain their original checksums. Role provisioning creates exactly two counters and grants no counter insert/delete or schema ownership.

## Qualification

Mandatory C07.4 tests: HTTPOverloadAndRecovery; BodyResponseTimeoutAndOutage; DistributedRateAndCapacity (two restricted-role connections, concurrent rate race, global work slots, recovery reserve, missing state, cancellation and tenant isolation); QueueBackpressureAndAtomicOutbox (real PostgreSQL row limits, full replay, altered replay rejection, fan-out rollback and emergency halt); BoundedSoak (32,000 requests, 32 concurrent producers); NetworkPostgreSQLSoak (30 seconds, eight TLS clients, real shared PostgreSQL admission, measured accept/reject/concurrency, fixed counter cardinality). Retain C07.1–C07.3 and directly affected C03/C04/C05/C06 race/security/database tests, Go vet, module integrity, immutable input verification and vulnerability review. Required tests must not skip.

The numerical bounds are conservative repository qualification policy, not approved/measured production throughput or release SLAs. Production fleet sizing, connection budgets across tenants, managed-provider latency, extended soak duration, ingress connection/TLS-handshake limits, external incident/recovery acceptance and approved operational targets must be measured under C09.8 before release. Synthetic thirty-second qualification is not production soak acceptance. C07.10 Level 2 and C08.5 Level 3 remain deferred until their canonical boundaries.
