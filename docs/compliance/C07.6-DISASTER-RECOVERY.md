# C07.6 — Recovery checkpoint (NOT COMPLETE)

Canonical C07.6: Backup/restore and disaster recovery with policy/publication consistency; stale backup must not reactivate a revoked policy. Ordinary Level 1; operational Level 2 C07.10; phase Level 3 C08.5.

## Implemented
An independently supplied latest-checkpoint comparison rejects mismatched scope, restore generation, policy digest, dependency digest, publication sequence, revocation epoch, expired fence, privacy receipt digest/count and authority failure. Adversarial unit tests cover stale policy/revocation, lost purge receipt, recovery generation mismatch, invalid expiry and external outage.

The comparison is a precondition, **not proof of safe restoration**. The independent authority must be authenticated, durable outside the restored failure domain, non-rollbackable and complete. The checkpoint must not be inferred from an old DB. No production authority or restore orchestration is wired.

## Blocking canonical work still required
- Protected encrypted and integrity-verified base backup/WAL, offsite manifest/custody, recovery key and loss testing.
- Independent, monotonic, durable publication/revocation and C07.5 tombstone journal with exact scope/identity, integrity, continuous recording and no trusted stale fallback.
- Fenced/quiesced restore: halt all serving, SDK, workers, dispatch and durable jobs, safely restore consistent primary, replay externally witnessed privacy deletions and revocations *before* opening any access; reconcile policy and publication; advance generations/leases and invalidate old cache/session/key state.
- Real PostgreSQL crash/PITR/partial/corrupt/stale restore and concurrent revocation/partition/outage tests; prove no resurrected deleted data, no unauthorized replay, no stale policy publication, and sound quota/hold state.
- Approved RPO/RTO and recovery runbooks, measured operator drills; physical backups/replicas/WAL/legal disposition and production acceptance remain later C09/C10 gates.

**Status: IN PROGRESS / not certified.** An isolated validator cannot satisfy the step. No permission to reopen a restored service is granted. PR #602 remains draft/open; do not advance to C07.7 until C07.6 exit criteria and exact-SHA fast qualification pass. Earlier C07.5 evidence remains valid for its original SHA, not for this implementation.

## C07.6 authenticated authority / release contract checkpoint

The repository now includes signed checkpoint verification with pinned Ed25519 issuer public keys, reject-on-rollback high-water comparisons, authenticated witness reads, and a C076MonotonicBackend interface whose WithCurrent operation must serialize the live external checkpoint and privileged service release. The coordinator calls ReleaseIfCurrent rather than a separate Release after an independently observed snapshot. Adversarial tests cover forged signatures, a stale signed checkpoint, external outage and a state change at release. A process-local high-water map is additional detection only and is NEVER durable anti-rollback evidence.

**Not yet production accepted:** No external independent storage service, immutable/WORM journal, production issuer identity, monotonic storage counter, or real atomic release backend was provisioned. Signed data alone can be replayed after rollback, and a backend that does not serialize all writers is unsafe. Operator acceptance must verify externally owned durable monotonic CAS, independent credentials and TLS authentication, safe failure handling after partial commit, and real competing revocation/release races before treating this contract as security-complete. Existing real PostgreSQL backup/restore and privacy deletion replay gates also remain open. Step C07.6 is NOT COMPLETE.

## Independent PostgreSQL authority adapter — repository implementation

C07.6 now includes `C076ExternalPostgres`, an adapter for an independently administered PostgreSQL primary. It stores signed high-water checkpoints and deletion-journal entries in separately controlled tables, uses serializable transactions and row locks to reject stale checkpoint CAS, and checks the complete deletion journal against the signed receipt count and digest before advancing. The `WithCurrent` callback runs under the same row lock as checkpoint updates. Targeted real-PostgreSQL tests exercise journal append, stale CAS, revocation rollback, digest mismatch and denied stale release using a disposable CI database.

**Critical production boundary:** A separate PostgreSQL connection object is not operational independence. The external database MUST have different failure/recovery domain, backup ownership, restricted network, keys, replication/storage/WAL and immutable offsite retention; its administrators must not roll back authority history. A database primary alone does not prove non-rollbackability across catastrophic loss or malicious backup restore. Independent witness attestation / durable externally anchored monotonic high-water evidence and a commissioned separately operated service remain unverified.

**Release atomicity limitation:** Row locking serializes committed checkpoint writes against the release callback inside the live independent primary. It does not make an external service-opening side effect atomic with a PostgreSQL transaction. If the database commit subsequently fails, the release side effect cannot be rolled back automatically. The serving gateway therefore MUST enforce a *durably recorded current-generation permit* for every authorization (or use one shared transactional resource for permit and authority), fail closed on loss of authority, and immediately revoke permits on checkpoint advance. That production serving-path integration and crash-after-release-before-commit acceptance are NOT implemented or certified by this adapter. Do not use `WithCurrent` alone as proof of truly atomic cross-system release.

The test PostgreSQL fixture runs in CI's disposable isolated database; it is not the separately operated production authority. C07.6 remains IN PROGRESS; C07.10/C08.5 deferred.

## C07.6 committed release permit and fail-closed serving read

The external PostgreSQL adapter now creates a durable per-scope release-permit table. Within the same serializable transaction and lock as checkpoint comparison, it writes the permitted checkpoint generation and next serving generation, invokes the recovery release callback, and commits. `CanServe` is a fail-closed **independent-primary** check that requires an authenticated matching signed checkpoint, current generation, matching durable release permit, and unexpired publication. Any committed checkpoint update invalidates the previous permit by generation mismatch. Tests exercise valid permit use and revocation invalidation in disposable real PostgreSQL.

**Deployment-critical:** The production serving gateway, evaluator and all clients that can authorize actions must consume `CanServe` (or an equivalent canonical authority gate) on every authorization. A restored app database, local cache, or a successful restore callback alone MUST NOT authorize. The adapter is not proof that these consumers are wired. An external PostgreSQL service with only mutable ordinary backups does not meet the strongest non-rollbackable adversary model: use separate protected admin credentials, tamper-evident externally anchored log and approved offsite immutable/WORM policy. No actual independent hosted backend, production secrets or real multi-instance serving acceptance has yet been verified. The full C07.6 step remains open.
