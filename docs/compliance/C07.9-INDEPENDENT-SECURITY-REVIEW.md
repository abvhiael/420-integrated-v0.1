# 420Compliance C07.9 — Independent security review intake and remediation

**Canonical step:** C07.9 — Independent security review intake, threat/evidence matrix and remediation; distinguish intake readiness from a completed independent review.

**Status:** INTAKE READY FOR QUALIFICATION; **independent security review NOT PERFORMED**. No outside reviewer or independent sign-off is identified; existing tests and security controls do not substitute for an independent review.

## Scope and methodology

The complete canonical T01–T16 risk register in `C01.5-THREATS.json` is mapped, unchanged, to evidence candidate files in `C07.9-SECURITY-REVIEW-INTAKE.json`. These are **candidates**, not independent reviewer validation or evidence of production behavior. The included verifier checks complete mapping and refuses phantom review attribution or implicit closeout.

Reviewer should request read-only access to pinned GitHub SHAs, threat register, architecture/trust boundaries, runbooks, retained CI artifacts, provenance of signed policy/review decisions, source-health and geography evidence, C07.8 drills, schema/tenant isolation, key and publication fence logic, and pending live/testnet acceptance register. Material shared-contract findings must go to owning app and canonical Solidity/Genesis owners rather than silently bypassing their qualification.

## Review intake protocol

1. **Independence and conflicts.** Assign an external qualified security reviewer, record legal entity/contact in restricted evidence, reviewer engagement scope, conflicts, start/end, report version and exact SHA; an unassigned or internal self-review remains `NOT_PERFORMED`.
2. **Evidence custody.** Provide tamper-evident manifest of implementation SHA, exact CI run/job IDs and retained artifact digests. Share minimum-required redacted evidence with least-privilege reviewer access and documented retention, never production secrets, private personal IDs or tokens.
3. **Attack review.** Reviewer must independently analyze T01–T16 and cross-boundary chains including spoofed sources, prompt injection, compromised reviewer and key, false approval, authority unavailability, geographic mismatch, replay, rollback, leaked private data, denial/return and consumer propagation.
4. **Findings register.** For every finding, record stable ID, threat IDs, affected exact SHA/path, reproduction with safe sanitized data, impact, severity, affected tenants/jurisdictions, containment, assigned remediation owner, deadline, commit SHA, affected targeted tests, regression outcome, independent retest evidence, residual risk, and disposition. Never label an unassessed row as PASS.
5. **Remediation and verification.** Security owner fixes root cause in-app, runs appropriate Level 1 against exact changed code SHA; independent reviewer retests and signs disposition or identifies accepted residual risk only under explicitly authorized risk governance. No review report or operational approval may grant regulated transaction authority.
6. **Escalation.** Critical false approval, private-data exposure, unauthorized review/publication or regulator restriction issue forces service fail-closed and incident escalation. Retain C07.8 incident runbook and valid lawful cancellation/refund/recovery while denying unsafe new actions.
7. **Release gate.** The external review is only **COMPLETE** once the independent report and disposition are actually delivered and verified. `READY_FOR_INDEPENDENT_REVIEW` never means assessment passed or production deployment authorized.
