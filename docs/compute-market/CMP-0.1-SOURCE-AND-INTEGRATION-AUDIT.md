# CMP-0.1 — Source inventory and integration verification

Status: **CMP-0.1 inventory assessment complete; ComputeMarket implementation and end-to-end integration NOT complete.** Inspected repository `abvhiael/420-integrated-v0.1`, immutable `main` baseline `277395931f5419af0728f3ea801800401a8bb336` (same main SHA checked at audit). This is a source-and-test evidence audit, not deployment certification or proof that external repositories contain no implementation. The frozen [ComputeMarket V1 architecture](../420-COMPUTE-MARKET-V1-ARCHITECTURE.md), not former recovery branches or aspirational contract catalogs, controls CMP.

## Method and evidence semantics

Checked the frozen architecture, Genesis dApp catalog, frozen system-address assignments, post-PR-365 reconciliation, target source directories and named source contracts, AI/Vault/Resource/Trust/Arbitration code, AI and Vault Foundry tests, `node420` source/CLI, service/SDK package directory, and the CMP PR qualification runs. **SOURCE** = executable checked-in source inspected; **TEST** = specific test source exists, not a new CMP integration test; **CATALOG** = filename in a manifest without proven deployable source; **NOT LOCATED** = queried named path absent on this baseline, not a universal negative about all branches/other repositories; **LIVE UNVERIFIED** = no execution-chain receipt, runtime codehash, deployed registry publication or live job/settlement evidence established here. Source URLs are pinned to the audited SHA.

## 3. Vault funding, accounting and authorization — source-level call-path verification

- [VaultFactory420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/vault/VaultFactory420.sol) deploys an `AssetVault420`, but factory deployment is not registry registration; [VaultRegistry420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/vault/VaultRegistry420.sol) requires caller = registered creator, correct vault ID/registry, valid active policies, and manages ACTIVE/FROZEN/WINDING_DOWN/CLOSED. Closure rejects nonzero assets or obligations.
- [AssetVault420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/vault/AssetVault420.sol) is the **write/custody interface**, not [VaultRouter420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/vault/VaultRouter420.sol), which exposes read/authorization views. `depositNative`/native `receive` deposit `address(0)`; `createObligation(operationId,obligationId,asset,beneficiary,amount,type,sourceRef)` checks the caller's vault-scoped capability and reserves free balance; `releaseObligation` turns it claimable; `claim` transfers only to recorded beneficiary, including in FROZEN state; `cancelObligation` frees a still-reserved obligation. Mutating calls consume one-time operation IDs and use a shared reentrancy guard. Delegated withdrawal to a third party requires recipient/asset/action route-scoped authority.
- [VaultAccounting420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/vault/VaultAccounting420.sol) authorizes bookkeeping only for the registered vault address, records `recordedBalance`, `reserved`, `claimable`, `released`, and prevents withdrawal of encumbered funds. Obligation states are 1=reserved, 2=claimable, 3=claimed, 4=cancelled, and obligation ID is globally unique in the accounting contract.
- [VaultAuthorization420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/vault/VaultAuthorization420.sol) consults the shared [CapabilityRegistry420.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/src/system/CapabilityRegistry420.sol) for principal/action/vault scope/amount and optional recipient-bound routes. There is **no ambient privilege for a CMP adapter**; registration, grants, actor identity, maximum per-call/period scope and revocation must be proven before operational wiring.
- [Vault420.t.sol](https://github.com/abvhiael/420-integrated-v0.1/blob/277395931f5419af0728f3ea801800401a8bb336/contracts/test/Vault420.t.sol) is **TEST** for reserved-balance protection, cancellations, beneficiary-only claims, frozen claims, closure/replay and permissions, but creates a mock capability registry and self-contained fixture, not a funded CMP job.
- **Integration decision:** use a registered Vault and narrowly authorized per-job obligation(s). A `cancelObligation` only frees balance *inside the Vault*; it does not itself send an unused/refundable balance back to a particular payer. In a shared Vault it must never make refunds withdrawable by unrelated principals. CMP needs an explicit payer-bound refundable obligation, authorized withdrawal route, or equivalent policy-proven mechanism; encode unique operation/obligation IDs, atomic order of funding confirmation versus actual custody, split/partial earning rules, failure/retry recovery, and reconciliation `funded = earned + refundable + still-reserved` before exposing a paid job. A one-obligation release for the entire deposit is **not** proof that a partial provider payout plus payer refund is supported.
