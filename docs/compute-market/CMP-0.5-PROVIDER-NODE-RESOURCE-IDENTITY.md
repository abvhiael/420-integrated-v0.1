## 1. Three distinct immutable identities

`ComputeProvider` is the economic/legal operator and beneficiary authority; `ComputeNode` is one execution operator endpoint permanently parented to one provider; `ComputeResource` is a schedulable compute capability permanently parented to one node **and** that node's provider. `providerId`, `nodeId` and `resourceId` are distinct nonzero `bytes32` canonical identifiers in separate authoritative registries and namespaces. An ID cannot be recycled, transferred to another entity, silently reparented or treated as an offer, request, match, job, unit or AI session ID. Do not hash an IP address, operator wallet address, advertised machine model or ephemeral endpoint into the immutable identity: those can rotate without changing the underlying entity. If ownership/provider parent genuinely changes, retire the original node/resource and register a **new ID**, with separately authorized disposition of outstanding jobs.

V1 registry allocation is monotonic and unique within each registry's chain-scoped namespace. To pin a reproducible canonical ID formula, define `IDENTITY_DOMAIN_V1 = keccak256(utf8("420Integrated.ComputeMarket.Identity.v1"))`, distinct ASCII tags `PROVIDER`, `NODE`, `RESOURCE`, and separate positive `uint64` counters for each registry, never reused or wrapped. Define `providerId = keccak256(abi.encode(IDENTITY_DOMAIN_V1,uint256(chainId),address(providerRegistry),keccak256(utf8("PROVIDER")),uint64(providerSerial)))`; `nodeId = keccak256(abi.encode(IDENTITY_DOMAIN_V1,uint256(chainId),address(nodeRegistry),keccak256(utf8("NODE")),uint64(nodeSerial),bytes32(providerId)))`; `resourceId = keccak256(abi.encode(IDENTITY_DOMAIN_V1,uint256(chainId),address(resourceRegistry),keccak256(utf8("RESOURCE")),uint64(resourceSerial),bytes32(providerId),bytes32(nodeId)))`. Standard static ABI words in that exact order, **not** packed encoding; Ethereum Keccak-256, not SHA3-256. Registry addresses must be deployed, verified and authorized, never invented fixed predeploys. Zero/foreign chain ID, zero registry, zero serial, exhausted serial, zero parent, unsupported schema, collision or stale/unauthorized registry must fail. Each parent is resolved from canonical state, never trusted from a caller-supplied alternative. Derive actual test-vector hex and independently verify Solidity/Go or TypeScript parity before implementing these proposed formulas; this document does not claim those fixtures exist.

## 2. Canonical records and revisions

Provider minimum: `providerId`, immutable original registrant/creation commitment, current operator account, `providerManifestHash`, stake/security-policy ID and stake reference, settlement account/reference, `createdAt`, monotonically increasing `revision`, and `REGISTERED | ACTIVE | SUSPENDED | RETIRED` state. Only `REGISTERED -> ACTIVE <-> SUSPENDED -> RETIRED` is allowed; `RETIRED` is terminal. ACTIVE requires a current, objectively checked minimum stake/security-policy configuration and valid operator/manifest authorization. An operator-account rotation or provider-manifest change creates a signed, auditable revision; it must not create a second provider ID or change a previously accepted beneficiary. `settlementAccount` is an operator-authorized destination associated with the provider, **not** an unreviewed destination for historical match obligations. Bind the beneficiary/reference and applicable version at match acceptance; later rotation is only effective for future matches or an explicitly authorized claimant migration that preserves an existing recipient's rights.

Node minimum: `nodeId`, immutable `providerId`, currently authorized node operator/account/public-key reference, `nodeManifestHash`, endpoint/service-manifest hash, endpoint expiry, `createdAt`, monotonic `revision`, and state `REGISTERED | ACTIVE | SUSPENDED | RETIRED`. A node becomes ACTIVE only if parent provider is ACTIVE and node authorization, endpoint/service-manifest integrity, freshness and operator capability all pass. A suspended or retired provider makes its nodes ineligible for **new** acceptance, irrespective of node-local status. Endpoint rotation changes signed endpoint revision, not node/provider identity; new endpoint MUST authenticate as the same node and provider. Expiry, removal or compromise stops *new assignment* until a valid new endpoint is published. A retired node cannot be resurrected by an endpoint update.

Resource minimum: `resourceId`, immutable `providerId` and `nodeId`, `computeClass`, `hardwareProfileHash`, canonical versioned memory/capacity declarations, `runtimeProfileId` and version, capability bitmap/commitment and its policy version, availability status, `createdAt`, monotonic `revision`, and optional independent attestation/evidence reference. Allowed initial classes are `CPU_GENERAL`, `GPU_INFERENCE`, `GPU_TRAINING`, `GPU_RENDER`, `ACCELERATOR_GENERAL`, `ZK_PROVER`, `HIGH_MEMORY`; commercial device labels remain noncanonical metadata. A resource is eligible for new matching only when both ancestors are ACTIVE, the resource is AVAILABLE, its signed capabilities meet the accepted workload/manifest and policy, and capacity is not already double-reserved. No operator may substitute a resource of a different compute class or weaker verified capacity while retaining an accepted resource ID. Hardware replacement or material capability downgrade requires suspension of new offers, a versioned revision and requalification of new work; irreversible physical replacement or reparenting that breaks identity continuity requires a new resource ID. A capacity **increase** cannot retroactively broaden an accepted job's resource/price/privacy terms.

`revision` increments atomically on every canonical material mutation; update events carry old/new revisions, effective time, policy version, actor and previous/new commitment hashes. Preserve an append-only reconstructable history, not only the latest mutable pointer. Raw endpoint credentials, private location coordinates, serial numbers, workloads, secret attestation collateral and private machine telemetry remain off-chain; canonical state records only bounded commitments and necessary policy decisions.

## 3. Registration and capability authorization

Provider registration requires an authenticated registrant, nonzero operator identity, manifest commitment, accepted provider policy, bounded security/stake reference and distinct allocated ID. Activation requires live eligibility evidence and separately scoped capability-registry authorization. Node creation requires an ACTIVE parent provider's **node-registration capability scoped to that providerId**; registration binds parent permanently and authenticates the operator and endpoint signing key under a versioned key policy. Resource creation requires the provider-scoped resource-registration capability, an existing node of the same parent provider, canonical compute class/profile, authorized operator and admissible capacity/capability claims. A provider's operator cannot attach a node from another provider or a resource to a different parent by presenting matching self-reported fields. Any delegation records grantor, delegate, action, object scope, nonce, expiry, revocation and revision; signer or session capability is checked at the actual action, not inferred from a successful prior login.

Distinct action scopes include `provider.register/update/activate/suspend/retire`, `node.register/update/status`, `resource.register/update/status`, `offer.publish/cancel`, `match.accept`, `attempt.assign`, and `receipt.submit`. These do **not** grant Vault release, requester funding, governance, validator, bridge, arbitrary-wallet or unrestricted registry-administration rights. A node key signs *node-local* liveness/endpoint/attempt claims only within its provider-bound grant; it cannot change provider economic identity or requester authorization. Provider suspension/retirement and key compromise immediately block new registration, offer/match acceptance and assignment; existing earned entitlements and payer refund rights remain governed by their accepted terms, never confiscated or redirected by status changes.

## 4. Signed manifests, endpoint freshness and hardware evidence

A provider manifest commits to operator/security policy, beneficiary reference policy, jurisdiction/region claim policy and approved node-registration scheme. A node/service manifest commits to providerId, nodeId, revision, endpoint public-key fingerprint, declared service protocols, expiry and region/privacy claims under a **versioned canonical byte encoding**, independently signed by an authorized provider/node key. Endpoints are *transport hints* and may rotate, but their signed content is validated against registry parent, revision, chain, expiry and an anti-replay nonce. An expired endpoint is never considered ACTIVE because a stale cache still contains it. A resource manifest commits to providerId/nodeId/resourceId, compute class, runtime/capability profile versions, bounded capacity and supportable verification modes. Hashes are claims, **not proof of physical GPU model, honest metering, trusted execution or computation correctness**. If an accepted policy needs hardware/TEE/region assurance, require a verified, fresh, provenance-bound attestation with explicit trust roots and expiry; do not silently treat self-attestation or a marketplace rating as hardware proof. No endpoint or manifest replacement can change the provider/resource/economic identity bound to an accepted job (CMP-INV-028/029).

## 5. Eligibility, acceptance snapshots and reservation

At offer publication and again atomically at match acceptance, resolve `providerId -> nodeId -> resourceId` using trusted registries; check immutable ancestry, ACTIVE provider and node, AVAILABLE resource, policy/security eligibility, nonexpired endpoint and offer, accepted compute class/runtime/verification and region/privacy constraints, sufficient remaining capacity and prequoted replication. Do not allow a scheduler's cached eligibility, self-reported device, or off-chain service discovery to override canonical checks. For class-based offers, an explicit eligible resource and node must be resolved before accepting the immutable match; no null resource may be left for the worker to pick after acceptance.

Persist the accepted `providerId`, `nodeId`, `resourceId`, relevant provider/node/resource revision and capability/policy hashes, frozen beneficiary/settlement reference, reservation quantity and accepted pricing in a canonical match/assignment snapshot. The architectural minimum ComputeMatch lists provider/resource; node is **derived via the resource's immutable parent** and its revision is committed as supporting evidence, not introduced as an alternative independently writable match authority. Compare against CMP-0.2 authoritative accepted match and CMP-0.4 manifest. Registry revisions after acceptance cannot silently rewrite that snapshot or reprice/refund an existing job. A critical security suspension may pause further execution under an explicit job lifecycle/dispute policy, but cannot erase an earned verified entitlement or silently substitute a new provider/resource. Release a capacity reservation exactly once on a terminal/authorized transition, and make duplicate acceptance, retry, cancel and timeout idempotent so the same physical capacity cannot be oversold by two conflicting live reservations.

For retries, CMP-0.3 `unitId` remains stable and each new `attemptId` is authorized separately. Node/resource/operator reassignment within the same accepted provider may be permitted **only** if the bound job/manifest/policy expressly authorizes an equivalence class and an auditable attempt-specific reassignment record checks all constraints and budget; a different provider or materially different resource requires separate requester-approved rematching/new job or an explicit preaccepted recovery policy that preserves immutable economic bindings and at-most-once unit payout. No scheduler may change the accepted match/beneficiary by changing a worker URL or assigning a new attempt. Receipts bind actual provider, node/resource, attempt, accepted manifest and assignment revision; signing authenticates a claim, not objective verification.

## 6. Implementation and executable test gate

Proposed source ownership follows the frozen architecture: `ComputeIds420.sol` owns ID derivation and canonical uniqueness; `ComputeAuthorization420.sol` checks narrowly scoped provider/node/resource actions; `ComputeProviderRegistry420.sol`, `ComputeNodeRegistry420.sol`, `ComputeResourceRegistry420.sol` own separate immutable parentage, status and versioned snapshots; offer/match/job registries consume these checks, not duplicate their authority. Registry publication is gated by deployment, code-hash verification and authorized ProtocolRegistry publication. Do not infer these proposed file paths are existing executable source.

Before claiming implementation: check in versioned positive and negative ID fixture vectors (domain hash, ordered ABI words, encoded bytes, expected Keccak outputs), independently assert byte-identical IDs in Solidity and Go/TypeScript, and implement registry lifecycle/capability/event tests. Positive coverage: same immutable identity after endpoint/key rotation and restart, distinct chain/registry/serial/entity types, active ancestry and compatible resource acceptance, idempotent reservation/release and accepted snapshot reconstruction. Negative coverage: duplicate/reused/wrapped serial, provider/node/resource namespace collision attempts, zero/foreign registry or chain, cross-provider node/resource reassignment, parent retirement, stale endpoint, forged key/unauthorized delegate, revoked registration, unsupported policy, false hardware claim when attestation is required, capacity oversubscription, accepted downgrade, class/runtime/privacy/region/verification mismatch, attempted beneficiary change after match, suspension confiscation, node substitution by scheduler, attempt reassign/double payout, missing or changed signed execution manifest, job in terminal state, stale snapshot replay and cross-chain signatures. Check concurrent offer/match acceptance and status/revision races; assert all failures leave balances, reservation counts and canonical parentage unchanged. Map relevant tests to CMP-INV-001–030, especially 002–005, 007–010, 018–021, 023–030; run contract/application qualification **after executable components exist**, and exact-head repository CI after each doc change.
