# CMP-1 — Executable ComputeMarket foundation

Status: **IN PROGRESS — implementation, not market deployment**. Base: merge of [CMP-0 documentation milestone](CMP-0-PROTOCOL-SPECIFICATION.md) via PR #367. The [frozen V1 architecture](../420-COMPUTE-MARKET-V1-ARCHITECTURE.md) and [CMP-0.12 qualification register](CMP-0.12-QUALIFICATION-AND-CLOSEOUT.md) control acceptance. Do not reinstate retired recovery branches as authority, assign a fixed Genesis predeploy, activate a registry entry before deployed codehash verification and authorized publication, or treat successful generic CI as funded-market proof.

## Implementation increments and exact boundary

- **CMP-1.1 — Canonical typed IDs and vectors:** create `contracts/src/compute/ComputeIds420.sol`, enforce exact CMP-0.3 domain-separated standard ABI unit/attempt derivation and invalid-input rejection, and check in dedicated executable Foundry positive/negative fixtures. The first increment may be a pure library; it does not instantiate registries, pay anyone, or make mutable job identity authoritative. Freeze independently generated byte-for-byte Solidity and Go/TypeScript ABI/Keccak vectors before marking cross-language parity complete.
- **CMP-1.2 — Object-scoped authorization:** implement `ComputeAuthorization420.sol` against the actual shared Capability Registry interface with explicit component/action IDs, versioned scope functions, signer-grant policy, expiry/amount checks where relevant, tests for unauthorized actor, cross-object capability, revoked/expired grants, payer and provider role separation. No caller's ownership of one object implies Wallet, Vault, bridge, consensus or governance control.
- **CMP-1.3 — Versioned policy foundation:** implement `ComputePolicyRegistry420.sol` with authorized publication, immutable accepted-policy commitments, supported schema/profile revisions and policy-specific bounds. An upgrade cannot substitute new rules for an already accepted match or verification profile. Add objective positive and downgrade/overrun/unknown-policy tests.
- **CMP-1.4 — Provider/node/resource identity:** implement registries with stable distinct IDs, permanent node parentage, resource provenance and revision/suspension guards. Register proposed CMP components only through authorized ProtocolRegistry publication after deployment and codehash check; no reserved Genesis address is allocated.
- **CMP-1.5 — Foundation qualification:** pin typed fixtures in two independent languages, test all source-appropriate frozen CMP invariants, run dedicated Foundry and relevant application gates, reconcile current `main`, and qualify the exact final head. Mark later-layer requirements (request/match, payer-isolated Vault, receipts, verifier, worker, dispute, SDK/UI, AI adapter and funded end-to-end) explicitly OPEN for later CMP increments.

## Branch and release rule

Keep CMP-1 changes isolated from the merged CMP-0 specification. A `forge build`/`forge test` result on the exact CMP-1 source and explicit CI workflow evidence are necessary for executable phase gates; a documentation check or unrelated Go build is insufficient. No production-ready declaration or merge on an untested implementation head. Phase records must distinguish source created, test committed, test executed/passed, integration evidenced and deployed/registered runtime.
