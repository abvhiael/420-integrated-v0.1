# CMP-1.1 — Original ComputeJobRegistry: implementation and qualification

Authority: original five-slice `CMP-1-IMPLEMENTATION-ROADMAP.md`. This work remains **CMP-1.1**, not a newly numbered CMP slice. The old foundation PR #369 remains distinct from the original CMP deliverables.

## Original eight required responsibilities

`ComputeJobRegistry420.sol` implements unique creation, guarded versioned lifecycle transitions, immutable manifest/workload/input/output schema bindings, creation caller as owner, authority-gated worker assignment, recorded result commitment, and independent verifier decision reference. `contracts/test/ComputeJobRegistry420.t.sol` covers these registry-local behaviors. The test-only `JobEvidenceFixture420` is not production proof. Do not publish a production job-registry endpoint from these tests.

## Concrete integration progress

`contracts/src/compute/ComputeJobVaultReservationEvidence420.sol` introduces a read-only evidence adapter backed by the existing `VaultRegistry420` and `VaultAccounting420`: a registered active escrow-type Vault created by the given owner, native or token asset configured for this instance, live reserved obligation referencing precisely this job ID, correct configured beneficiary, positive minimum value, and sufficient recorded reserved balance. The adapter does not create money, obligations, settlement authority or any synthetic evidence. It is an **intermediate, unadmitted source**; the existing Vault uses pooled vault-level deposit accounting, so Vault creator identity plus an obligation cannot prove which payer actually deposited money. The current adapter therefore MUST NOT be configured as sole production funding authority or interpreted as a complete CMP-1.2 escrow. `fundingRef` is an obligation ID, not a payer authorization. The adapter is not deployed or published.

## Remaining blocking work — do not mark CMP-1.1 complete

1. **Authoritative request/manifest:** `createJob` presently accepts caller-provided request ID, request revision, manifest and commitments. Implement an independently verifiable versioned `ComputeRequestRegistry420`/signed-manifest authority, check exact owner/request/revision/workload/input/output/deadline bindings **inside** the creation path, verify signature domain, expiry, authorized payer and bounded spending. Merely emitting request fields, checking nonzero hashes or trusting a mock is not authority.
2. **Real owner/payer funding:** implement payer-specific deposit authorization and job-isolated reservation under the original CMP-1.2 `ComputeEscrow` duties, bound to native $420 as the canonical Vault asset; prove payer, source transfer, vault, job, maximum authorized spend, reservation amount, cancellation/refund beneficiary, live reserved state and replay resistance. `AssetVault420.depositNative()` and `VaultAccounting420.recordDeposit()` aggregate by vault, not by payer; current obligation records have no payer field. Do not infer payer deposits from vault creation, the mere presence of a reservation or permissive adapter callbacks. No worker may enter paid RUNNING without the qualified result.
3. **Authenticated worker/assignment/result:** establish authorized, accepted match with locked provider/node/resource and a currently eligible operator; bind job+assignment+attempt, worker identity and signed receipt/result to that match, with replay and stale-revision prevention. The current `ComputeResourceRegistry420.isAvailable` is only identity availability, not independently attested hardware or a match engine. No caller-supplied assignment hash is proof of a real execution attempt.
4. **Independent verifier:** use verifiers distinct from job owner/worker according to approved verification profile and CMP-1.4 verifier authority, signed decision binding job+attempt+result+profile+nonce, provenance and expiry; prevent verifier self-selection and forged outcomes. A caller-provided verifier address or a mock `verified=true` is not a verified decision.
5. **Closeout / qualification:** prove failure, expiry and dispute custody-safe paths; run real-source positive and hostile cross-job/cross-owner/replay tests with required Solidity, app and docs checks on exact final reconciled PR head. No actual settlement authorization or production deployment until all proofs exist.

**Current status: incomplete; PR remains draft.** Green unit CI only establishes local state-machine behavior and compilation on its tested SHA. Preserve the original CMP-1.1 → CMP-1.2 → CMP-1.3 → CMP-1.4 → CMP-1.5 order, and do not introduce a second permissive escrow, fabricated worker registry or shadow verifier authority to fake completion.
