# CMP-1.1.3 — accepted match, worker assignment, result provenance

This slice builds on CMP-1.1.1 request consent and CMP-1.1.2 payer-attributed reservation. It is NOT the independent correctness-verification or complete CMP-1.3 worker protocol.

`ComputeJobAcceptedMatch420` is configured as `ComputeJobRegistry420.matchEvidence`, and `ComputeJobMatchedWorkerEvidence420` is configured as `workerEvidence`. Both bind to the same immutable registry, once, through deployment-admin-only binding. Legacy `ComputeJobWorkerEvidence420` remains an earlier identity/capability gateway, not the strict worker evidence source for accepted matches. Do not configure permissive test fixtures in production.

The job owner proposes exactly one match for a FUNDED job, selecting a currently available resource and snapshotting its provider, node, resource revision, and registered operator. The owner transitions the job to MATCHED only if the evidence authority recognizes its request and manifest. The exact registered operator, with canonical job-scoped `ACTION_ACCEPT_MATCH`, accepts the match through the authority, which writes `recordAcceptance` to the registry at the expected revision. A resource/node/provider revision or operator change invalidates the admitted match; a fresh acceptance requires a new qualified protocol path, not silently replacing the agreed resource.

The strict worker authority binds a unique assignment to job, accepted match, acceptance reference, resource, operator and attempt 1. It requires job-scoped `ACTION_EXECUTE_ATTEMPT` and correct registry revision, and calls `assignWorker`. The same authenticated operator, with `ACTION_SUBMIT_RECEIPT`, commits a one-time nonzero receipt/output hash to the exact job, request, manifest, match, acceptance, resource, assignment and attempt, then calls the registry's authenticated `recordResult`. This is evidence of WHO submitted a commitment for WHICH assignment, not objective proof of GPU runtime, completed computation, trustworthy measurement, or correct outputs. The first attempt only is supported; retries and additional execution units require separately specified custody-safe rules.

`ComputeJobAcceptedMatchWorker420.t.sol` uses test-only funding evidence and real provider/node/resource state plus a test-only capability source; it covers owner proposal, operator acceptance, assignment and result commitment, unaccepted-match rejection, unauthorized operator, wrong resource, stale job/resource revisions, duplicate assignments/results, and cross-job evidence replay. It does not qualify real funding (qualified separately in 1.1.2) or deployment integration with the production capability registrar. Confirm Solidity Contracts, 420 Integrated Qualification, and 420Docs on the exact final branch head. Never treat green unit CI as independent worker-output correctness or a production launch approval.

Remaining CMP-1.1 gates: reconcile signed-request + real payer custody + accepted-match authorities in one end-to-end positive/hostile integration test and deployment graph, qualify canonical capability registration rather than test grants, and complete independent verifier provenance under CMP-1.1.4. Complete escrow settlement, capacity reservation, actual hardware attestation, retries and dispute refunds belong to later CMP slices. PR #370 remains draft and unmerged.
