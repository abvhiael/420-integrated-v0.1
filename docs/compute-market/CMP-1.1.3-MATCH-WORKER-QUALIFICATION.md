# CMP-1.1.3 — accepted match, worker assignment, result provenance

CMP-1.1.3 builds on the EIP-712 signed request and actual payer-attributed, job-isolated native-420 reservation in CMP-1.1.1–1.1.2. This is not general-purpose escrow, capacity reservation, independent verification, or the full CMP-1.3 worker protocol.

## Evidence configuration

Use `ComputeJobSignedRequestAuthority420` for request evidence, `ComputeJobPayerCustody420` for funding evidence, `ComputeJobAcceptedMatch420` for match evidence, and `ComputeJobMatchedWorkerEvidence420` for worker evidence. Bind the identical registry in custody, match and worker contracts. Configure verifier and settlement interfaces as fail-closed pending their separate qualification. Do NOT substitute the unsigned request authority, pooled legacy Vault reservation adapter, older worker identity gateway or permissive funding fixtures.

The owner proposes a single match after actual funding; this snapshots the available resource, provider, node, resource revision, and registered operator. That operator must explicitly accept the match with job-scoped `ACTION_ACCEPT_MATCH`. The strict worker evidence checks the exact accepted resource/operator, job revision and job-scoped `ACTION_EXECUTE_ATTEMPT`, records attempt 1, and permits the same authenticated operator holding `ACTION_SUBMIT_RECEIPT` to commit a single receipt and output hash. The result commitment includes job, request, manifest, match, acceptance, resource, assignment and attempt. Neither authenticating a worker nor recording an output hash establishes real hardware, verifiable execution, correct output, capacity reservation, metering or entitlement to release funds.

## Code and tests on PR #370

`ComputeJobAcceptedMatchWorker420.t.sol` tests accepted-match/worker edges with explicitly TEST-ONLY funding and grants. `ComputeJobSignedCustodyMatchWorkerIntegration420.t.sol` uses the combined signed authority, real native payer transfer, isolated funding evidence, accepted match and strict worker receipt; it covers the successful request-to-result path, unfunded and unauthorized funding, over-ceiling payment, cross-job funding/assignment reuse, separate job balances, stale resource revisions, and payer-only unmatched refunds without consuming a different job's reserve. The integrated graph denies verifier and settlement admission. It uses TEST-ONLY capability grants to isolate authorization mechanics from registrar lifecycle.

`ComputeJobCanonicalCapability420.t.sol` separately uses the REAL shared `CapabilityRegistry420` with `ComputeAuthorization420`: its registrar registers the compute component and authority, tests grants for each of `ACTION_ACCEPT_MATCH`, `ACTION_EXECUTE_ATTEMPT`, and `ACTION_SUBMIT_RECEIPT` in one job scope, rejection of other principals/jobs/actions, unauthorized grant/revocation attempts, revocation isolation and expiry. These tests establish behavior of the canonical permission contract, not the actual target network's governance/registrar configuration. Production deployment must verify the compute component is registered by its authorized registrar, and that only the designated authority may issue and revoke grants. No unrestricted or test-only grants may be carried into deployment.
