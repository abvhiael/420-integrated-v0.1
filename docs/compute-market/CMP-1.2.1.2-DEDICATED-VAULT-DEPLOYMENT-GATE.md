# CMP-1.2.1.2 — Dedicated CMP Vault authorization and deployment gate

**Status:** deployment-ready *candidate source* on draft PR #371; actual testnet/mainnet deployment NOT performed by repository commits. Paid-worker execution, matched-job refunds and settlement remain disabled. Do not label the phase qualified until exact-head Foundry/CI evidence and the chain-specific deployment proofs below are recorded.

## Security property

`AssetVault420` accepts `authorization_` at constructor time and stores it as an immutable contract reference. For a CMP-dedicated Vault, this MUST be the address of `CMPVaultAuthorization420`, **not** the generic `VaultAuthorization420`. The CMP policy inherits the canonical shared grant check but additionally requires `sealed`, `msg.sender == boundVault`, exact `cmpVaultId`, `principal == fundingAdapter`, and action CREATE or RELEASE. It rejects CANCEL, generic/route WITHDRAW, delegated CLAIM and all other Vault action requests. A new arbitrary grant issued by `CapabilityRegistry420.componentAuthority(COMPONENT_VAULT)` or by a rotated registrar cannot satisfy the independent CMP restrictions; the grant is necessary but not sufficient. An ordinary beneficiary's direct immutable-beneficiary `AssetVault420.claim()` needs no privileged grant and remains possible when claimable.

Policy bindings are written only once, before sealing; they cannot be reassigned after sealing. Until sealing all privileged actions fail closed. The funding adapter may CREATE only the exact amount of the signed payer's atomic native deposit and may RELEASE only the original payer-beneficiary obligation of an expired job still in CREATED/FUNDED state, with exact immutable job/beneficiary/amount checks; release makes refund claimable, not externally paid. It has no CANCEL or WITHDRAW operation. The feature branch's former generic-Vault real-registry attack reproduction remains intentionally valid *for an incorrectly constructed generic Vault*, and must not be mistaken for an attack against the sealed dedicated policy.

**Residual policy/grant risk:** the component authority can revoke the funding adapter's CREATE or RELEASE shared grants and block further funding or refunds. A governance protocol without bounded, audited revoke/change controls does not establish uninterrupted payer exit. The policy also presently denies VaultRegistry state-management actions because its authorization is CMP Vault-entry-scoped. This limits the initial V1 topology: do not deploy real-value jobs until a narrowly scoped, tested emergency freeze/wind-down and grant-revocation recovery policy exists without adding an unrestricted payer-credit spending route. Sealing prevents code/policy address replacement, but it does not make the general shared capability registry itself immutable or revoke-proof. Historical direct-custody deposits are never migrated by this construction.

## Exact deployment order (new dedicated Vault, no fixed Genesis address)

1. Select network and chain ID; inventory canonical `CapabilityRegistry420`, `VaultRegistry420`, `VaultAccounting420`, approved policies, registrar/component authority, authorized deployment signer and any existing CMP Vault/service registration. Establish the exact code hashes and operational governance controls. Do not reuse a pooled general-purpose Vault.
2. Deploy `CMPVaultAuthorization420(sharedCapabilityRegistry, cmpVaultId)`; verify its source/runtime code hash, immutable shared registry, vault ID and deployer. Deploy/verify a `VaultRegistry420` whose constructor authorization is **this CMP policy** (not a separate generic authority), and the corresponding accounting/policy references. If canonical registry/accounting must be shared rather than dedicated, first verify every caller's authorization and registration constraints; do not substitute unexamined deployed addresses.
3. Deploy `AssetVault420(cmpVaultId, registry, cmpPolicy, accounting, registrationCreator)` and register it with approved policies; require `vault.authorization() == cmpPolicy`, `vault.vaultId() == cmpVaultId`, `vault.registry() == registry`, `vault.accounting() == accounting`, `registry.getVault(cmpVaultId).vaultAddress == vault`, and ACTIVE state. The registration creator must match the actual caller.
4. Deploy fresh dual-signed request authority and `ComputeEscrowFunding420(requests, vault)`; deploy a *new* `ComputeJobRegistry420` with that funding address and matching request evidence; call `funding.bindJobs(jobs)` and verify both immutable evidence endpoints. Never reinterpret existing `ComputeJobPayerCustody420` balance as Vault funding.
5. Call `cmpPolicy.bindVault(vault)` and `cmpPolicy.bindFunding(funding)` using its deployer; verify code and immutable topology, then issue ONLY the funding adapter's vault-scoped CREATE and RELEASE shared grants under controlled governance. Check grants' component, action, scope, principal, limits, validity, revocation and active ID. Call `cmpPolicy.seal()` once; verify `sealed()` true and that no route withdrawal/third-party release/cancel grants can override the CMP policy, even if the component authority later issues them.
6. BEFORE live deposits, qualify emergency/grant-revocation recovery, a real payer-refund claim (including expired unmatched), hostile grants, second-payer isolation, ACTIVE/FROZEN/WINDING_DOWN behaviour, monitored authorization history and a controlled no-privilege-expansion operational policy. Explicitly decide how a deployed Vault may be frozen without opening release/cancel/withdraw grants to outsiders. Record all addresses, transactions, code hashes, configuration revisions, grant IDs and named exact-commit CI/Foundry results.
7. Only after the above and separately qualified settlement/dispute routes, apply for authorized CMP service publication via the canonical ProtocolRegistry. There is no automatic fixed Genesis predeploy or paid-job activation from merging this PR.
