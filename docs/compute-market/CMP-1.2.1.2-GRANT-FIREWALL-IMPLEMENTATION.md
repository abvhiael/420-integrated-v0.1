# CMP-1.2.1.2 — CMP Vault grant-expansion firewall implementation

Status: **security fix candidate, NOT deployed, NOT funding-qualified**. Draft PR #371. The unrestricted generic Vault-authority configuration in `ComputeEscrowRealCapability420.t.sol` remains an intentional vulnerability-reproduction fixture and MUST NOT be used for actual CMP custody.

## Problem and code-level mitigation

`CapabilityRegistry420` lets the current `COMPONENT_VAULT` authority create a new grant for a second principal; `VaultAuthorization420` ordinarily recognizes a correctly scoped grant. A generic Vault then allows the freshly authorized party to release or cancel a pending payer safety obligation, or exercise separately granted withdrawal rights. The payer credit may become claimable or unencumbered *before* an approved settlement/refund. Monitoring and incident response after the call cannot prevent this.

New `contracts/src/compute/ComputeEscrowVaultAuthorization420.sol` is a dedicated authorization implementation with ABI selectors compatible with the generic Vault's `isAuthorized`, `isRouteAuthorized`, `scopeForVault`, and `scopeForRoute` calls. It is intended to be passed **at construction** as the authorization address of the newly registered CMP-dedicated `AssetVault420` (and through its `VaultRegistry420`). Its immutable `protectedVaultId` is the only Vault ID to which these extra restrictions apply; it forwards other Vault scopes to the existing registry. It is **not** a generic registry-wide denial of Vault privileges.

The CMP-specific fence checks the principal and action *before* asking the actual capability registry: pending unfrozen bindings allow no protected-Vault capabilities; after one-time irrevocable `freezeBindings` by the frozen binding authority, CREATE permits only the funding adapter or settlement controller, RELEASE/CANCEL only the controller, and self/route WITHDRAW and delegated CLAIM never authorize. Ordinary beneficiaries retain the Vault's existing direct `claim` path for already claimable obligations. Grant issuers, registrar rotation and arbitrary new grants cannot bypass this on-chain action check. Vault lifecycle/metadata actions continue through ordinary component grants; they do not themselves transfer pending CMP balances.

**Important binding and exit restrictions:** `freezeBindings` checks two distinct deployed contract addresses and freezes them but does not yet prove their bytecode, registry linkage or safety. The test `EscrowFenceActor420` controller is a *capability plumbing fixture*, not a job-aware verified earnings or lawful-refund controller. Do NOT bind this fixture, an arbitrary operator contract, or the old unrestricted authorization to real payer assets. Before live funding, the qualified production controller must check immutable original payer, canonical job status, accepted match and dispute/timeout policy, and guarantee a reachable lawful payer refund. The funding adapter must be verified to point to this same registered protected Vault and the frozen binding must equal the verified adapter/controller addresses. Reject the deployment unless its `vault.authorization()` points at this fence, `protectedVaultId` matches, and all immutable account/registry/Vault identities, bytecode hashes, and refund paths have been independently checked. Existing generic-Vault CMP funding fixtures are test-only legacy paths.

## New adversarial executable evidence

`contracts/test/ComputeEscrowVaultAuthorization420.t.sol` runs the **real** capability registry, Vault registry/accounting and Vault implementation with the CMP-specific firewall. It tests that unfrozen authorization cannot create obligations, that two pending payer-specific safety obligations remain backed, that correctly issued hostile CREATE/RELEASE/CANCEL/WITHDRAW/CLAIM and recipient-route WITHDRAW grants cannot bypass the fence, that the funding writer has no RELEASE privilege, and that the binding cannot be changed after freezing. A bound dummy controller demonstrates only that the necessary authorization plumbing is possible; it is not evidence of correct refunds. The predecessor `ComputeEscrowRealCapability420.t.sol` demonstrates the old generic configuration's vulnerability and is retained as a negative control.
