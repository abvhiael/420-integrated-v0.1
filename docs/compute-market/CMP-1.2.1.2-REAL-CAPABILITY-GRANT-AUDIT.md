# CMP-1.2.1.2 — Real capability, payer-isolation and grant-issuance audit

Status: source audit and deployment-realistic Foundry fixture added to draft PR #371. **NOT operationally or testnet qualified**: the real capability registry permits its authorized component authority to issue a fresh action grant to an arbitrary principal. No actual deployment, current grant inventory, independent grant firewall, completed settlement/refund exit, or real-network funding is represented by these findings. The five original funding tests and their exact-run evidence remain in `CMP-1.2.1-VAULT-PAYER-FUNDING-QUALIFICATION.md`.

## Verified source and configuration semantics

- `contracts/src/system/CapabilityRegistry420.sol`: `componentRegistrar` begins as deployer. Only that registrar can `registerProtocolComponent(COMPONENT_VAULT, authority)`, subsequently `updateProtocolComponentAuthority` or transfer the registrar. The registered `componentAuthority[COMPONENT_VAULT]` may call `createGrant` for *any* nonzero principal, action ID and scope hash, subject to generic argument validation; it may `revokeGrant`. Active grants are keyed by `(principal, componentId, actionId, scopeHash)`. Creating another grant for the same exact key revokes the prior one; it does not revoke unrelated principals. `validUntil == 0`, `perCallLimit == 0` and `periodLimit == 0` are supported unlimited settings. There is no Vault-specific list of approved principals and no requirement for timelock, separate multisig, code-hash approval or challenge period in `createGrant` itself.
- `contracts/src/vault/VaultAuthorization420.sol`: Vault action scopes are `keccak256(abi.encode(vaultId))`; withdrawal route scopes separately bind `(vaultId, asset, recipient, actionId)`. There is no CMP obligation/job identifier in release/cancel authorization.
- `contracts/src/vault/AssetVault420.sol`: CREATE, RELEASE and CANCEL trust the matching action capability. `withdraw` permits an authorized self-withdraw from global free balance or recipient-scoped route withdrawal. Claim transfers only to the immutable beneficiary, although a grant can delegate who triggers it. `releaseObligation` makes the *entire* safety obligation claimable, allowing the payer to withdraw it before the permitted job outcome. The fact that early payout goes to the original payer does not make it authorized: it can invalidate backing for a matched job.
- `contracts/src/compute/ComputeEscrowFunding420.sol`: the pending full-amount safety obligation ensures no ordinary Vault free balance remains from a newly admitted payer deposit and the adapter itself exposes no release/cancel/withdraw method. `funded()` fails after a grant-expanded principal releases or cancels that pending obligation; this is detection **after** monetary state was already affected, not prevention of an externally granted Vault operation.

**Finding CMP-1.2.1.2-GRANT-001 (deployment blocker):** Giving the CMP dedicated Vault's actual registry component authority the unrestricted generic `createGrant` power leaves the authority capable of granting another principal RELEASE or CANCEL for existing payer-safety obligations. Existing funding tests deny this power to outsiders only because the fixture never issues the conflicting grant. Off-chain monitoring of `CapabilityGranted` cannot atomically stop an already executable unauthorized release; pausing new job funding after detection does not recover prematurely claimable or cancelled balances. A deployment-safe policy must prevent unauthorized grant issuance or prevent dangerous grants from authorizing CMP Vault operations at the on-chain check boundary, not merely promise to monitor them.

## New executable evidence (pending exact-run log confirmation)

`contracts/test/ComputeEscrowRealCapability420.t.sol` deploys the **actual** `CapabilityRegistry420`, `VaultAuthorization420`, `VaultRegistry420`, `VaultAccounting420`, `AssetVault420`, policy registry, jointly signed payer/owner request authority, funding adapter and newly bound job registry (test local addresses, no deployed Genesis claim). It verifies:

1. Two distinct owner/payer signatures fund distinct jobs with actual native value into the same real Vault, with two pending payer-beneficiary obligations, zero unallocated free balance and each job's own `funded()` proof.
2. An arbitrary outsider cannot call the real registry's `createGrant` or the Vault's release/cancel/withdraw methods without a matching grant.
3. The properly registered component authority **can** issue a competing principal a real RELEASE grant; that principal can release an existing payer's safety obligation and invalidate that job's original `funded()` evidence. This deliberately *passes only when the actual underlying vulnerability is reproduced*. It is a negative security finding, not a qualification success or an instruction to grant this capability in deployment.

## Required change before operational qualification and any actual payer deposit

Establish a deployable, non-bypassable CMP-Vault-specific authorization boundary: the canonical Vault's actual `VaultAuthorization420` must resolve through a capability policy which **rejects** CREATE by anyone except the frozen and verified CMP funding/settlement services and rejects RELEASE/CANCEL of payer safety reservations except a separately qualified, job-authorized settlement/refund path. A generic Vault-wide grant from an otherwise authorized registrar or component authority must not override this fence. A naive irrevocable denial of every RELEASE/CANCEL action is also unacceptable: it would lock payer deposits permanently and prevent authorized refunds. Design the settlement path and recovery route together, including how their code hashes and immutable beneficiaries become fixed before actual value enters the Vault.

Re-run the same hostile scenario through that real fenced authorization boundary, then assert that newly issued rogue grants cannot release or cancel either payer's obligation, cannot create unrelated obligations against CMP payer assets, cannot withdraw native funds, and cannot redirect the original payer. Include registrar transfer/authority rotation/grant revocation, native donor surplus, other-Vault scopes, frozen/winding-down Vault states, payment denial, and two-payer conservation. A failed refund-exit or missing authorized release path must block actual funded deployment even if the safety fencing test passes.

Before registration/activation, record the network and chain ID, exact independently verified contract addresses and runtime hashes for registry, authority, actual grant policy, Vault, accounting, signed request, job registry and adapter; immutable Vault ID and policies, current grant IDs/principals/scopes/limits/time windows, component registrar and protocol authority, governing upgrade/timelock/emergency authority, deployment transaction, payer refund exit and proof no historical direct-custody balance has been imported. Verify the published registry entry is authorized and points to the checked deployment. No such deployed evidence exists in this PR.

**Disposition:** Leave PR #371 draft and paid-job admission/deployment blocked. The original CMP-1.2.1.1 funding-suite gate is closed; the 1.2.1.2 security/operational gate must remain OPEN until a tested on-chain authorization fence and authorized refund route supersede the source-confirmed grant-expansion vulnerability. Do not advance to price-based reserved execution on the assumption that mock grants imply immutable real custody authority.
