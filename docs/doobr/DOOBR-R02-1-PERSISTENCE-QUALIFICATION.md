# DOOBR R02.1 — Postgres/PostGIS, isolation and encryption/retention qualification
Status: IMPLEMENTED, Level 1 CI pending. Canonical step unchanged: **R02.1 Postgres/PostGIS schema, migrations, tenant isolation, encryption/retention.** PR #601, starting main baseline `c5a4f220d1fbda01f707d359aa9bb32921a138b1`.

## Implemented assets
- `doobr/storage/migrations/0001_initial.up.sql`: PostgreSQL 15+ and PostGIS 3.x schema, regions as validated multipolygons in SRID 4326 with GiST geospatial index; tenant/actor/order relationships, private delivery payload, custody evidence, authoritative policy reference and retention audit. Composite foreign keys bind related records to same tenant. No retail price or regulated transaction settlement/dispatch engine is implemented by these tables.
- `0001_initial.down.sql`: **destructive, development/test-only** schema rollback, prohibited on production with regulated evidence. Production migration rollback requires backup/restore and legal hold policy, R02.12 and R05.6.
- FORCE ROW LEVEL SECURITY on all eight tenant-bearing business tables with deny-by-default absent tenant context; schema/table PUBLIC access revoked. App runtime must use an unprivileged **non-owner** role without BYPASSRLS, and a trusted server must bind `SET LOCAL doobr.tenant_id` to independently validated session/tenant membership inside the transaction. **Custom PostgreSQL GUCs can be changed by an untrusted database principal.** RLS alone therefore does not provide tenant authentication; granting direct untrusted DB connections or allowing callers to choose arbitrary tenant context is forbidden. R02.2 must implement authoritative identity-to-tenant binding before any production exposure.
- `doobr/storage/crypto.py`: encrypted byte payloads with AES-256-GCM, fresh 96-bit nonce, authenticated `tenant_id + order_id + purpose` binding. External KMS must provide and rotate 256-bit key: no static key in repo. Versioned key IDs are present in schema; the cryptographic routine does not implement a production KMS service or key escrow.
- `doobr/storage/tests/r02_1_rls.sql`: actual PostGIS/SQL schema, unprivileged tenant RLS visibility and wrong-tenant INSERT rejection checks.
- `doobr/storage/tests/test_crypto.py`: encryption, randomization, wrong tenant/order/purpose/key and ciphertext corruption tests.
- `.github/workflows/doobr-r02-1-level1.yml`: exact-SHA test job with isolated PostGIS/Postgres service, AES-GCM Python tests, schema migration, tenant RLS test, destructive test-only down/up migration.

## Retention design and legal hold boundaries
`private_delivery_data` and `custody_evidence` have per-record `retention_until` and `legal_hold` fields. No application can bypass approved legal retention by automatically running expiration delete. `retention_audit` records authorized disposition as a tenant-bound and RLS-protected table. **Automated purge, legal hold authority, data-subject workflows, DB recovery and encryption key rotation are not built in R02.1**: R02.12, R05.2/R05.6 and actual qualified counsel-backed retention schedule own these operations. A clock-expired record is not legal authorization to delete it. Until an approved policy/retention worker exists, records are held in restricted storage rather than silently purged; future deployments must remain disabled.
