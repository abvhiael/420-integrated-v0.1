## Transaction admission implementation update
`doobr/admission.py` now provides a transaction-scoped admission operation for an already-created DRAFT order, using tenant-local PostgreSQL context, locked order and retailer evidence rows, authoritative licence and seller/prepaid checks, unique payment/order reference constraints, and a single committed transition to `ELIGIBILITY_PENDING` (not legal ELIGIBLE). The caller must already have authorized the exact retailer/order action through R02.2; this module checks tenant/actor session binding but does not itself verify a signed session. `test_admission.py` covers an isolated transaction double for successful admission, replay, stale/foreign session denial and issuer outage. Those doubles do NOT substitute for real PostgreSQL concurrent transaction, rollback, actual retailer service or real Pay integration evidence. Additional persistent PostgreSQL multi-session tests and actual approved service bindings remain open. Never activate a real order handler on this basis alone.

## External transport and concurrent-transaction implementation
`doobr/authority_clients.py` implements independently configured HTTPS Bearer-authenticated service requests for retailer licence status and prepaid order confirmations. Endpoints require operator-provisioned issuer identity and scoped credentials. Response scope, status, timestamps and transaction references are checked; failures deny. These clients do **not** certify that any retailer regulator, municipal government, payment provider or operator has approved a deployed endpoint, nor do they independently attest to mTLS, provider signatures, finality or credentials. Provider selection, credentials, operator acceptance and independent signature/revocation validation remain unresolved deployment gates.

`doobr/storage/tests/test_pg_admission.py` exercises real PostgreSQL concurrent attempts using restricted non-owner credentials and verifies unique payment/order references with rollback on denial. Admission uses serializable isolation and DRAFT order row locking; external approvals checked within the DB transaction. The current public API still needs signed R02.2 session verification and approved 420Compliance authorization before invoking admission. Exact-SHA target CI must be confirmed after final commit. This remains repository-side integration, not production-operational qualification.
