# DOOBR R03.6 — Retailer intake, dispatch and exception management

**Scope and status:** App-scoped Level 1, exact-SHA CI pending. PR #601, branch `roadmap/doobr-bc-vancouver-infrastructure`. Main snapshot at inspection `fe21ef07359d6915bf5daac37c4bf24a24fcf19b`. R03.6 is the canonical retailer client step; Level 2 remains R03.12 and comprehensive Level 3 R05.10.

## Delivered
- `doobr/retailer_queue.py`: signed 420Identity authenticated, tenant-scoped, retailer-owned, read-only order intake, dispatch and exception projection. Requires READ_STORE_ORDER order-specific retailer grant; actor must match retailer ID; query binds tenant, order and retailer; rejects unknown states, bad revisions and inaccessible/foreign records. Never claims license verification, prepaid proof, dispatch approval or exception resolution from client input. The UI reports intake needing verified admission and dispatch as operator-controlled, and flags failure/return/dispute states for escalation.
- Canonical seller-of-record licensing and independently verified prepaid evidence stay in `doobr/retailer.py`; authorized dispatch remains `doobr/dispatch.py`; failure and return lifecycle remains `doobr/returns.py`. R03.6 does not recreate or bypass those authorities.
- `web/doobr/retailer.mjs` and accessible site section deliberately reject all claimed order, license, dispatch or exception state from untrusted public input. Public onboarding, order intake and dispatch stay CLOSED/DISABLED without collecting customer/order/license data.
- Negative coverage: `doobr/storage/tests/test_retailer_queue.py` (different retailer, missing order, revoked session, invalid state/revision/identifier, read-only and bound query, exception escalation), `web/doobr/scripts/test-retailer.mjs` (forged licensing/prepayment/dispatch/exception submissions).
- `.github/workflows/doobr-r03-6-level1.yml`: exact-SHA Python and Node tests, affected static build and retained client negatives.

## Explicit limits and acceptance
**This is an authenticated retailer read-model and a safe non-operational website section, not a production retailer portal or completed live retailer intake/dispatch.** Operator control cannot be delegated to a self-attested retailer. Real enrollment, credentials, orders, municipal jurisdiction evidence, live authoritative prepaid proof, operator-approved dispatch, exception workflow/return deadlines, multi-device portal and production deployment remain outstanding and must be accepted in the appropriate canonical workstreams. No external approval can be inferred from CI. Full R03.6 functionality cannot be described as operational or fully accepted until these are integrated and tested. Required targeted CI must be successful before even repository-side qualification can be declared. Preserve R03.12 device/app Level 2 and R05.10 comprehensive Level 3.
