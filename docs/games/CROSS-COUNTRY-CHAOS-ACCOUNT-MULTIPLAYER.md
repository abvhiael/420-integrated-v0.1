# CCC — Online account multiplayer delivery correction

The user-reviewed screenshots of `/classics/cross-country-chaos` showed four entire public seat mats, a handoff prompt and one keyboard. That **was an implementation error in delivery mode**, not a product-approved multiplayer experience. CCC-1 through CCC-6 implement the core **gameplay engine**, but CCC-6's browser-local save did not authorize account-based multiplayer. Preserve its frozen gameplay and assets; do not describe local pass-and-play as satisfying the online objective.

The correction makes this public route an authenticated **420ID account multiplayer room**: host creates private room; each additional human joins from a distinct app-scoped account; 2–4 seats may be mixed with computer players. An independent Node game authority receives a short-lived HMAC-protected assertion from the existing Go Account Social service **after real app-session introspection**, and uses the frozen original CCC engine for rule-governed actions/scoring/bots and a separate cryptographically secure shuffle for each region's card deal, preventing prediction of private hands from the original local 32-bit hazard seed. PostgreSQL persists private state, row locks, membership and turn revisions. The browser receives only the verified viewer's hand and legal actions plus public information. The static site cannot forge a result or read opponents' cards. The former local journal remains a legacy source fixture only and must not authorize the public online route.

The initial replacement frontend deliberately uses a denser single-player layout: minimal full-width game chrome; room lobby, current seats, 2,500km progress, public discard and stage, and a private row of card controls. It removes sidebar/rail clutter on the game route, shows one hand rather than four full physical mats, and offers responsive narrow-device layouts. This is the **delivery correction**, not the final art-directed redesign: actual production desktop/mobile browser screenshots and final spacing/asset choices require acceptance in a separate UI task.

Security and lifecycle gates: real 420ID on every request, exact same-origin protection, non-guessable private room code, outsider 404, blocked peers denied, versioned strictly increasing mutation revision, server-only shuffle/stock, redaction of all rival hands, bounded bot decisions and turn actions, three regional stages, reconnect/restart with server-owned persistence, no wallet requirement, no wagers or 420Bet coupling. A 503/401 failure must never fall back to local multiplayer. Match/room state may not be stored in the account-social browser localStorage. Only server-side admin migrations and least-privilege DB roles may access game secrets.

**Release boundary:** source qualification and PR merge do not deploy the dedicated game server, migration, secrets, Cloudflare worker or production web build. Enable public online play only when the operator deploys and verifies these dependencies and checks two separate 420ID accounts. A user seeing “multiplayer unavailable” during rollout is an honest fail-closed state, not a completed live game. Do not merge without explicit request. No separate BC-0.2 catalogue task has been initiated.
