# Smoke & Chrome — SC-1.6 Stack / Priority System

Status: Frozen for V1 ruleset

## Purpose

SC-1.6 defines the canonical interaction model used whenever players may respond to actions or triggered effects. It establishes deterministic priority ownership, pass semantics, Stack resolution, trigger ordering, and the narrow classes of effects that may resolve outside the Stack.

## Core rule

Smoke & Chrome uses one shared LIFO Stack.

Unless a rule explicitly says otherwise, a card play, activated ability, or triggered ability that can be responded to is placed onto the Stack as a StackObject and does not resolve immediately.

The top StackObject resolves only after both players consecutively pass priority without adding anything new to the Stack.

## Priority owner

At the start of each priority window, priority is granted to the active player unless the rules explicitly assign it otherwise.

After a player adds a new StackObject, that same player receives priority again.

Whenever the top StackObject resolves, priority returns to the active player before any further automatic phase progression.

## Pass semantics

Passing priority does not end a phase by itself.

A consecutive-pass pair means:

- if the Stack is non-empty: resolve the top StackObject;
- if the Stack is empty: close the current priority window and continue the phase/step state machine.

Any legal action that adds a StackObject resets the consecutive-pass count to zero.

## StackObject model

Every StackObject MUST contain enough canonical data for deterministic replay, including at minimum:

- stackObjectId;
- controllerPlayerId;
- sourceObjectId or explicit synthetic-source marker;
- effectId / abilityId;
- legal targets, choices, and values locked at creation time where required;
- creation sequence number;
- provenance event/action id.

The client must never be the authority for Stack ordering or legality.

## LIFO resolution

The Stack resolves last-in, first-out.

Only one StackObject resolves at a time.

After resolution completes:

1. apply all resulting state mutations atomically;
2. perform required state-based checks;
3. collect newly triggered abilities;
4. enqueue/order those triggers according to the trigger-ordering rules below;
5. evaluate terminal game conditions at the authoritative boundary defined by SC-1.1 / SC-1.3;
6. if the game remains active, grant priority to the active player.

The engine MUST NOT recursively auto-resolve the next StackObject without first reopening priority.

## Triggered abilities

Triggered abilities may be generated by any deterministic state transition.

Triggers created during resolution do not interrupt the resolving StackObject.

They are collected into a pending-trigger batch and placed onto the Stack only after the current StackObject has finished resolving and mandatory state-based checks have completed.

### Simultaneous trigger ordering

When multiple triggers are created from the same atomic event:

1. active player orders all triggers they control;
2. non-active player orders all triggers they control;
3. the active-player group is placed onto the Stack first;
4. the non-active-player group is placed above it.

Because the Stack is LIFO, non-active-player triggers will normally resolve before active-player triggers from the same simultaneous batch.

Within a player's trigger group, the controller chooses the order unless a card/rules effect specifies otherwise.

If a controller fails to submit a legal ordering before timeout, the authoritative engine applies deterministic fallback ordering by stable trigger identifier / creation sequence.

## Target legality and fizzle behavior

Targets are validated when a StackObject is created and again when it resolves.

If some targets become illegal, the effect resolves against the remaining legal targets where its rules allow partial resolution.

If all required targets are illegal at resolution time, the StackObject resolves with no effect and is considered fizzled.

Costs are not refunded merely because an effect fizzles unless the effect explicitly says otherwise.

## Copies

Copying a StackObject creates a distinct new StackObject with its own id and creation sequence.

A copy preserves the copyable rules/effect payload of the source StackObject but is not the same game object and does not inherit non-copyable external provenance such as collectible edition/printing ownership.

## Countering

A counter effect removes the target StackObject from the Stack without resolving it.

The countered StackObject then transitions according to its source/type rules, normally to Discard if it originated from a played card.

Countering does not roll back costs already paid.

## Effects that do NOT use the Stack

Only narrow mandatory engine operations may bypass the Stack in V1:

- state-based checks;
- terminal game evaluation;
- deterministic cleanup mandated by zone/attachment rules;
- resource/limit normalization that is explicitly defined as state-based;
- phase/step transitions themselves;
- replacement effects that modify an event before it occurs.

These operations are not player actions and do not create independent response windows unless another rule explicitly creates one.

## Replacement effects

Replacement effects do not use the Stack.

They modify or replace an event before that event is committed.

If multiple replacement effects could apply to the same event, the affected object's controller or affected player chooses among legally applicable replacements unless another rule specifies an ordering.

After one replacement is applied, legality is recomputed before another replacement may apply.

The same replacement effect cannot apply to the same event more than once unless it explicitly says otherwise.

## Mandatory vs optional triggers

Mandatory triggers are always created when their trigger condition is met.

Optional triggers are created in a pending-choice state. The controller must explicitly accept or decline them during the appropriate trigger-placement window.

Declining an optional trigger is final for that trigger instance.

Timeout fallback for optional triggers is decline unless a card/rules definition explicitly specifies a different deterministic fallback.

## No priority during resolution

Players never receive priority in the middle of resolving one StackObject.

All instructions belonging to that StackObject resolve as one rules transaction except where its own text creates a defined delayed effect or future trigger.

This prevents recursive mid-effect response ambiguity.

## Nested decisions

If resolution requires a player choice, the StackObject enters a deterministic suspended-resolution substate tied to that StackObject.

No other player receives normal priority while that required choice is pending.

Choice legality, timeout fallback, and the selected value must be recorded in the match log.

After the choice is resolved, the same StackObject continues resolution.

## Priority windows and phase advancement

A phase/step may advance only when all of the following are true:

- the Stack is empty;
- both players have consecutively passed priority in the current window;
- no mandatory trigger batch is waiting to be placed;
- no mandatory choice or suspended resolution remains;
- terminal evaluation does not end the match.

## Disconnects / timeout

Priority ownership is authoritative server state.

A disconnect does not transfer priority to the opponent.

When a priority timer expires, the authoritative engine submits a PASS for that player unless a tournament/ranked mode rule defines a match-loss escalation after repeated timeouts.

Timeout-generated passes are recorded as explicit authoritative actions.

## Replay / determinism

Given the same initial state and ordered canonical action stream, all Stack behavior MUST replay identically, including:

- StackObject ids / ordering;
- trigger batches;
- priority ownership;
- pass counts;
- target legality outcomes;
- timeout fallback choices;
- counter/fizzle outcomes;
- final state.

## SC-1.6 invariants

### SC-INV-STACK-001 — single shared stack
A match has exactly one authoritative shared Stack.

### SC-INV-STACK-002 — LIFO resolution
Only the top StackObject may resolve or be removed by ordinary resolution.

### SC-INV-STACK-003 — consecutive-pass gate
A StackObject may not resolve until both players consecutively pass without an intervening Stack addition.

### SC-INV-STACK-004 — no mid-resolution priority
Normal player priority cannot exist while a StackObject is actively resolving.

### SC-INV-STACK-005 — deterministic simultaneous triggers
All triggers generated by one atomic event are ordered by the canonical simultaneous-trigger rule.

### SC-INV-STACK-006 — state-based operations bypass stack
Only explicitly defined engine/state-based operations may mutate state outside ordinary Stack resolution.

### SC-INV-STACK-007 — target revalidation
All target-dependent StackObjects revalidate target legality at resolution.

### SC-INV-STACK-008 — paid costs remain paid
Countering or fizzling a StackObject cannot implicitly refund previously committed costs.

### SC-INV-STACK-009 — recorded priority
Priority ownership and every pass/action transition must be representable in the authoritative replay log.

### SC-INV-STACK-010 — wallet neutrality
Wallet linkage, collectible edition, printing provenance, token ownership, or blockchain state cannot alter priority timing, Stack order, response windows, or effect resolution.

## Completion gate

SC-1.6 is complete when the above Stack/priority rules are accepted as canonical V1 semantics and subsequent rules phases reference them instead of defining parallel response systems.
