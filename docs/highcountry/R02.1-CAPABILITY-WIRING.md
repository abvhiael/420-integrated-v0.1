# R02.1 — Five audit fixes and production CapabilityRegistry wiring

Scope: Level 1, real production-contract integration and regression qualification. No deployed production addresses, cumulative budget enforcement or SmartAccount factory attestation are claimed. Original acceptance remains the R02.1 roadmap row. Exact results are in `qualification/R02.1-level1.json`.

## Gap analysis and changes

Five fixes are present: nonzero Genesis admin scope; canonical plant genome at expression; rejection of zero-grower migration receipts; nonzero GenomeRegistry dependencies; session registry must equal trusted HC authorization registry. Their unit regressions exist. The prior production-registry integration checked only Genesis success/revocation/finalization, leaving negative grant and handoff behavior insufficiently demonstrated.

Expanded `RealCapabilityGenesis.t.sol` with 12 production-registry tests for component registration, registrar/issuer/revoker permissions, zero scope, exact component/action/scope/principal/amount, inclusive grant time bounds, replacement/revocation and authority/registrar handoff. Existing five-fix regressions and their affected invariants are retained by the exact-head runner. No production source or frozen ABI/address map changes were necessary for this step.

One initial test-harness defect was diagnosed with a trace: an ADMIN_SCOPE staticcall after vm.prank consumed the spoofed caller before createGrant. Scope is now read before prank; the production registry's authorization behavior was correct. No assertion or production guard was weakened. The first exact-head formatter check also identified use of default formatter settings from the repository root during preparation; formatting was corrected from `contracts/` using the committed Foundry configuration, and the new candidate is requalified.

## Production-contract registration and grants

1. Resolve actual canonical CapabilityRegistry address, code/version, chain and registrar from authoritative deployment records; do not use the test's deployed instance as a production address. Deploy HighCountryAuthorization with that trusted dependency; consumers point to it.
2. Registrar calls `registerProtocolComponent(ModuleIds.<consumer>, componentAuthority)` once for each actual consumer. Protocol component IDs are the exact constants, not contract addresses or wallet component IDs. Registration does not grant any player authority. AUTHORIZATION is an adapter, not a substitute grant component for consumers.
3. Component authority calls `createGrant(grantId, principal, componentId, actionId, scopeHash, perCallLimit, periodLimit, periodSeconds, validFrom, validUntil)` with actual call-site scope and amount. Nonzero ID/action/component/scope/principal are mandatory. A root-setting grant and finalization grant are separate; no implied wildcard action. Production credentials remain protected, never committed.
4. Genesis uses component GENESIS_REGISTRY, actions GENESIS_SET_ROOTS / GENESIS_FINALIZE, scope `keccak256("HC.GENESIS.ADMIN.V1")`, amount 0. Verify all six roots before finalize. Zero scope is unissuable. Finalization permanently disables game Genesis authority; granting again cannot restore it.
5. Other consumers use their own exact action and scope expressions from source and the R01.5 action catalogue. Player-principal grants do not authorize engine→registry calls. BreedingEngine needs its own principal grants for the coordinator/request and genome/child scopes. No blanket scope or all-action grant is authorized here.
6. Per-call limits are checked, but existing HC views do not consume cumulative periodic usage. Do not activate finite-period HC grants before R02.2 defines/enforces consumption or rejects such grants. R02.1 tests do not certify metering.
7. Confirm default denial, exact tuple matches, not-yet-active/expired denial and live revocation at real consumers. Registry validFrom and nonzero validUntil are inclusive: timestamp==validUntil remains authorized; timestamp>validUntil rejects. This differs from some mocks; real registry behavior controls deployment policy.
8. Rotate/handoff with explicit inventory of outstanding grants. `updateProtocolComponentAuthority` changes issuer/revoker authority but does NOT revoke already-issued principal grants. New authority must explicitly revoke bootstrap/compromised grants; old authority cannot revoke after rotation. Registrar transfer independently disables the old registrar. Record transactions, grant state and negative smoke results in R07.
9. Reissuing the exact authorization tuple under a new grant ID revokes the previous active grant. Grant IDs cannot be reused. Verify the new active pointer and revoke the replacement to close the authorization.

Actual addresses, principal custody, founder/root manifests and deploy/seed/grant scripts remain R07 deliverables. This is a verified wiring procedure using actual contract semantics, not a completed deployed rollout.
