# R02.12 — Canonical ruleset and approved module execution

## Deployable artifact provenance
Before registering a module, an independent holder of `MODULE_APPROVE_ARTIFACT` authority scoped to the exact module ID must approve the deployed artifact. `approveArtifact` verifies on-chain code presence, the module's claimed ID/version/ruleset/interface, and that the ruleset is registered in the canonical `RulesetRegistry`. It stores `keccak256(abi.encode(moduleId, extcodehash(implementation), interfaceId, version, rulesetId))`. Registration must reproduce that tuple exactly; an unapproved binary, changed bytecode, changed interface, wrong version or wrong ruleset is denied. Authority grants must not be shared with ordinary module operators.

`ModuleRegistry.bindRulesetRegistry` is a one-time, module-scoped capability-authorized binding. The candidate must implement the canonical RulesetRegistry interface and expose the same authorization root. A ruleset passes only when `exists` is true, `getRuleset` returns a nonzero content hash, and `deriveRulesetId(contentHash)` equals the bound ID. These checks run at approval, registration, activation and executable resolution.

`ModuleRegistry.bindEmergencyState` remains one-time and authorization-root-bound. Only ACTIVE modules whose bytecode and module identity still match the approved record and whose ruleset is still canonical are returned by `activeImplementation`. An unbound or restricted emergency domain fails closed, including at scheduled-to-ACTIVE transition. State history views `getModule` and `implementationOf` are audit-only and cannot justify dispatch.

## Real consumer
`ModuleExecutionGateway.execute(moduleId, callData)` is a production contract enforcing the caller's `MODULE_EXECUTE` capability scoped to `keccak256(abi.encode(moduleId, selector))`, then resolving `activeImplementation` anew immediately before the contract call. It forwards no ETH and bubbles module reverts. It does not permit a synthetic local fallback or raw address override. Do not give wildcard call selector grants. Any future direct-call integration needs separate proof that it enforces equivalent registry checks.

## Required deployment package
For each activated module, the deployment operator must retain: chain ID; network; implementation address; build toolchain and source commit; deployed runtime bytecode hash from `EXTCODEHASH`; approved interface ID and ABI; module ID and version; registered ruleset ID and its content hash; `RulesetRegistry`, `EmergencyState` and `ModuleRegistry` addresses and frozen authorization roots; artifact approval transaction; module registration transaction; qualification/state-transition transactions; and the exact selector grants permitted in the gateway. An independent reviewer must compare the recorded runtime hash against reproducibly compiled bytecode and confirm network-appropriate system address provenance before testnet or production activation.

No testnet deployment address, live network attestation, or independent signer attestation is invented in R02.12 repository qualification. CI only proves the adapter and gateway's on-chain fail-closed behavior with deployed fixtures.

## Qualification
Targeted R02.12 Level 1 includes mismatched ruleset and version, missing approved artifact, code tampering, registered canonical ruleset, scheduled/draining denial, emergency stop/activation denial, permission-scoped gateway dispatch, retained app invariants, compilation, formatting, source and ABI verification. Broader phase Level 3 and live deployment acceptance remain separate.
