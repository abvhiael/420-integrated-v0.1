# R02.12 — Executable module provenance and activation

The `ModuleRegistry` accepts only deployed contracts with a static-callable `highCountryModuleIdentity()` returning the exact registered module ID, nonzero version, ruleset ID and nonzero interface declaration. It snapshots the implementation code hash and declared interface. EOA/empty-code, missing/malformed identity, mismatched versions and rulesets, and arbitrary replacements fail closed.

The existing ordered `PROPOSED → QUALIFIED → SCHEDULED → ACTIVE → DRAINING → RETIRED` states remain authoritative, with rejection paths preserved. No proposed/qualified/scheduled/draining/retired/rejected module is executable through `activeImplementation`. On each active lookup, the registry validates the runtime code hash and identity again; code removal/replacement fails closed. The registry has a separately scoped one-time EmergencyState binding (shared authorization root and module activation domain), and active execution is denied if unbound or the module-activation emergency restriction is active. Activation itself is denied when emergency-restricted.

`implementationOf` and `getModule` remain historical/audit views and are **not safe executable authorities**. Execution adapters must consume `activeImplementation` instead. Existing legacy modules not implementing the new module identity interface cannot be registered as qualified executable modules until adapted and reviewed; do not silently grandfather or infer identity from EOA/module address.

This R02.12 repository implementation does not assert that unrelated consumer services have been rewired, nor that deployed/frozen module binaries have been attested on testnet. R02 Level 1 qualifies module register/activation and direct consumer view; operational deployment and phase Level 3 remain separate.
