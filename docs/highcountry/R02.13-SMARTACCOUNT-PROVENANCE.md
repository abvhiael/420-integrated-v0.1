# R02.13 — Canonical SmartAccount factory provenance and reviewed routine selectors

High Country routine access does not trust an arbitrary contract's self-reported session views. `HighCountrySessionAccess420` binds an immutable deployment-time factory and its entry-point/capability-registry roots. The factory's registry must equal the High Country authorization root. `attestAccount(account, initialOwner, initialRecovery, salt)` requires deployed bytecode, an exact factory `getAddress(initialOwner, initialRecovery, salt)` CREATE2 derivation, and matching deployed account entry point and capability registry. **Do not substitute an account's current mutable owner/recovery for the original constructor arguments.** Factory configuration must resolve to the canonical deployed `SmartAccountFactory420`, with independently checked address/code and Genesis-approved configuration at deployment; a fabricated factory is not valid production provenance.

Unknown, unproven or missing-code accounts are denied session authorization before any account-provided epoch or registry value is inspected. Current authorization/session epochs, account component, full wallet grant and non-periodic limits remain mandatory, and pending wallet recovery fails closed.

An independent `SESSION_POLICY_REVIEW_ROUTINE_CALL` capability first approves the exact target/selector/deployed runtime code-hash tuple. Only after that separate approval may the `SESSION_POLICY_SET_ROUTINE_CALL` authority classify the pair as routine; every check revalidates that the deployed codehash still matches the reviewed binary. An unreviewed or mutated target fails closed.\n\nAdministration may only classify an exact deployed target + selector as routine. The policy forbids classifying SmartAccount execution envelopes, session-grant management, session-key enable/revoke, ERC20 transfer/approval/transferFrom, passkey verifier changes or owner recovery as routine. Unknown selectors, all native value and all non-reviewed calls escalate to Wallet owner/passkey authority. A selector denylist is a second defense; production approval must also audit each proposed target/selector's actual implementation and effects, including asset movement, fee charging, permission/grant mutations and privileged state transitions.

The trusted policy contract is an advisory checker; actual execution must continue using canonical SmartAccount420 and CapabilityRegistry420 grants. Repository tests include a real SmartAccountFactory420 CREATE2 deployment and SmartAccount420 session key/grant lifecycle, as well as malformed/forged account declarations, un-attested accounts, exact session grants, revocation and epoch behavior, malicious selector classification and existing Progressive Session invariants. Production deployment code-hash/Genesis-address attestation, user-device/passkey acceptance and full Level 3 remain later operational gates.
