# R02.2 — Explicit rejection of finite-period HC grants

Chosen canonical alternative: **disallow finite-period HC grants**. HC authorization remains view-only and does not consume cumulative capability usage. This resolves HC-SEC-14 through rejection, not metering. No shared CapabilityRegistry/SmartAccount authority, ABI, frozen namespace or address map is changed.

## Why this boundary

The real registry allows consumption only by its component authority. Existing HC grants identify individual registry/engine components and governance-managed authorities; the generic HC adapter is not their authority. Making the adapter a global issuer/consumer, or changing every view interface to mutations, would silently redesign authority. The roadmap explicitly permits rejection instead. Nonperiodic grants retain scope/action/principal, amount/per-call limits, validity windows and revocation. They do not promise a cumulative spend/call limit.

## Implemented enforcement

HighCountryAuthorization resolves the exact active grant through the existing operational extension, then reads grant metadata. It requires the same principal/component/action/scope, no revocation, and periodLimit==0 AND periodSeconds==0. Missing/zero active ID, malformed/mismatched or unavailable grant metadata fails closed. The registry still decides per-call limits and validity. requireAuthorized calls the same predicate; engine mutators cannot bypass it by invoking the view separately. No fallback to an older nonperiodic grant is allowed when the active grant is periodic.

HighCountrySessionAccess420 independently applies the same period/tuple/revocation checks before its existing exact epoch/selector/zero-value registry authorization. A zero native-value session does not justify periodic grant acceptance: the advisory HC verifier does not consume that budget. Nonperiodic HC sessions still require the existing canonical wallet/registry grants. HC does not modify SmartAccount's own consumption rules for other apps; canonical account provenance remains R02.13.

The frozen base capability interface is unchanged. HC now requires the activeGrantId operational extension already implemented by production CapabilityRegistry420. Deployments with only a legacy yes/no oracle fail closed. Test doubles gain the same tuple-based active lookup; existing amount-specific mock test behavior is preserved. These mocks are not evidence of production registry behavior.

## Grant/operator procedure

Issue HC protocol and routine-session grants with both period fields zero. Use positive bounded expiry where deployment policy requires it, and exact per-call limits where meaningful. Zero perCallLimit means unbounded per-call amount under existing registry semantics; it is not a quota. Never advertise a time window as a cumulative budget. Do not silently convert an existing periodic grant to unlimited: it becomes denied. An explicitly reviewed replacement with a new grant ID and both period fields zero can restore authorization, revoking the previous active tuple under existing registry rules. Preserve player consent and scope.

Registry consumption authority remains the actual component authority; HC receives no new privilege. A future metered design needs its own reviewed consumer/issuer boundaries and atomic rollback/replay/period tests. There is no automatic expiration override, reset or allowance conversion here.

Current HC contract dependencies are immutable. Qualification is repository-side; deployment of the changed adapter/session contract and any required dependency closure follows R01.5 replacement and R07 rehearsal, not an assumed in-place upgrade.

## Proof and scope

- RealCapabilityBudgetPolicyTest: repeated zero-amount mutators/read checks deny periodic grants without changing roots/usage; positive/max amounts deny; old grant cannot be fallback after periodic replacement; explicitly nonperiodic replacement works and revokes; rollover never enables periodic grants; only actual component authority can consume.
- RealCapabilityWiringTest: production per-call limits, wrong tuple/principal, validity inclusivity/expiry, replacement/revocation and registrar/component handoff stay intact.
- HighCountryAuthorizationTest: missing active metadata and malformed one-field periodic metadata deny; nonperiodic behavior remains compatible.
- HighCountrySessionAccess420Test: periodic/malformed grants deny even with zero native spend; valid nonperiodic exact grants still work; forged registry/epoch/revocation boundaries retained.
- All HC suites and immediate Gaming/access/SDK integration are rerun because the central adapter is imported by every HC mutator. This is a material authorization boundary, not ceremonial repository-wide testing. Retained app integration is scoped to existing foundations, not absent gameplay/services.

Exact-SHA commands, raw outputs and results are recorded in `qualification/R02.2-level1.json`. Static findings are reported, not suppressed. Broad/global Solidity, Genesis/address and Docs qualification remain R08 Level 3. No deployment/testnet/production qualification is inferred.
