# R02.5 — atomic mother-cutting consumption during clone issuance

## Canonical requirement

The retained R02.5 roadmap requires clone issuance to spend an actual cutting from a registered, eligible mother. Exhausted, retired, mismatched-genome and mismatched-owner mothers must fail closed. Failed clone issuance must preserve the mother cutting balance and not leave a clone. R02.4 subsequently spends each registered clone at plant admission; these two consumptions are distinct and both must be enforced.

## Authority and consumption

CloneRegistry.registerClone is the only supported clone issuer and requires the existing CLONE_REGISTER capability scoped to the new clone ID. The mother registry is bound to exactly one reviewed CloneRegistry through MOTHER_BIND_CLONES, scoped to BIND_SCOPE = keccak256("HC.MOTHER_REGISTRY.CLONE_BINDING"). Binding is authorized once; trust in reviewed bytecode remains a deployment/attestation requirement. MotherRegistry.consumeForClone is callable only by that bound registry and requires the bound caller's MOTHER_CONSUME_CUTTING capability scoped to mother ID and amount one. No grant to ordinary users burns cuttings directly; legacy consumeCutting reverts.

MotherRegistry checks the bound registry's canonical cloneContext, confirms the recorded mother ID, genome and owner exactly match the mother record, and rejects already retired mothers and duplicate clone links. The current mother holder is required to own the issued clone; trusted registrars cannot silently mint a clone belonging to another owner. Mother transfers change subsequent clone eligibility. Atomic EVM transaction rollback ensures any failed consumer permission, owner/genome mismatch, exhaustion or registry failure rolls back both clone record and cutting count.

The original MotherRecord and CloneRecord shapes and existing lifecycle events remain. Mother.cuttingsTaken increases by exactly one per successfully issued clone; remainingCuttings is maximum minus consumed; reaching max retires the mother. cuttingForClone links the clone to its mother, and CloneCuttingConsumed provides a distinct provenance event. No terminal plant transition restores a cutting or clone.

## Deployment and compatibility

1. Deploy canonical auth, genome registry and mother registry, then clone registry with exactly the same auth/genome and the intended mother registry.
2. Grant the reviewed deployment principal MOTHER_BIND_CLONES with BIND_SCOPE, then call MotherRegistry.bindCloneRegistry(clones) once and revoke that bootstrap grant.
3. Give the CloneRegistry only scoped MOTHER_CONSUME_CUTTING capability for eligible mother IDs (amount one, zero period budgets) and give the authorized issuer scoped CLONE_REGISTER grants.
4. Verify real clone issuance, mother retirement, denied wrong owner/genome/duplicate/exhausted/legacy calls, and capability revocation rollback; retain transaction, code hash, authority and finality evidence in R07/R09.
5. Existing immutable components must be replaced under reviewed migration policy. Previous source-less cuttings cannot be treated as canonical clone issuance. Preserve prior immutable histories.
