# R02.8 — EmergencyState enforcement in mutating engines

Status: **implementation pending; specification of required fail-closed boundary**. This document is not Level 1 evidence.

## Authoritative emergency domains and selectors

Use existing `EmergencyDomains` and `IEmergencyState` without inventing new emergency flags. Emergency restrictions must be consulted by the actual state-changing contract, not only by UI/API/policy. The `EmergencyState.setRestricted` path independently requires scoped `EMERGENCY_RESTRICT` or `EMERGENCY_RELEASE` authorization; domain release does not grant any gameplay capability.

| Domain | Restricted operations | Operations still allowed, subject to original authorization and invariants |
| --- | --- | --- |
| CULTIVATION | New private/public plants, nonterminal growth advancement, offline advancement, environment update and phenotype expression | Existing plant read APIs; an already-READY plant's authorized transition to TERMINATED, releasing occupancy exactly once. No expedited harvest, rewind or product creation implied. |
| BREEDING | New breeding requests | Reads; previously accepted and provably fulfilled request settlement may be considered only after a dedicated reviewed risk assessment. Default deny finalization while restricted until safe-exit semantics are proven. |
| RANDOMNESS_REQUEST | New randomness requests, including engine-mediated requests | Read existing request/result; fulfillment and consumption of an already accepted request remain governed by provider/requester/domain/context/replay authority, and must never create a new restricted breeding commitment. |

Other listed emergency domains have no implemented economic/competition engines to guard in this phase; no claim of emergency protection for nonexistent consumers.

## Required contract wiring and acceptance

- Use one immutable or one-time, strongly authority-bound canonical emergency dependency for every affected engine. Reject zero address, EOAs, wrong authorization, wrong domain and spoofed replacement. A merely unset optional binding cannot be treated as protected production behavior. Source and test fixtures must agree on the approved wiring, with explicit R07 deployment argument/binding updates and code-hash preflight.
- Check the correct domain on **every** entrypoint mutating restricted domain state before any external resource commitment; `syncOfflineGrowth` must also be gated even if it might do zero advances. A successful domain check never bypasses `requireAuthorized`, source approvals, quotas, stage timing, genome rules, one-time consumption or provenance checks.
- For `PlantRegistry.advanceStage`, permit READY→TERMINATED on restriction only with all the current progression/authorization constraints intact. Never allow an earlier stage to jump to TERMINATED. Capacity decrements must remain atomic and exactly once. For any future cancellation/refund method, require explicit separately reviewed authorization and conservation tests.
- `CultivationEngine.updateEnvironment` and `expressPhenotype` fail closed in restricted cultivation regardless of route/ruleset. Pure scoring/view methods remain callable.
- `BreedingEngine.requestBreeding` must fail closed in restricted breeding or restricted randomness-request mode (because it calls `RandomnessCoordinator.request`). `finalizeBreeding` defaults to no child issuance during BREEDING restriction until safe settlement semantics are qualified. R02.9 pending-child reservation/cancellation remains **future**, not an emergency recovery mechanism already implemented.
- `RandomnessCoordinator.request` must reject restricted RANDOMNESS_REQUEST; existing fulfill/consume paths retain exact requester/provider/context/one-time checks. The provider authorization remains essential.
- Release must restore ordinary paths only after explicit `EMERGENCY_RELEASE` authorization, never merely because the caller holds gameplay authority. Existing plant/asset history and pending entropy are not reset by a restriction toggle.

## Level 1 qualification required before marking COMPLETE

Deploy real `EmergencyState` with the same authorization root as affected engines; grant distinct scoped emergency restrict/release principals and scoped gameplay principals. Test unauthorized restriction/release, wrong scope/domain, zero/EOA/mismatched emergency wiring, reentrancy/failure rollback, growth pause and recovery, READY→TERMINATED occupancy conservation during pause, no premature termination, environment/expression denial, breeding request/finalize denial, randomness request denial, existing entropy settlement, no duplicate child/consumption, and successful authorized resumption. Repeat restriction/release toggles and preserve immutable records. Run affected High Country unit/integration/invariant tests, build/format/static lint, source/spec verifier, ABI and constructor compatibility checks and an R02.8-only exact-SHA workflow. Store the job IDs, tested SHA and counts in `qualification/R02.8-level1.json` **only after successful execution**. Do not use skipped Solidity/Genesis global jobs as test evidence.

## Deployment, trust, and explicit limitations

R07 must document constructor or one-time binding changes, full dependency replacement plan and revoke bootstrap grants. Since contracts are not live-qualified, this does not assert any deployed emergency guard. Restrictions cannot safely promise refunds or economic recoveries from modules not yet built. R02.9 owns breeding cancellation/timeout and stranded-resource recovery; R03/R04 own future product/economic exit design. No global Level 3 or merge is authorized by this specification.
