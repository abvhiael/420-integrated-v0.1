# R04.8 production dependencies — engineering vs live-testnet acceptance

**Status: PARTIAL — not production certified.** The R04.8 ordinary internal BUDS market has repository-side qualification, but that evidence does not establish live production safety. This follow-up introduced an explicit `InventoryEscrowAuthority` to check an independently read *locked and finalized* R04.1 escrow receipt against exact registry, chain, issuer, owner, resource, quantity and receipt ID. Caller-supplied receipt fields are not used as authority; guest imports are rejected. The tests are a mocked authoritative reader, **not an actual canonical inventory integration**.

## Outstanding work that must be implemented before production, regardless of testnet

1. **Canonical custody:** R04.1 `InventoryRegistry` exposes an owner-authorized `reserveFor` and `consumeReservedFor`, but does not expose market-settlement transfer of reserved ownership. The ordinary-market import path therefore remains a separate off-chain accounting entitlement. A real canonical escrow/reserve/release/transfer or reviewed proof-of-custody bridge with global receipt consumption must be implemented and verified before market activation. It is UNSAFE to treat an observed reserve as transferable custody or import the same proof into multiple namespaces.
2. **Authenticated service:** compose a real route/worker with independently authenticated registered principals, role/nonce/revocation checks, trusted issuer and receipt verifiers, strict caller ownership, and auditable operations. No `verifyAssetReceipt` function provided by an untrusted caller may be accepted in production.
3. **Consistency across boundaries:** either keep the ordinary marketplace strictly in its own validated internal asset authority, or implement explicit durable cross-ledger intent/outbox, reconciliation, global idempotency and compensation when mixing canonical R04.1 and off-chain BUDS. A database transaction cannot atomically commit an on-chain event.
4. **Catalogue and clients:** approve numerical catalogue data and reward proofs, implement account REST/client integration and reconciliation views, test replay, concurrent buyers and seller cancellations against actual multi-process database and account services.
5. **Separate ecosystem market:** native $420, token custody, player signatures, rights/Pay, fee models, reentrancy and external settlement cannot be enabled via ordinary internal BUDS market. Requires separate approved design, concrete implementation and qualification.

## Live-testnet-gated acceptance (retain for R07)

- Real contract deployment/address-authority and chain finality/reorg/receipt attestation against live canonical state.

The code-only adapter **does not complete** the outstanding dependencies. It improves fail-closed policy and tests; R04.8 cannot be declared fully production-ready until a real authoritative escrow/settlement design is implemented and qualified. ## Repository follow-up: canonical custody and multi-domain settlement implementation

**Implemented after the original dependency analysis, qualification still pending on latest executable SHA:** `ResourceLedger.transferReserved` now provides a one-time canonical handoff of already-reserved units with zero issuance/burn. `InventoryRegistry.transferReservedFor` requires *both* explicit inventory-operator consent and independent `marketTransferOperators` consent. Prior manufacturing operators cannot inherit buyer-transfer power. `CanonicalMarketEscrow` creates owner-signed and quantity-frozen escrow listings, exposes deterministic operation IDs, permits only the configured operator to settle to one buyer, and provides seller cancellation/expiry recovery. Exact-custody Foundry tests include owner consent/revocation, replay, overdraw, conserved totals, unauthorized close and one-time listing resolution.

`CanonicalMarketSettlement` uses persisted BUDS reservation and listing lock before any separate on-chain transaction. Its confirmation path independently verifies the exact finalized transfer, owner, buyer, quantity, asset and original escrow receipt before transferring funds and resolving the local listing. Its cancellation path requires final irreversible on-chain cancellation; pending or ambiguous receipts cannot refund BUDS. Direct local buy/cancel/expiry of canonical escrow-backed inventory is disabled, and seller imports/listings must reference the identical canonical escrow ID. `CanonicalEscrowReader` supports chain-specific contract reads and settled/closed logs with explicit confirmation depths, while `InventoryEscrowAuthority` independently checks finalized locked source receipts. Standalone ordinary internal BUDS listings remain wallet-free and zero-fee. A SQL mock is not evidence of real chain atomicity; **no database transaction can atomically commit an EVM transfer**.

The R04.5–R04.8 Level 2 workflow now includes a disposable PostgreSQL 16 service and actual serializable conflict/replay/persistence/market settlement tests, as well as Foundry market escrow and inventory custody tests. Their latest candidate results must be checked before qualification can be recorded. Production configuration still needs an authenticated service composition, operator-signed chain submission/reconciliation worker, canonical account/address binding, approved business catalogues, local deployable client/service route integration and production-like database authorization tests. These are **pre-testnet engineering obligations** under R04.8/R05, not requirements waived by the live-testnet deferral.

**Genuine live-testnet acceptance** remains: deployed R04.1 + escrow address authority, funded and separately authorized operators, chain finality and reorganization validation, independent Indexer/RPC event reconciliation, deployed PostgreSQL failover/backup and TLS secret rotation, real-user client acceptance, cross-worker fault drills and final security/release approval. All remain OPEN until independently executed.
