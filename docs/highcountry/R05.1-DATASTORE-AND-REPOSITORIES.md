# R05.1 — Datastore and repositories

Qualification is pending actual PostgreSQL Level 1 acceptance. This step is stacked on the recorded R04 Level 3 evidence; it does not merge any R04 PR or alter the canonical sequence. Next: **R05.2 — authenticated API/session/signed wallet linking**.

## Implementation and authority

The shared player-profile service previously provided process-local Maps. That API remains a clearly marked fixture. Production storage is now exposed by `PostgresGamingRepository420` and `createPostgresGamingPlayerProfileService420`; deployments must select the PostgreSQL factory explicitly. The adapter verifies the retained R04 signed `RuntimeAuthority` before and after each transaction and binds issuer, account, game and authentication epoch. No caller-supplied wallet establishes account authority.

| Requirement | Production implementation | Acceptance |
| --- | --- | --- |
| Accounts | Operator-provisioned credential commitment, issuer, active state and revocation epoch; no raw credentials/email | Wallet-free profiles, epoch revocation, sanitized account DTO |
| Game profiles | Compound account/game identity, immutable ruleset and registered-state authority domain | Distinct accounts/games, database RLS and scope forgery attacks |
| Cloud-save references | Immutable opaque provider/object references, exact decimal revisions, approved schema mapping, original references retained | Atomic head/reference update, concurrent compare-and-swap, fresh pool persistence |
| Consent | Purpose, policy/context/nonce commitments, expiry and irreversible revocation | Wrong purpose, expiry, revocation, immutable history and rollback |
| Migration records | Durable scoped source revision uniqueness, exact target intent and terminal cancellation | Idempotent retry, alternate payload conflict, cross-scope denial and no reactivation |
| Schema evolution | Checksum marker, transactional advisory lock, empty rollback; populated rollback fails closed | Concurrent deploy once, empty down/up, drift denial and history preservation |

Database isolation uses operator-provisioned login roles mapped to one account/game. Policies use `current_user`, never request variables. Runtime roles must be nonsuperuser, without BYPASSRLS, migration membership, DDL or deletion authority. All seven privacy tables enforce FORCE RLS and migration-role ownership. An account column UPDATE grant exists solely because PostgreSQL requires it for row locks; an unconditional runtime-update rejection trigger prevents account mutations. Operator role bootstrap separately requires CREATEROLE and database-owner authority to grant schema creation. Runtime credentials cannot bootstrap, migrate, disable accounts, change immutable consent facts or delete replay history.

Transactions use SERIALIZABLE isolation, bounded lock/statement timeouts and explicit retry-required errors. Callers may retry a whole operation; callbacks must not send external effects. Handles close after commit/rollback. Values remain validated decimal strings through uint64/uint32 boundaries; schema labels map through an operator-maintained registry rather than a numeric cast. Private SHA-256 integrity digests do not replace canonical keccak/ABI commitments or signed claims.

## Privacy and deployment requirements

Only opaque IDs/references and commitments are accepted; raw saves, URLs, contact data and credentials are rejected at repository DTO boundaries. No datastore row is sent on chain. The metadata byte-length ceiling is 64 MiB; provider-side object verification, retention, deletion and backups remain R05.5. Deployments must provision isolated roles/pools through a trusted resolver, configure PostgreSQL TLS and secrets, apply migrations with a separate operator identity and explicitly select the durable factory. Per-account/game roles provide strong isolation with an operational scaling cost; pooling must never reuse a differently scoped role. This step adds no public HTTP authentication endpoint or wallet-link signature format (R05.2).

Migration records represent **intent only**, not proven save ownership, applied inventory, consumed claims, grant entitlement or chain finality. Durable migration application, global validated replay authority, outbox, receipts and reconciliation belong to R05.3; real GameClaims/grower binding to R05.4. Cancelled history remains preserved. Populated downgrade cannot silently discard user data: an explicit future reviewed forward migration/export plan is required.

## Qualification cadence

Level 1 runs retained profile tests, input/domain regressions, actual PostgreSQL 16 isolation/concurrency/migration/privacy tests and the directly affected retained runtime-authority suite against one exact SHA. Local embedded PostgreSQL validation is only preliminary SQL validation. Level 2 remains pending accumulated runtime integration; proposed app review gates are R05.3, R05.6 and R05.9, without adding roadmap steps. Level 3 is deferred to complete R05 closeout with reconciliation and the canonical ownership/shard model. No unrelated Foundry/global/Genesis suites are required for this datastore-only Level 1.
