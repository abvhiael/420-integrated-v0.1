## Database authority, migrations and invariants

Use a separately approved migration-owner connection and a non-owner runtime role. Migration takes a transaction-scoped advisory lock, applies ordered files once and records their SHA256 checksums atomically. Runtime checks the exact migration inventory/checksums before operations; altered, missing or unknown ledger entries fail closed. The runtime cannot own schema, create roles/databases or alter the ledger. Table/schema/function privileges are revoked from PUBLIC.

Protected tables:
- trips: bounded IDs, exact snapshot shape, safe revision integer, participant/vehicle relationship and lifecycle constraints; immutable rider/route/trip ID. Insert must be REQUESTED revision zero. Update must advance exactly once through allowed lifecycle. Deletion and terminal resurrection are denied.
- events: append-only snapshots and actor/action/command metadata, unique (trip,revision), previous/event SHA256 links and UTC database timestamps. No signed tokens, raw licences or precise coordinates are stored.
- commands: immutable actor-scoped idempotency keys, request digest, exact committed result and event foreign key. No automatic replay-ledger expiry is introduced.

Partial unique indexes allow only one active assignment per driver and vehicle across ASSIGNED/ARRIVED/IN_PROGRESS. Cancellation/completion release active uniqueness but retain history. Durable available capacity/matching policy is still L01.6.

Runtime grants: USAGE on liftd; SELECT on migrations/trips/events/commands; INSERT/UPDATE on trips; INSERT on events/commands. Do not grant DELETE, schema ownership, trigger disablement, migration writes or arbitrary public SQL access. Approved service processes own database access; HTTP clients cannot supply SQL, credentials or actor authority. Tests create a disposable non-owner fixture role only in database liftd_qualification.

## Atomic execution and exact retries

Postgres store execute() uses one checked-out client for BEGIN through COMMIT/ROLLBACK. No transaction statement is dispatched through random pool connections. Actor/command advisory lock serializes duplicate keys; per-trip advisory lock plus SELECT FOR UPDATE serialize creation/update; UPDATE WHERE revision provides compare-and-swap. Parameterized queries prevent command/ID SQL injection. Hash-lock collisions only serialize more work and cannot merge command identities.

Trip snapshot, next immutable event and command result commit together. Failure before commit rolls them all back. An ambiguous/lost response is recovered by retrying the SAME command key/payload after fresh authorization: one durable prior result, no second mutation/event. Reusing a key for a changed payload/action/trip gives IDEMPOTENCY_CONFLICT. Different keys cannot recreate an existing trip. Keys are scoped by authenticated subject, not request-supplied identity.

Every mutation with this store requires a bounded commandId. HTTP accepts Idempotency-Key header or commandId body; conflicting values are rejected. A key is not a credential. Reads require existing authenticated participant checks and do not bypass protection through the command ledger.

Protected service refreshes authorization after lock waits and again before mutation. Verified subject/account/role must remain bound to the original actor. New-risk eligibility is refreshed in the locked operation and before mutation; expiry/pause/revocation deny new risk. Cancellation/completion keep the existing valid-exit policy. No cached positive session/eligibility approval is used to authorize a retry.

Lock timeout 3s, statement timeout 10s and idle-in-transaction timeout 15s bound failed operations. Pool connects with a bounded timeout and returns/destroys clients appropriately. Database errors produce bounded error codes, not query strings/passwords. Timeouts and lost connections are not silently retried with a new command ID.

## Event verification and restart qualification

history() uses a repeatable-read transaction, verifies contiguous revisions, previous/event hashes and equality of latest event/snapshot. Restricted history is internal; it is not a public trip-history API. A new application process recovers committed state through PostgreSQL, not an in-memory replay map.

Required L01.4 CI uses a real PostgreSQL 16 service. The database suite rejects a missing URL and refuses any database other than liftd_qualification; no skip/fake database can satisfy this gate. Tests use a non-owner runtime role and cover concurrent migration, duplicate requests, changed payload replay, stale revisions, driver/vehicle contention, rollback, immutable history/participants, migration tampering, missing keys, authenticated HTTP retries and new-process recovery.

After the suite, a checkpoint hashes verified trip/event/command state. CI SIGKILLs and restarts its disposable PostgreSQL container, then a new Node process checks the same counts/digest and all event chains. This is database crash recovery qualification, not a production backup/failover certificate.
