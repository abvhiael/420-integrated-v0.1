L01.3 required a server-owned routeScopeFor seam but did not supply actual Location consumption or private endpoint storage. L01.4 persisted opaque route refs only. This step adds a canonical provider consumer, independently signed Location client, encrypted PostgreSQL endpoint storage, authenticated service/HTTP access and retention erasure. No map/geographic/Identity/transport authority is minted by LIFTd.

Native Go bridge rideshare/locationbridge consumes existing location/providers.Adapter.Route and location/geo.Route with required source validation. ScopeResolver must be an approved independent geographic classifier for the complete route, not rider-provided municipality or inferred permission. Gateway request fields map origin/destination latitude/longitude to the canonical RouteRequest; approximate endpoints must already be reduced. Bridge projection omits raw route geometry and preserves the application's opaque routeRef across provider swaps. The approved external gateway binds authenticated rider subject, purpose/issuer/audience, nonce/point digest and signs the projection; this repository does not create its signing authority or deploy a gateway.

Node createLocationRoutingAdapter verifies pinned RS256 Location proofs, max 30-second lifetime and exact nonce/route/rider/normalized point-payload digest. Require available, unambiguous bounded distance/duration, source provider/provenance revision and exact Vancouver passenger scope; reject airport/cross-boundary routes. The existing HTTPS status transport supplies bounded time/payload/redirect behavior. Native Go tests exercise the real canonical provider adapter and retained Location provider/privacy suites; Node tests verify signed consumer behavior.

## Endpoint precision and private storage

POST /v1/rideshare/routes accepts authenticated riderId, commandId/Idempotency-Key, pickup/dropoff objects (latitude, longitude, precision exact or approximate) and passengerCount. Coordinates must be finite and within geographic bounds. Approximate input is rounded to two decimal degrees BEFORE routing or storage; original finer values are discarded. Exact input stays private. Public route preparation response has municipality precision and route/provenance refs plus distance/duration only; no endpoints, addresses or geometry. Do not publish private-route metrics as public user discovery or infer precise residences from other services.

Migration 002 adds liftd.private_locations. Endpoint payloads are AES-256-GCM encrypted with random 96-bit IV, 128-bit authentication tag and AAD binding routeRef, rider/account and fixed expiry. Configure managed 32-byte encryption key(s), active key ID and approved retentionSeconds explicitly; no key or retention default is fabricated. Retention must be positive and no more than the 30-day technical ceiling; that ceiling is not a recommendation/legal retention approval. Keep old approved keys only while needed for still-live payloads; missing/wrong keys fail closed. Production KMS/rotation/backup handling remains independent acceptance.

No coordinates or unkeyed point hashes are persisted in trip snapshots, immutable events or durable trip command ledgers. Location request digests go only to the approved routing gateway; they are not a public index. Preparation retries compare decrypted normalized payload under an actor/command lock; changed payload is denied, expired/purged retries cannot recreate private data. Opaque route refs are generated by the server, not derived from provider IDs or addresses.

## Ownership, access and atomic trip binding

Rider route.prepare is an independently signed exact account resource grant. Preparation reauthenticates around provider/storage waits; signed rider/account binding must persist. Database command uniqueness is rider-scoped. Trip creation binds the private route to the actual rider/account and exactly one trip INSIDE the existing trip/event/command transaction. If binding fails, the trip write rolls back. Client-supplied route refs cannot claim another rider's endpoints or reuse a route across trips.

GET /v1/rideshare/trips/:id/coordinates requires a fresh trip.read grant plus actual current trip state. Rider can read own live retained payload; assigned driver can read only while ASSIGNED/ARRIVED/IN_PROGRESS. Unassigned drivers, other accounts/riders and operators cannot obtain coordinates. Terminal driver access ends immediately. No broad emergency/operator privilege is introduced here; L01.9 owns bounded incident access. HTTP responses are no-store/nosniff, query tokens/proxy roles are rejected and no coordinates are logged by runtime code.

Location service routeScopeFor fetches/decrypts the retained endpoints internally and obtains a fresh signed Location scope for each new-risk eligibility evaluation. Production assembly wires its routeScopeFor into createEligibilityAdapter and supplies privateLocationStore to createTripService. Internal routing/storage methods are server-only capabilities; they must not become unprotected HTTP endpoints.

## Retention and tombstones

Reads, route refresh and binding deny expired payloads immediately even before physical cleanup. purgeExpired clears ciphertext and marks a durable tombstone. Database guards forbid location deletion, participant/expiry/descriptor mutation, trip rebinding, ciphertext replacement and tombstone reactivation. New requests cannot restore a purged route by reusing its old command key. Stable non-coordinate trip/event/command history is retained separately.

Approved operations must schedule `LIFTD_DATABASE_URL=<runtime connection> node rideshare/scripts/purge-locations.mjs`. It validates the migration ledger and erases expired ciphertext without requiring decryption keys; it emits counts only. Repository tests call actual erasure and confirm ciphertext null/irreversible tombstone. Actual scheduler deployment and protected backup-tombstone replay are LT-07; a stale restored database cannot be declared safe solely from these same-database guards.
