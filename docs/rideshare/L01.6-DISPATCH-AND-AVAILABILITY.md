## Gap analysis and adopted repository semantics

L01.3 already enforces independently signed vehicle capacity against the private route passenger count. L01.4 serializes trip writes and prevents simultaneous active driver/vehicle reuse. L01.5 supplies private endpoints and fresh signed Location scope. Missing: durable consent to availability, freshness/CAS/idempotency, deterministic server choice, assignment deadline and concurrent dispatch across instances.

This step adds availability and assignment leases, consuming existing Identity/session/Registry/Location/passenger eligibility without minting any authority. DOOBr dispatch demonstrates transactional row locks, scoped offers and independent capacity admission, but its delivery authority/state is not reused as passenger permission.

A match is an exclusive passenger-trip reservation; no pooling or concurrent seat sharing. Capacity comes ONLY from the current signed Registry vehicle projection, compared to the server-owned private route passenger count at selection and again before assignment/arrival/start. Drivers declare willingness/vehicle, never capacity or geographic/transport permission. No GPS tracking, invented ETA or client-chosen ranking is added. Rank eligible candidates by binary driver ID then vehicle ID, independent of provider/order; selection is deterministic for the serialized current candidate snapshot. This simple rule is the repository pilot matcher, not a claim of shortest pickup or fairness optimization.

Arrival is the existing driver acceptance boundary. The assignment deadline applies to ASSIGNED before arrival. Arrival before the deadline changes the lease PENDING -> ACCEPTED; timeout must not interrupt an ARRIVED or IN_PROGRESS trip. Completion/cancellation close the reservation. Future explicit accept/navigation UX is an L02 owner, and post-accept incident resolution is L01.9.

## Protected availability and matching

Production assembly MUST supply the same durable PostgreSQL pool to trip storage and createDispatchAdapter, the canonical authenticated session boundary, createAvailabilityVerifier with independently approved session trust/HTTPS client, actual signed eligibilityAdapter.project, Location/private storage and protected trip service. Configure availabilitySeconds and assignmentSeconds explicitly, each positive and at most 300; this technical bound is not a live operational approval. Use createHttpHandler(service,locationService,dispatchAdapter). Legacy service assembly without dispatch is only for retained isolated trip/eligibility tests; it cannot execute match/expire. No public listener/deployment is added.

POST /v1/rideshare/availability requires a Bearer credential and independently signed driver availability.set grant for exact account:<driver subject>. Body: driverId, vehicleId, online boolean, expectedRevision, commandId (or Idempotency-Key). Revision starts at 0; first durable row is revision 1. TTL and expiry are server-owned. The authenticated account, session, device, recovery epoch and token digest are stored privately; never store Bearer token or role authority. Each match rechecks fresh independently signed session status, active token/device/recovery binding and exact live availability grant. A stored online flag cannot survive revocation as authority. Offline withdrawal is allowed during pause and busy trips; it stops future matching without invalidating an accepted/current ride. Vehicle changes while busy are denied.

Availability actor/command replay returns the original historical response after fresh authorization and never refreshes TTL or changes current status. A changed payload/account or stale expectedRevision fails. Availability command namespace is separate from immutable trip commands. Responses are own-driver only and no-store; no public candidate-list/private coordinate endpoint exists.

POST /v1/rideshare/trips/:id/transitions with action match, expectedRevision, commandId requires the existing exact operator trip.assign grant. Production dispatch rejects direct assign/driverId/vehicleId overrides. Server reads live online/unexpired availability, excludes self/busy driver/busy vehicle, orders candidates and obtains fresh current session, driver/vehicle and transport/Location evidence. Ineligible candidates are excluded; unavailable authorities fail closed. Selected account must equal independently verified Registry driver account. Response to operator remains id/state/revision only.

## Serialization, leases and expiry

Migration 003 adds driver_availability, immutable availability_commands and assignment_leases; extends append-only event action vocabulary with expire. Existing migrations/checksums are unchanged. Availability account identity/revision and lease identity/expiry/lifecycle are database guarded. Closed leases cannot reopen and their deadline cannot extend. Existing trip/event/command immutable invariants and active driver/vehicle indexes remain.

Availability and dispatch serialize on a Vancouver advisory transaction lock. Trip commands retain actor-key and trip locks; matching reads the candidate snapshot only while holding the dispatch lock. The selected availability revision, account, vehicle, online state, TTL, independent session and current eligibility are rechecked immediately before trip mutation. Trip snapshot/event/idempotent result and lease reserve/accept/close commit or roll back together on one database client. Concurrent independent application processes cannot reserve the same driver or vehicle. No skip-locked nondeterminism or cached candidate authority is used.

At now >= lease expiry, arrival is denied immediately regardless of cleanup. An exact operator trip.expire grant allows action expire with expectedRevision/commandId only for an expired PENDING/ASSIGNED trip; server supplies the deadline to the domain kernel. It writes CANCELLED plus immutable expire event and closes the lease atomically. No re-open/reassignment of the old trip; rider can issue a new request. This pre-trip terminal outcome has no payment side effects. Timeout never cancels an accepted/active ride. Expired reservations continue to block capacity until authenticated expiry/cancellation commits, which favors safety over silent double-booking.

The timeout path is executable through the protected HTTP/service boundary. Approved operations can run it with independently issued bounded operator grants; this step does not fabricate worker tokens or deploy a scheduler. An overdue-worker backlog cannot enable late arrival or duplicate capacity. Live scheduled worker/account/transport acceptance remains LT-07/LT-04. Existing pre-trip rider/driver cancellation and in-progress driver completion remain available during pause/transport revocation.
