# LIFTd L02.1 — application shell and design system

## Scope and authority

Canonical instruction: responsive navigation; accessible components; loading and error states; authenticated routing; clear availability information. This is the first L02 web client, not permission to advertise live rides or payments. The L01 backend is the sole owner of session verification and role authorization; the static client renders navigation only and cannot independently grant service access.

## Implemented

- `rideshare/web/index.html`: semantic primary navigation, skip link, status banner, focused main landmark, menu state and non-live pilot notice.
- `rideshare/web/styles.css`: mobile-responsive navigation, focus visibility, contrast-aware dark/light palettes, reduced motion, generous targets and panel components.
- `rideshare/web/app.mjs`: navigation/history, optional injected independently authenticated `LIFTdSessionAdapter.getSession()`, fail-closed loading/error/sign-in/forbidden states, stale request invalidation, navigation cleanup. No demo credentials, stored tokens, live dispatch controls or fake bookings.
- `rideshare/web/route-policy.mjs`: explicit route allowlist; separate rider, driver and operator roles; revocation and malformed session denials; safe route sanitization and canonical non-live metadata.
- `rideshare/web/test/route-policy.test.mjs`: role-matrix negative/positive tests, revocation, missing credentials, path escape and external redirect handling.
- `.github/workflows/liftd-l02-1-level1.yml`: affected-scope Node 22 qualification, exact SHA checkout and semantic/accessibility structure check.

## Integration and limitations

This is a static application shell; no session service is connected, and protected workspaces remain gated by an independently supplied authenticated session adapter. An injected adapter is trusted to do real session verification and remain consistent with backend revocation; frontend roles cannot replace backend authorization. No actual ride request, driver availability, payment or launch approval exists. Browser-based screen-reader/mobile/keyboard acceptance and a deployed origin require later integration/operational evidence; static structural checks do not constitute independent assistive-technology acceptance.

## Qualification

Level 1: Node syntax, routing authorization regression tests, semantic/accessibility structure checks, exact-SHA CI. Level 2 at canonical L02 cross-app integration milestone. Level 3 at final L02 phase closeout only. CI run outcome and evidence SHA must be recorded after GitHub Actions executes; do not claim PASS from a registered or skipped workflow.
