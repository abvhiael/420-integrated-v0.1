# LIFTd L02.10 — Operator console implementation and qualification plan

**Original canonical requirement:** dispatch monitoring, eligibility status, incident triage and recovery tools with least-privilege access and audited actions.

## Implementation and authority ownership

Concrete read adapters in `rideshare/src/operator-monitors.mjs` retrieve the private PostgreSQL assignment lease and independently recheck Registry/transport signed eligibility via the existing eligibility adapter. Missing runtime owner/keys deny or return explicit UNKNOWN; no browser mock creates a legal eligibility status.\n\nThe LIFTd operator UI at `/operator` is a read-only-by-default, authenticated, redacted console; operator sessions come only from the independent L01 Identity/session authority. No public trip index or operator bypass is enabled. The operator must supply a bounded trip reference and the service uses only current authoritative trip state. The summary omits route, coordinates, contact details, documents, payment and message content. Dispatch/eligibility statuses come from separately injected authoritative read adapters, **not guessed from the browser**.

`rideshare/src/operator-console.mjs` gates monitoring under `operator.monitor` scoped to the exact trip, and incident triage/recovery under existing canonical `safety.read`/`safety.resolve` permissions. Session recovery/device/account binding is checked again across external I/O, with trip revision consistency checks. Unsupported projection values fail closed. The operator cannot create assignments, set driver eligibility or capture payments.

Recovery is restricted to `IN_PROGRESS` and an explicitly selected incident plus expected trip revision, and delegates actual incident existence, transactional compare-and-swap, idempotency, settlement/safety coupling and terminal cancellation to the **existing L01 Safety service**. The console does not create an independent state-mutating service.

`rideshare/migrations/010_operator_audit.sql` creates an append-only private audit ledger. `rideshare/src/postgres-operator-audit.mjs` uses inserted actor/account/trip/action/outcome/time and unique recovery command ID. The ordinary non-owner runtime is granted INSERT/SELECT but denied UPDATE/DELETE, with restricted fields and uniqueness checked in PostgreSQL. All console observations and recoveries are logged through this separate durable owner; production assembly must supply that owner, otherwise the facade fails closed. Safety recovery also retains canonical L01 transactional audit.

`rideshare/web/operator-console.mjs` renders the protected operator dashboard, explicit incident selection and a safety-resolution confirmation UI. All rendering uses textContent, never HTML or private payloads. A rejected/stale request clears displayed confirmation and does not claim operator action success.

## External acceptance and limitations

Independent production operator identity/keys, real dispatch/Registry projections, approved Vancouver driver/vehicle/licence/insurance, real on-call safety staffing, operational backup/recovery, deployed transport messaging, accessibility and incident response are NOT ACCEPTED. Mock/fake adapters in unit tests are test fixtures only; the app fails closed if owner adapters or audit storage are unavailable. Keep `LIFTD-TESTNET-ROADMAP.md` and `L02-PRODUCTION-ACCEPTANCE-REGISTER.md` gates open. Merging repository code does not activate live rides or production operator authority.
