# LIFTd L02.2 — rider account and preferences

**Canonical deliverable:** account/session management, accessibility requirements, communication preferences and privacy controls.

## Authority and integration

The independent L01 Identity/session authority remains canonical: `rideshare/src/auth.mjs` now recognizes the bounded rider `account.preferences` permission and constrains the resource to the authenticated account ID. The preferences service requires an L01-verified principal with matching rider role, action, resource and account ID; missing, revoked, expired or foreign-account permissions fail closed. No additional token issuer or demo credentials are introduced.

The protected HTTP API uses `GET`, `PUT` and `DELETE /v1/rideshare/riders/:accountId/preferences` through `createHttpHandler(..., riderPreferencesService)`. Bearer/session verification remains server authoritative; unknown verbs, credentials and malformed bodies are rejected. The optional service argument must be wired by the deployed host to `createRiderPreferenceService` using its real L01 authenticator and `createPostgresRiderPreferenceStore`. There is no independent running/deployed listener or live Identity acceptance in this development step.

## Rider-facing UX and controls

`rideshare/web/rider-account.mjs`, `preferences-api.mjs` and `preference-policy.mjs` extend the protected rider workspace: accessible labeled checkboxes and contact selection, status/live-region messaging, loading/error/denied states, read/save/erase controls and stale-revision rejection. The browser adapter makes same-origin, no-store, cookie-free requests with a fresh ephemeral access token from the approved session provider; no token is persisted to local storage or put into query strings. The application remains visibly a non-live preview until deployed authority and approvals exist.

Default-off preference fields:
- Accessibility: large text, reduced motion, screen-reader hints.
- Communications: none/email/SMS contact method, opt-in trip messages and opt-in marketing consent.
- Privacy: opt-in location-history retention, disabled by default.

Unknown/accessor-backed fields, invalid option values, malformed commands and incompatible contact/notification settings are rejected. Browser input validation is advisory; server validation is authoritative.

## Durable storage

`rideshare/migrations/007_rider_preferences.sql` creates the account-keyed private JSONB preference table with positive monotone revision. `rideshare/src/postgres-rider-preferences.mjs` implements parameterized atomic insert-on-first-write and conditional SQL updates on subsequent revisions; concurrent stale writes fail, and erasure clears preference content while advancing a tombstone revision so stale writes cannot resurrect erased consent. No preference payload is put on-chain or in trip events.
