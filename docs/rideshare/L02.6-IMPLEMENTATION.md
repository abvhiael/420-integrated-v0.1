# LIFTd L02.6 — Driver onboarding

Canonical scope: driver/vehicle submission, eligibility status, document lifecycle and remediation, with sensitive onboarding material outside public discovery.

The scoped implementation adds a signed-session `onboarding.manage` driver capability, `GET/POST /v1/rideshare/drivers/:driverId/onboarding` and a role-protected driver form. Submissions contain opaque private-upload references only; raw document bytes are never accepted by these interfaces, returned in browser status, logged to client storage or exposed through public trip/discovery. The driver cannot grant eligibility to themselves. States include PENDING, REVIEW_REQUIRED, REMEDIATION_REQUIRED, APPROVED, REJECTED and REVOKED, with document expiry and remediation summaries projected on authorized reads. Re-submission uses server-side revision/command idempotency through an injected confidential store contract.

**Important integration gap:** No durable encrypted/segregated document storage, authenticated reviewer/transport-authority approval API, or actual document-upload issuance service is supplied by L02.6. The injected store must provide transactional compare-and-swap and role-scoped private reads and be connected to an approved private document vault; a test in-memory fixture is not a deployed backing system. External approval remains solely with the L01 Registry/transport eligibility authorities; this UI cannot admit vehicles, override revocations or begin dispatch.

Level 1: Node syntax, account/role denial, malformed/expired/duplicate document metadata, redacted projections, stale command replay, protected driver UI and retained web/auth regressions. Level 2: confidential vault, operator review and Registry/Compliance integration, including real document lifecycle and remediation acceptance. Level 3: complete L02 current-main reconciliation and repository-wide owner qualifications once at phase closeout. External transport and live-driver approvals remain uncaptured.
