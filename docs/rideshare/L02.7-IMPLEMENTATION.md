# LIFTd L02.7 — Driver availability and offers

**Canonical:** Online/offline controls, availability freshness, offer countdowns, acceptance/rejection and capacity constraints, safe recovery from disconnects.

## Current implementation

`rideshare/web/driver-availability-policy.mjs` validates server ownership, states, revision, deadline, and bounded passenger capacity. `driver-availability-controller.mjs` enforces no actions while disconnected, single-flight operation, exact command IDs, authoritative server-read refresh after uncertain responses, expiry at decision time, and does not infer acceptance from a successful command response. `driver-availability-api.mjs` uses same-origin ephemeral bearer authentication, and `driver-availability-view.mjs` provides keyboard-accessible controls, explicit online/offline states, expiring countdown, accept/reject choices, error/refresh states and disconnect recovery. The protected driver workspace mounts this UI without reporting live dispatch.

## Repository gap discovered

Canonical L01 `dispatch.setAvailability` already provides signed session authorization, PostgreSQL revision/CAS, 1–300 second freshness, disabled-while-paused, active-trip vehicle-change exclusion, independent session/eligibility checks and safe assign capacity. It exposes **POST /v1/rideshare/availability**, but not **GET /v1/rideshare/drivers/:driverId/availability**, **GET /v1/rideshare/drivers/:driverId/offers** or **POST /v1/rideshare/drivers/:driverId/offers/:offerId/response**. Current assignment leases are PENDING/ACCEPTED/CLOSED, and `arrive` transitions the lease to ACCEPTED; reusing `arrive` to mean offer acceptance would incorrectly advance the trip lifecycle. A new independent authoritative offer read/accept/reject contract is mandatory, with signed grants, driver/vehicle account binding, capacity, lease expiry, stale revision, concurrent winners, decline/redispatch and replay consistency. **The frontend must remain fail-closed until that contract exists.**

## Verification and exit criteria

Level 1 client tests exercise expired offers, cross-driver responses, capacity bounds, revisioned online/offline commands, lost connectivity, missing/invalid authority and retained web regressions. Full L02.7 Level 1 PASS cannot be claimed solely from those tests: backend offer acceptance/rejection and current authoritative offer projection, including transactional races and disconnect/retry, still require implementation and PostgreSQL integration qualification. Do not weaken the gate or invent offers.

Level 2 only at an actual driver/operator cross-app milestone; Level 3 once at Phase L02 closeout. Production Identity, licensed transport, vault, messaging and independent accessibility remain on `LIFTD-TESTNET-ROADMAP.md` as NOT ACCEPTED.
