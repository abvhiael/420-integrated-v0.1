# LIFTd L02.8 — Driver trip controls: implementation and acceptance boundaries

Canonical scope: navigation handoff, authoritative driver arrival/start/completion, explicit pickup confirmation, safety incident workflow, offline/reconnect consistency.

## Architecture and trust
- `rideshare/web/driver-trip-{policy,api,controller,view}.mjs` and authenticated driver route in `app.mjs` consume the existing protected L01 trip read/transition and safety endpoints. No independent trip authority, new on-chain contract or public dispatch is created.
- Arrival/start/completion are existing L01 `POST /v1/rideshare/trips/:id/transitions` commands, bound by server session authorization, driver/trip/vehicle/route, current admission, revision, PostgreSQL atomic event history and replay key. UI labels reflect only independent authenticated rereads.
- Start requires a separate explicit in-person rider pickup confirmation in the client in addition to backend-required fresh driver/vehicle/route admission. The UI confirmation is not independent safety authorization and cannot override backend gates.
- Safety reporting uses protected `/safety/report`, never a direct status mutation or payment capture.
- Navigation handoff is disabled unless the authenticated deployment injects a separately authorized `LIFTdNavigationCapability` that returns a matching trip/route-bound short-lived HTTPS navigation target. No client-generated coordinates, public-route tokens, guessed maps, or unsupported live navigation claims.
- Connectivity loss blocks all actions and clears confirmed in-memory state; no offline write queue or fabricated trip events. Reconnection requires a fresh verified read. Ambiguous network result retains a stable command ID until reconciliation.
- Protect against cross-trip/cross-driver responses, stale revisions, invalid lifecycle, unauthorized bearer use, unsafe navigation scheme, query-string identity and unverified session. Client only consumes protected first-party endpoints.
- This scope does not provide independent real-world trip, licence, driver/vehicle insurance, live payment or navigation-provider acceptance. Those remain testnet/production external gates in the canonical registers.
