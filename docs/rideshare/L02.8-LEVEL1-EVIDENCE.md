## Implemented requirements
1. Driver-only authenticated workspace displays authoritative assigned trip states, vehicle identity and revision, and requires manual server verification by trip ID. Previous L02.7 availability and offer controls remain mounted in the driver workspace.
2. Client submits only existing protected `arrive`, `start` and `complete` transitions with expected revision and idempotency command key; rereads the authoritative server state rather than inferring success from the POST acknowledgment.
3. Start button requires explicit in-person rider pickup confirmation after server-confirmed ARRIVED, on top of L01 admission, signed session and driver/vehicle/route security gates. The UI cannot override the server's real eligibility checks.
4. Safety reporting uses existing independently authorized `safety/report` service, with client-side incident type constraints. No direct emergency trip-cancellation or settlement impersonation.
5. Navigation handoff is fail-closed unless the independently authorized deployment supplies a trip/route-bound short-lived HTTPS capability through `LIFTdNavigationCapability`. Client never invents coordinates, routes or navigation provider credentials. This contract is repository-implemented, but production provider issuance/deployment acceptance remains blocked.
6. Disconnection blocks commands, clears in-memory asserted trip state and never queues offline transitions. Reconnect requires an authenticated reread; failed commands retain their idempotency key when server revision remains unchanged, while changed authoritative revision clears pending assumptions.
7. Cross-driver/cross-trip snapshots, stale revision, same-revision mutation, bearer/session errors, invalid transitions, unverified navigation URLs, unsafe credentials and cross-origin transport fail closed.
