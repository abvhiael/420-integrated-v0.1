# LIFTd L03.6 — deployment and managed security

Canonical requirement: **Production packaging, TLS, managed keys, least-privilege database access, migrations, health/readiness checks and rollback procedures.**

## Security admission
The repository `rideshare/Dockerfile` packages locked Node 22 dependencies without credentials and runs as an unprivileged user. It intentionally fails closed when launched without an admitted runtime composition and TLS termination. No passenger or payment traffic can be enabled by the package alone.

`rideshare/src/deployment-security.mjs` verifies HTTPS origin, database hostname/TLS `verify-full`, named non-superuser runtime role, separate managed-key fingerprints, immutable 40-character release SHA, request size and timeout, and disabled live dispatch, payment and passenger operations. Never store actual managed keys, database passwords, or connection strings in Git or CI artifacts. The public TLS listener must be independently configured with certificate validation, trusted-proxy allowlisting and safe header handling; no direct backend public access.

## Migration and least-privilege deployment sequence
1. Pin the container image by SHA-256 digest and verify the release source SHA. Create the isolated database and `liftd_migrator` role through an authorized provisioning system, not the runtime.
2. Provision `liftd_runtime` as a **non-owner**, **NOLOGIN inheritance**? Use a dedicated LOGIN role with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`; explicitly grant only necessary schema/table/sequence permissions through approved ordered SQL migrations. Do not grant `CREATE` or `TRUNCATE` to runtime.
3. Run the repository's checksum-verified, transactional, advisory-locked `migrate(pool)` with the separated migration authority before starting application replicas. Check all migration hashes and deny checksum drift; never run migrations under the web runtime role.
4. Inject trust keys from the managed secret provider using distinct Identity, session and private-location key IDs; rotate and test revoked/expired keys without permitting fallback to fixtures.
5. Validate deployment config and `assessReadiness` against the live database. Readiness must fail on non-verified schema, insufficient migration count, or privileged runtime DB role. Liveness may respond without sensitive data; readiness must not leak credentials or subject records.
6. Configure reverse proxy or ingress with TLS 1.2+ and verified certificate, restrictive origin/Host and trusted forwarding headers, authenticated internal health access, request timeouts/size limits, and private network-only PostgreSQL.
7. Keep production dispatch, payment and passenger traffic disabled until independent launch-jurisdiction, operator and financial signoff; deploy initially to isolated testnet.

## Rollback and incident response
Retain last accepted image and config digests, migrations and encrypted backup receipts before each promotion. On failure: stop external traffic; disable entry point; roll the app image back to the last accepted digest; **never blindly reverse or delete append-only database migrations**. If schema compatibility with prior image is not proven, remain stopped and restore via independently authorized, audited point-in-time recovery in a segregated environment. Verify integrity, role grants, backup key availability and readiness before any restart. Record operator identity, exact SHAs, UTC event times, incident/evidence holds, authorization, and test outcomes.

## Deferred deployed acceptance — NOT ACCEPTED
Repository validation is not proof of valid TLS certificates, real managed keys, independent IAM, vault/DB grants, trusted reverse proxy, image signing, successful deployed rollback, health probe wiring, restored production backup or actual disaster recovery. These require isolated deployment receipts, operator-owned evidence and independent security approval. No simulated checks grant live authorization.
