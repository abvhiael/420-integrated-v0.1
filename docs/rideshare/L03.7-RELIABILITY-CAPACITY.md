# LIFTd L03.7 — Reliability and capacity

**Canonical scope:** Multi-instance dispatch, load tests, worker failure, stale availability, provider outages, queue recovery and database backup/restore.

## Repository implementation and evidence

- `rideshare/src/dispatch.mjs` already uses PostgreSQL advisory transaction locks, independent verification of driver authority, deterministic candidate selection, expiring availability and leases, and revision/idempotency fencing. The retained real PostgreSQL `dispatch.test.mjs` includes two **independent Node processes** racing for a driver, rejected stale authority and availability, provider outages and retry/concurrency behavior.
- `rideshare/migrations/016_recovery_jobs.sql` adds durable restricted recovery-job state. `rideshare/src/reliability.mjs` implements transactional `FOR UPDATE SKIP LOCKED` multi-worker claims, unguessable per-lease fencing tokens, expiry/reclaim, bounded exponential retry, dead-lettering exhausted failures/crashes, deterministic job-ID idempotency and allowlisted `createRecoveryWorker` handlers. No external operator can select dynamic code via payload.
- The provider guard enforces bounded request lifetime, cancellation signal and cooldown after repeated failures. It rejects while the circuit is open and admits service recovery after cooldown; upstream adapters must honor abort signals and independently signed authorization.
- Real PostgreSQL tests run multiple concurrent worker claims, crash after a claim, reclaim without stale-token completion, repeated-crash exhaustion, unauthorized database writes and a bounded 50-claim load against 30 jobs.
- `rideshare/scripts/test-backup-restore.sh` invokes actual `pg_dump -Fc` and `pg_restore` on isolated qualification databases, checks recovered data, verifies all migration checksums and re-runs migration validation against the restore. It never targets a production database.

## Deployment controls and limitations

The admitted L03.6 runtime remains loopback-only and passenger operations remain disabled. A production worker process, configured provider guard, multi-replica capacity configuration, autoscaling, operator alerting, backups, independent signed provider credentials and recovery ownership must be provisioned only on an independently accepted environment. `createRecoveryWorker` is a backend integration API; it does **not** activate a public endpoint, standalone process or transport authority. Do not claim repository-local tests show live multi-instance acceptance, real production RTO/RPO, external provider readiness or approved passenger dispatch.

An operator integrating the recovery queue must supply independently authenticated handlers for `dispatch_reconcile`, `availability_sweep` and `provider_recheck`; only a least-privileged dedicated role may read/write `liftd.recovery_jobs`. Run bounded polls under a private scheduler, observe failures/dead letters, record lease ownership and reconcile reprocessing by business idempotency. External API calls must use signed current proofs and reject expired availability; never promote recovery results without fresh authorization. Validate database backups and staged restore before using recovery in an operational environment.

**Deferred acceptance:** isolated/testnet and production-equivalent multi-instance operation, realistic capacity targets, provider-outage behavior with real independent authorities, queue recovery under deployed process failure, database point-in-time/backup restoration, backup encryption and retention, and measured RTO/RPO require independent deployed receipts, reviewer acceptance and operational signoff. These belong to the existing TN-0–TN-6 sequence, not new development steps.

**Level 1 qualification:** see `L03.7-LEVEL1-EVIDENCE.md`. The next canonical step is L03.8; its independent operational safety acceptance is not satisfied by this step.
