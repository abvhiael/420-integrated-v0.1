# W15.2 — 420Wallet complete Solidity entry-point security review

**Review type:** manual source/control-flow and existing regression coverage review. **Baseline:** `main` `ba20d87b505db3d116968aa0bddbe8aa197e2040` (2026-11-11). **Scope:** W15.2 public, external, privileged functions, contract setup, exposed autogenerated getters and critical internal boundaries. **Status:** source review complete; **W15.2 security qualification NOT closed** because the findings and independent Foundry/fuzz/invariant/static-analysis gates below remain.

This is not a formal third-party audit, proof of exploitability, live-testnet attestation, or a new assertion that any test ran on this audit SHA. The separate WebAuthn parser regression is preserved at PR #1107, security workflow run [43110758499](https://github.com/abvhiael/420-integrated-v0.1/actions/runs/43110758499), implementation SHA `61c27f2c99e38d6bb2ce5cbe00985ebbad9d7a58`, merged in `0ff8c409998c907e6955a1c285accda1dab3a485`. No previously passing tests have been rerun.

## Review methodology and trust assumptions

Reviewed complete contents of `contracts/src/accounts/*.sol`, `contracts/src/system/CapabilityRegistry420.sol`, and `contracts/src/interfaces/genesis/ICapabilityRegistry420.sol` / `ICapabilityRegistryExtended420.sol`, including constructors, receiving ETH, implicit public storage getters, modifiers, library helpers, user-operation forwarding, capability consumption, P-256 verifier delegation and paymaster settlement. Compared against existing `contracts/test/{SmartAccount*,EntryPoint*,CapabilityRegistry420,Paymaster*,P256WebAuthnVerifier420,Sponsorship*}.t.sol`. No claims about contracts behind Identity/Names/ProtocolRegistry are made beyond their explicit interfaces and integration boundaries.

**Trusted roles:** owner, recovery authority, registrar for protocol-managed components, policy owner, sponsor signing key; an installed EntryPoint address and installed P-256 verifier are consensus/security-critical dependency anchors. A malicious keyholder of a designated role can act within that role; unauthorized callers must not acquire it. A generic third-party target of `execute` can revert/reenter; an arbitrary UserOperation can be submitted by an untrusted relayer, but must pass SmartAccount validation.

## Security findings and evidence classification

### W15.2-R01 — Declared UserOperation gas limits do not constrain gas forwarded (medium, open)

`EntryPoint420.handleOp` invokes `IAccountValidation420.validateUserOp(...)` and `userOp.sender.call(userOp.callData)` without a gas stipend from `accountGasLimits`. The same packed gas limits are used to compute the sponsor's maximum reservation, and actual charge is clamped to that reserve. Therefore a valid sponsored operation can execute with more gas than its declared call limit, consuming relayer gas beyond the signed sponsor reservation. The paymaster deposit *is* bounded by the reservation (no direct unbounded sponsor debit is claimed), but there is a griefing/metering mismatch and missing explicit enforcement. Existing hostile accounting tests check cost caps and reentrancy, not actual EVM gas forwarding. **Disposition:** targeted Foundry gas-probe adversarial test and scoped correction/explicit budget enforcement after confirming intended EntryPoint model; no deployed/funded operation is authorized by this audit.

### W15.2-R02 — Session spending limit is not a generic token-value bound (medium, open)

`SmartAccount420._tokenSpend` extracts amounts only from ERC20 `transfer`, `approve`, and `transferFrom`. For every other selector, `_resolveCallAuthorization` applies only the *native ETH value* as `authorization.amount`; if the call sends no native value, consumption is zero regardless of what token/asset amount may be encoded in calldata. The grant still requires owner-approved exact **target + selector** and current session epoch, so this is **not an arbitrary-target authorization bypass**. However, an owner who grants a nonstandard token transfer/permission selector and expects its per-call/period limits to measure token value may unknowingly authorize unmetered token movements. **Disposition:** determine/document supported selector set and test that value-bearing selectors outside the known set cannot masquerade as quota-metered; either fail closed for such scopes or explicitly narrow/validate the applicable spend-limit contract. Existing fuzz tests cover canonical ERC20 functions, not every possible selector.

### W15.2-R03 — ABI malformed session data can bubble revert during validation (low, open for negative-test confirmation)

`_authorizeSessionCalls` checks selector and uses `abi.decode(callData[4:], (address, Call[]))` without a catch; malformed encoded call data may revert from validation rather than returning `validationData == 1`. This causes `handleOp` to revert, and should not authorize a forged operation. **Disposition:** negative-case tests must establish nonce/deposit state preservation on malformed calldata. Not classified as theft or bypass.

### W15.2-R04 — Configuration and integration trust roots (assumption, pretestnet qualification boundary)

Account and factory constructors check nonzero EntryPoint/Registry, not deployed code for every dependency. Correct canonical binding is a deployment/chain authority prerequisite. Replacing the passkey verifier is owner-only and epoch-invalidating; the verifier's P-256 backend must be trusted/available. Paymaster's policy owner is immutable, so operational recovery of that role must use a planned authority. Namespace/address policy is frozen separately; this document neither changes nor attests deployment addresses.

### W15.2-SEC-01 — WebAuthn top-level JSON mismatch (resolved)

Original substring parsing was replaced, supported by adversarial tests, exact-head CI #43110758499 and merged PR #1107. **Do not rerun that passing qualification absent an invalidating change.**

## Integration boundaries and non-goals

- Wallet's capability registry grants are scoped to the smart-account component; this is separate from Identity credential authentication and from Names resolution. No caller may treat a human-readable name or an unsigned Identity record as executable transaction authorization.
- Registry contract discovery, canonical chain ID and runtime code/hash attestation remain W15.3/W15.9 deployment assertions, not locally manufactured evidence.
- EntryPoint's `initCode` is explicitly unsupported; factory creation is a separate transaction. Do not claim ERC-4337 account deployment parity with a full upstream EntryPoint.
- This review modifies **documentation only** and does not weaken a runtime control, reclassify previous test runs, enable sponsorship, or set a release flag.
