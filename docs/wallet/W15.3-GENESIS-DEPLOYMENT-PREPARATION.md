# W15.3 — Wallet Genesis contract and deployment preparation

**Authority:** canonical main at c9a05e9594ea0834547a419e532e26a8a2e6e895, frozen Genesis namespace and all predeploy mirrors. **Scope:** reproducible offline preparation, not live deployment attestation, testnet activation, governance approval or public-RPC publication.

## Placement and collision policy

The 29 frozen Step 6.2 system owners must remain exactly the same across contracts/config/system-addresses.json, config/system-addresses.json, contracts/config/genesis-address-namespace.json, contracts/config/predeploy/predeploy-plan.json and contracts/config/deployment-manifest.json. The frozen system-address range 0x0420–0x04ff is RESERVED, never an unallocated application namespace.

- ProtocolRegistry remains frozen at 0x0434, Names420 at 0x0435, Identity420 at 0x0436, ConsensusSystemCall420 at 0x043c.
- EntryPoint420 has historical reservation 0x041f, RESERVED_PENDING_PRODUCTION_IMPLEMENTATION. This is NOT deployed or approved as a populated Genesis predeploy. Ordinary CREATE deployment cannot arbitrarily occupy it.
- SmartAccountFactory420 0x0446 and CapabilityRegistry420 0x0447 are CANDIDATE_NOT_DEPLOYED_NOT_FROZEN. They receive independent, verified deployment addresses and authorized Registry publication, NOT Genesis alloc entries.
- SmartAccount420 is deployed per owner via Factory CREATE2, with owner/recovery/salt and the actual factory binding; never assign it a global predeploy address.
- Paymaster, sponsorship policy and P-256 adapter/verifier are optional independently deployed components with additional signer, relying-party, backend and governance dependencies. None is silently enabled.

Explicitly retired proposals MUST remain non-deployable: factory 0x0420, capability registry 0x0421, second Registry 0x0422/0x0448, duplicate Identity 0x0424/0x0449, duplicate Names 0x0445, old bridge proposal 0x043c, and GatewayRouter proposal 0x0443. Those addresses may retain their actual frozen owners and must not be reused for a retired identity.

## Deterministic artifact generation

The qualified script scripts/prepare-wallet-w15-3.py reads all frozen manifest mirrors, canonical Registry anchors and Wallet deployment inventory. It fails closed on drift, collisions, retired claims, false approval, missing artifacts and unpinned inputs. It does not write to the frozen namespace.

Pinned compiler: Solidity 0.8.24; Cancun; optimizer enabled at 200 runs; via-IR true (from contracts/foundry.toml). Foundry 1.8.6 and PyCryptodome 3.23.0 are pinned in the scoped CI workflow. The package contains eight contract ABIs, creation code, runtime templates, immutables references and storage layouts, with SHA-256 hashes of every authoritative input and artifact. Runtime template Keccak-256 is computed with PyCryptodome and **independently verified with Foundry cast keccak**.

A runtime code hash is labeled final only where no constructor immutable references require patching. If compiler immutables change runtime, the final on-chain code hash stays null pending approved actual constructor arguments and deployment. Constructor creation code is never mistaken for deployed runtime.

Run the scoped pinned build in the contracts directory, then:
- python scripts/prepare-wallet-w15-3.py --namespace-only
- python scripts/prepare-wallet-w15-3.py --output artifacts/wallet-w15-3
- python scripts/prepare-wallet-w15-3.py --verify-only --output artifacts/wallet-w15-3

The exact-head GitHub qualification archives artifacts/wallet-w15-3/ (manifest.json, eight contract artifacts, unsigned-deployment-plan.json and constructor-and-init.json). The output does not claim deployed network code, approved addresses or a signer.

## Constructor and initialization strategy

Wallet fixed Genesis alloc patch: EMPTY. There is no approved Wallet fixed predeploy to overwrite, and constructor execution is not reproduced by copying runtime bytes into Genesis.

1. Verify existing Step 6.2 Registry, Names, Identity and the network identity from independent evidence.
2. Obtain authorized placement and deployment signer; resolve the EntryPoint 0x041f historical reservation without promoting it by assumption.
3. Prepare and independently deploy EntryPoint420 (no constructor arguments). Verify actual address, receipt and code hash before any use.
4. Prepare and independently deploy CapabilityRegistry420 (no constructor arguments). Its componentRegistrar storage is the approved CREATE transaction sender; this value cannot be fabricated before signer approval.
5. Deploy SmartAccountFactory420 only after verified EntryPoint and CapabilityRegistry exist; its two constructor addresses are immutable and change the deployed runtime hash.
6. Verify constructor-patched Factory runtime, then publish authorized service identities through the actual ProtocolRegistry. Do not infer authorized Registry state from a local example.
7. Allow per-user Factory CREATE2 account deployments after owners approve owner/recovery/salt inputs. Verify deployed account and capability component authority.
8. Optional sponsorship policy/paymaster/P-256 verifier deployments require independent approvals, signer/policy/RP and precompile availability; do not bypass these gates.

The unsigned plan includes complete unbound CREATE transaction data for zero-argument EntryPoint/CapabilityRegistry and constructor-dependent Factory template material. Sender, nonce, derived contract address, live transaction receipt, RPC and explorer remain null. Expected chain ID 420 is not an attested network identity.

## Recovery, rollback and redeployment

Before publication, discard the unsigned bundle, preserve frozen Genesis allocations and regenerate deterministically from the pinned authoritative source. After actual chain deployment, neither storage nor the CREATE2 wallet address can be rolled back by editing a manifest. Preserve immutable receipts/runtime evidence and disable new client-side sessions/sponsorship when authority is uncertain. Invoke actual authorized account revocation and owner/recovery controls, and use governed ProtocolRegistry publication controls to suspend an unsafe reference. Do not claim an on-chain pause where the contract provides none.

For a new deployment, obtain a fresh authorized signer/nonce/placement, generate new constructor-bound runtime hashes, independently verify receipts/code and update only legitimately authorized Registry records and signed clients. Never reuse retired proposals, silently redirect existing user accounts, overwrite fixed Step 6.2 authorities, or treat a new Factory as preserving previous CREATE2 account addresses.

**Emergency reject conditions:** runtime/hash mismatch, wrong Registrar or EntryPoint, conflicted/retired address, missing chain identity or receipt, unavailable passkey verifier/RIP-7212 precompile, or unauthorized service publication. Fail closed and do not mark Wallet live-testnet ready.
