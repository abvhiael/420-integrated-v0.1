# W15.4 — Common Wallet Core, Account Management and Transaction Qualification

**Scope:** shared Wallet Core behavior in web, extension and mobile delivery channels, reusing authoritative SmartAccount420 / Factory / EntryPoint / CapabilityRegistry and EIP-1193/native signing authority. This work does not deploy any contracts, approve Genesis candidate addresses, enable an unsigned backend signer, or invent network endpoints. The frozen Step 6.2 system-address authority and previously qualified W15.2/W15.3 artifacts are unchanged.

## Canonical account and network authority

`wallet/web/runtime-config.json` is an **unbound offline configuration**: chain ID, RPC, factory address and public endpoints are null. The old `0x0420` Factory value was retired (RewardController owns 0x0420). CapabilityRegistry's old `0x0421` address was retired (AttentionTreasury owns 0x0421). Neither may act as a Wallet authority. Factory and capability registry are registry-resolved and remain unapproved candidates `0x0446`/`0x0447`, not fixed or live addresses.

The Wallet live-runtime generator now requires every relevant Wallet authority to be chain-verified and preserves frozen ProtocolRegistry `0x0434`, Names420 `0x0435`, Identity420 `0x0436`. There are no invented receipts or code hashes. Wallet Core validates a connected network against the runtime-approved chain **at preparation and again before submission**. A restored SmartAccount's EntryPoint and CapabilityRegistry must match the configured verified contract bindings; malformed runtime code and mismatched JSON-RPC response IDs are rejected. The browser remains read-only when the actual network/Factory/Registry/EntryPoint are absent. Capabilities and session authority cannot be derived from an unapproved or retired fixed address.

Run the existing exact-head Wallet Web, Extension and Mobile JavaScript qualification paths. Retain W15.3 offline artifact run [43247416014](https://github.com/abvhiael/420-integrated-v0.1/actions/runs/43247416014) (12 namespace tests and 8 independently verified runtime hashes); it does not establish live contract availability.

**External qualification still required:** live network identity/receipts and finality/reorganization observations, actual approved Factory/Registry/EntryPoint deployment evidence and addresses, optional paymaster funding policies, device passkey credential/RP verification, and physical Android/iOS signing experience. The Wallet must fail closed until those are independently verified. No testnet/faucet/explorer is published by this change, and no browser/client is authorized to create a chain account merely because an old address is present.

## Recovery / rollback

Reverting this client release must not alter on-chain authorizations: preserve transaction hashes and receipts, stop signing/broadcast when runtime binding changes, recover account control using the deployed contract's actual recovery authority and timelock, revoke compromised sessions/grants with owner permission, and republish only verified signed deployment metadata. A pending or reorganized transaction is **not** automatically rebroadcast; users explicitly re-review after chain revalidation. If a device/browser session is compromised, invalidate its session keys or passkeys using the contract-authorized revocation workflow. Never copy private keys or seed phrases to a Wallet server.
