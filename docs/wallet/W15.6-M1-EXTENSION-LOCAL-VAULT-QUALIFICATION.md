# W15.6-M1 — 420Wallet extension: local creation, import and recovery qualification

**Scope:** MetaMask-style self-custodial wallet creation and local recovery, without requiring a running testnet.

## Authority and source

- Canonical repository: `abvhiael/420-integrated-v0.1`; implementation in `wallet/extension/`.
- BIP-39/BIP-32/BIP-44, EVM addresses and Ethereum keystore decryption: **ethers 6.17.0** vendored from the official upstream published release `ethers-io/ethers.js`, tag `v6.17.0`, Git blob `8b1bb8fb32192a266cbe2cf27983c71a69ba7d4c`; MIT license preserved. `check-release.mjs` verifies the exact official Git blob hash. No dynamic scripts.
- The encrypted vault (`core/vault.js`) never passes recovery phrases, keys or password to RPC or the service worker. The Chrome background worker stores **public** account addresses only and cannot decrypt the vault.
- `wallet.html` is a trusted extension-page tab with an isolated CSP. No web page can open a vault method through the content-script RPC bridge. Browser wallet provider origin restrictions remain in the service worker.

## Locally implemented

1. First-run welcome with Create, Import, Passkey SmartAccount option and Hardware Wallet option. Passkey option can register a device-bound WebAuthn ES256 credential from an unlocked extension vault; the resulting public metadata remains explicitly pending until authorized on-chain.
2. Secure random 12/24-word BIP-39 English mnemonics, valid-checksum imports and BIP-32 derivation at `m/44'/60'/0'/0/{index}`; BIP-39 optional passphrase; deterministic recovery vectors.
3. Private-key and encrypted Ethereum JSON keystore import; distinct wallet IDs and multiple derived accounts.
4. Password-derived AES-256-GCM encrypted JSON vault; versioned envelope; PBKDF2-HMAC-SHA256 (600,000 iterations), random 256-bit salt and independent 96-bit IV for each revision, authenticated metadata and integrity checks. No unencrypted mnemonic or private key is written to Chrome storage.
5. Local unlock, explicit password change, lock and timed automatic lock. Decrypted session is confined to the extension page and discarded when it closes. Secret recovery display requires password reauthentication.
6. Three-position phrase backup confirmation before creating the vault. A failed phrase check never creates a vault.
7. Complete encrypted vault export/import, including imported private keys, BIP-39 passphrases and stored derivation indexes; no overwrite of an existing vault.
8. Manual restoration of a user-specified number of derived accounts, deterministic next-account derivation, optional chain-checked balance/nonce account discovery with configurable gap and max-scan bounds, explicit truncation warnings and offline/manual restoration.
9. Read-only EOA address/balance/Receive integration for provisioned vault accounts. EOA send/sign functionality is **not** presented as enabled merely because a private key exists. SmartAccount420 and EOA authority are not mixed.
10. Website account exposure of vault-owned addresses requires a non-expired extension session lease; local account lock does not alter unrelated on-chain grants.

## Security boundaries

- **BIP-39 is not a passkey backup.** A mnemonic restores only matching derived EOAs; separately imported keys need their own backup. Passkeys remain device-bound. The Chromium extension supports local ES256/WebAuthn creation with RP scoped to its own extension ID. Public key coordinates and credential ID are stored only inside the encrypted vault, explicitly marked `pending-onchain-enrollment`. This metadata **does not grant any authority**: live SmartAccount420 owner, epoch, verified deployment and canonical recovery policy enrollment still have to succeed. Restoring an encrypted backup does not recreate a deleted device credential.
- **Hardware keys stay on hardware.** The welcome option explains the device integration gate; it does not pretend an unconnected device is imported.
- **No server-side signing or RPC key fallback.** The existing SmartAccount420 local passkey execution path remains unchanged. A locally generated EOA address is not treated as a deployed SmartAccount or a passkey authority.
- **RPC discovery is not complete-history indexing.** Scans explicitly disclose gap and truncation limitations and support manual account-count recovery. Restore the encrypted backup to preserve account inventories (including imports).
- **Vault passwords cannot be reset by 420Integrated.** Password loss requires a usable recovery phrase or a correct encrypted vault backup password.
- WebCrypto and JavaScript cannot guarantee instant erasure of immutable string copies in browser memory. The in-memory vault is never persisted in plaintext or included in page analytics.
- A running testnet is unnecessary for local creation, derivation, encryption, lock/unlock and restoration tests. Live chain ownership, SmartAccount passkey enrollment and dApp execution require their own authoritative deployment evidence.

## Explicit external qualification boundaries

The passkey SmartAccount and hardware onboarding choices are offered without inventing unverified signing authority:

- Active passkey **on-chain enrollment** requires a deployed and verified SmartAccount420 and a WebAuthn origin supported by the canonical authorization policy. Browser-only registration is locally implemented and does not activate SmartAccount execution. It is not completed by phrase backup or offline vault creation.
- Ledger/Trezor transport and actual device signing are the later hardware-wallet milestone, not part of EOA mnemonic import.
- End-to-end EOA transaction signing, replacement and fee lifecycle are the later Send/Transaction milestone and must not be silently replaced by SmartAccount passkey execution.
- Multichain account/connection compatibility and hardware-device-specific releases are separate roadmap milestones.

**Completion criterion:** Local wallet creation/import, encrypted retention, account management and recovery are qualified independently; none of the external requirements above are misrepresented as completed.
