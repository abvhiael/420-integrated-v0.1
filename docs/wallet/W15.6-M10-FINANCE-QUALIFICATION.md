# W15.6-M10 — Extension swaps, bridging and staking software qualification

**Scope:** advanced financial wallet interface, on-chain quote comparison, route selection, slippage protection, allowance review, source/destination bridge evidence, applicable genesis validator staking.

## Architecture and trust boundaries

- `wallet/extension/core/finance420.js`: exact EIP-155 chain, nonzero token/contract addresses, distinct approved on-chain route identities, release-approved provider manifests, matching router/spender runtime code hashes, canonical `ExchangeRouter420.quoteExactInput` multi-route comparison, BPS slippage bounds, safe exact-in router calldata, exact ERC-20 allowance/approval calls, registered `GatewayRouter420.initiateOutbound`, source/destination event and bridge-transfer-registry reconciliation, and 420Stake validator read-only contract queries.
- `wallet/extension/core/finance-runtime420.js`: decimal-to-raw token precision, verified nonspam spendable balance and independent on-chain payer address (EOA or SmartAccount), quote expiry/recomputation, exact spender/allowance separation, simulation and gas review, and immutable review comparison. Unconfigured or unapproved adapters yield **no executable routes**.
- `wallet/extension/service-worker.js`: trusted popup-only finance commands, ephemeral account/chain/epoch-scoped quote/review state and one-time consumption, repeated on-chain simulation before signing, reuse of local EOA/hardware or passkey SmartAccount authority, existing pending/submitted/confirmed/reverted/reorganized transaction lifecycle and same-nonce replacement rules. No backend or RPC holds signing keys; no automatic unconfirmed retry.
- `wallet/extension/popup.html` / `popup.js`: accessible Finance tab, categorized swaps/bridges/validator info, route comparison by received amount, slippage and impact, explicit one-time approval or exact execution review, source activity links and separately supplied destination receipt checks. Display-only data cannot bypass worker validation.
- Source bridge success is only `source-included`, `source-confirmed` or `source-finalized` when a canonical finalized block is observed. Destination receipt needs independently trusted chain, matching gateway code, adapter, transfer registry and source message/amount/owner. `inbound-accepted` is **not a beneficiary payment**. Paused/failure/reorg/unknown routes require manual canonical reconciliation; never auto-refund or double send.
- Current genesis `Stake420` is read-oriented, explicitly `delegationEnabled() == false` and lacks public delegation. No fabricated validator staking, delegation, APY, withdrawal or reward-claim transaction is exposed.

## Provider provisioning (disabled without deployment)

`420-wallet-extension-config-v1.financeProviders` must contain only independently approved entries (`releaseApproved:true`) with canonical `chainId`, `router`, actual `keccak256(runtime code)`, `spender` and its runtime code hash, governance-approved market/route IDs or bridge adapter/asset/route IDs, and approved asset representations. External third-party providers are separately approved by the same identity/call-data policy, never by an unauthenticated quote URL. Swaps require active deployed liquidity (on-chain `quoteExactInput`); bridge entries require a distinct destination chain and pinned destination gateway/registry runtime code hashes and adapter identity. No hardcoded fictional deployments or liquidity are supplied. Only configured verified portfolio tokens can be spent; gas and bridge network fees are disclosed individually. Route price/fee data cannot be authoritative merely because it is returned by an off-chain provider.

## Focused software verification

`wallet/web/test/w15-6-m10-finance.test.js` verifies approved exact-chain/codehash, hostile/empty quote outputs, quote ordering, bounded slippage, exact token amount, allowance and approval calldata, stale review rejection, EOA/SmartAccount payer semantics, source/destination bridge canonical event and registry matches, and no public delegation/claim on genesis stake.

Existing tests for send/receipt/replacement, security scopes, contract ABI/route status, extension popup, and strict CSP remain authoritative; no unrelated casino or exchange full-suite tests need repetition. Confirm passing actual run IDs and SHA on the Phase 10 PR before marking software qualified.
