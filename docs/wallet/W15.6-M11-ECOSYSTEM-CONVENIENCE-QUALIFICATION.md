# W15.6-M11 — Expanded ecosystem and convenience features

**Repository:** authoritative 420Wallet extension and existing portfolio, site permissions and local signing authority. **Software boundary:** Phase 11. **External acceptance:** [W15.9-M11](W15.9-M11-EXTERNAL-ECOSYSTEM-ROADMAP.md). Never claim production acceptance from offline SDK tests.

## Reuse of canonical existing functionality

Existing token/NFT discovery, fiat price trust, cross-network balance aggregation, chain-scoped address book, ENS-compatible/420Names recipient resolver, approved site permission/revocation, signer and transaction-lifecycle flows remain authoritative. New local labels cannot resolve names or alter ownership. Portfolio analytics are current verified positions and bounded activity status only; cost basis, tax reporting, and historical profit/loss are unavailable without independent validated history.

## Added implementation

- wallet/extension/core/extension-convenience420.js: schema-versioned local privacy, per-chain address labels, consent-gated operator-approved HTTPS service directory, verified balance/activity summary, scoped local alerts, strict WalletConnect v2 pairing URI input validation and password-encrypted local metadata backup (600,000 PBKDF2-SHA256 iterations, random salt/IV, AES-256-GCM with authenticated version).
- Backup never exports or restores BIP-39 recovery phrases, private keys, SmartAccount passkeys, vaults, accounts, origin grants, RPC configuration or transactions. No remote backup/sync provider is configured; remote contact and backup sync fail closed without independently approved end-to-end encryption.
- wallet/extension/core/walletconnect-policy420.js: untrusted relay session proposal restricted to HTTPS origin, selected account, exact EIP-155 chain, requested methods/events; signed requests fail on wrong topic/network/account or ungranted method.
- WalletKit 1.6.0 and WalletConnect Core 2.25.0 are built locally from pinned packages into the extension. Service worker accepts explicit project and HTTPS app identity configuration only, requires one-time consent for pairing, separate approval of namespace proposal and each signing request via existing extension UI, disconnection, and revocation on privacy opt-out. No signing keys are sent to relay or remote SDK. Actual relay/device acceptance is deferred to W15.9-M11.
- wallet/extension/popup.html, popup.js, popup.css: full-page browser mode reusing the same extension worker and authority UI; Tools navigation; verified analytics, contacts/labels, privacy mask, optional notifications, encrypted backup export/import, mobile/WC v2 pairing UI, session disconnect and approved 420Integrated service list. External app links never silently grant website permissions.
- wallet/extension/manifest.json: notification permission is optional; user gesture required for browser permission. Alarms run local receipt/transaction alerts at opt-in interval; first enrollment suppresses historical replay. There is no remote push service or tracking endpoint.

## Test strategy and evidence

Focused wallet/web/test/w15-6-m11-convenience.test.js exercises corrupted backup/wrong passphrase and excluded key material, verified-asset analytics, off-by-default privacy and scoped notifications, cross-chain labels, origin/spoof protection for services, malformed/duplicate pairing query parameters, unapproved WalletKit proposal chains/methods and wrong signer/topic session requests.

Use only related Wallet Web, Extension, Chromium popup, Browser Accessibility, Docs and dedicated SDK packaging checks. Preserve prior qualification evidence. Actual mobile hardware pairing, relay sleep/restart behavior, externally provisioned E2E sync, deployed 420Integrated service identity, and independent W15.10 security/release checks remain genuine external blockers in W15.9-M11.
