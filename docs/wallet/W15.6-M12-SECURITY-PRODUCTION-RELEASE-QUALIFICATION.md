# W15.6-M12 — Wallet extension security and production release qualification

**Release blocker:** This step is a security and browser-release gate, not a claim that public distribution is qualified. The authoritative extension's current `main`, Phase 9 hardware, Phase 10 finance, Phase 11 WalletKit and W15.9 testnet handoffs remain scope boundaries.

## Threat model and executable work

- **Custody:** The existing vault uses BIP-39/BIP-44, local WebCrypto PBKDF2-SHA256 (600,000 iterations), AES-256-GCM, version/AAD binding, encrypted browser-local storage, scoped unlock policy and no server/RPC signing. New M12 hardening requires a cross-window browser Web Locks API for *all* vault mutations; creation and encrypted restoration serialize under the same lock and recheck existence after PBKDF2. A missing lock fails closed instead of racing. An independently reviewed browser must demonstrate the lock is implemented and actually held across windows.
- **Attack suite:** `wallet/web/test/w15-6-m12-security-release.test.js` covers missing lock rejection, concurrent creation (only one winner), stale concurrent modification, wrong password, authenticated ciphertext and revision tampering, key-exfiltration source boundaries, malicious/malformed RPC endpoint and chain IDs, infinite allowance warnings, and EOA wrong-chain/wrong-nonce/weak-fee-bump replacement. Existing M1/M2 vault regressions run under explicit serialized browser-lock mocks rather than bypassing the production lock.
- **Permission, phishing and message isolation:** Existing service worker only accepts trusted popup/authority origins, binds top-frame site requests to sender origin, prevents sensitive RPC forwarding, and requires site permissions, explicit approval and local device/passkey/EOA authority. Existing permission, phishing and EIP-6963/MetaMask coexistence tests retain their passing SHAs. Malicious extensions with more privileged permissions cannot be guaranteed isolated by this wallet: threat-model browser process compromise and permission escalation separately.
- **RPC manipulation, replay, replacement and restart:** Existing chain-bound endpoint checks, signature recovery and transaction envelope review, receipt recheck/reorg/dropped classification, same-nonce EOA and ERC-4337 replacement/cancellation, browser restart/grant recovery and invalid origin/chain guards remain release requirements. No provider-supplied fee, nonce, block hash or indexer projection can become signer authority.
- **Browser compatibility:** Chromium MV3 uses `background.service_worker`. Firefox MV3 uses an event page `background.scripts` with `type:module`; the separate `scripts/build-firefox.mjs` manifest intentionally does not advertise Chromium Trezor `externally_connectable` capability. Its Firefox declaration uses explicit privacy/no-collection metadata and requires a verified release add-on ID for signing. A Firefox schema lint or static package check is **not** runtime qualification.
- **Reproducibility:** `scripts/qualify-reproducible.mjs` hashes every packaged asset and requires exact repeated Chromium outputs, identical common code for Firefox and Chromium, and distinct browser manifests. Production reproducibility additionally requires a committed integrity-pinned transitive dependency lockfile and actual independently verified release provenance. Same-environment double-build is useful evidence but insufficient for reproducibility across clean systems.

## Release criteria (not waived by CI)

1. Focused unit, fuzz/adversarial and existing regression tests on exact code SHA; no weakened assertions.
2. Chromium Chrome/Edge/Brave packaged extension behaviour and in-browser accessibility, signing/replacement, cryptographic recovery, restart and denied permissions.
3. Firefox *separate* packaged event-page, Web Locks, vault, RPC/extension messaging, EIP-1193, permission/restart, hardware/passkey API capability checks, and real supported Firefox browser acceptance. Browser-specific hardware unsupported features must remain disabled.
4. Byte-identical builds across independent environments with the same reviewed *locked* transitive dependency graph, pinned vendor blobs, extension CSP and no remotely hosted executable scripts.
5. Real deployed services, hardware wallet models, signed transactions, WalletConnect/mobile and destination settlement completed under existing W15.9-M9/M10/M11 evidence; no offline mock replaces on-chain/device acceptance.
6. **External independent security review** of custody, key handling and exfiltration, authorization/UI and phishing, cryptography/entropy/passkeys, transaction execution, consent/replay and browser isolation, supply chain and dependency vulnerabilities; signed and scoped findings remediated with exact-head regression evidence.
7. Final distribution signing and provenance approved for each browser. No signed/public production release prior to all gates.

**Qualification state:** local implementation and automated tests may be merged independently, but the extension must not be labelled production certified or distributed as security audited. See the existing canonical W15.9 and W15.10 roadmaps for external work, with no added roadmap phases.
