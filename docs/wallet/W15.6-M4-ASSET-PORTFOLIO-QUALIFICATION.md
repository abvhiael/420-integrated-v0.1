# W15.6-M4 — Extension asset management

## Authoritative implementation
- `wallet/web/core/extension-portfolio.js`: account/chain scoping, strict ERC-20 contract metadata verification, bounded Transfer-event discovery, current ERC-721 ownerOf verification, spam heuristics, balance status, price provenance and exact-decimal fiat.
- `wallet/extension/service-worker.js`: trusted extension UI only; portfolio RPC through the M3 verified same-chain transport; account-scoped import/hide/spam/configuration, read-only bounded discovery, no private key access, chain epoch revalidation and storage caches.
- `wallet/extension/popup.js` / `popup.html`: Tokens, NFTs and Activity views; detail pages, hidden-token toggle, manual ERC-20 contract import, optional price service, explicit refresh and discovery. A read-only account never receives executable Send.
- No change to transaction signing authority. Network, signing, user-operation, nonce or authorization policy is never inferred from a token price or token transfer.

## Trust and data-status rules
1. A token returned in a Transfer log is merely a **candidate**, not a certified asset. A new ERC-20 entry requires code at the specified address, decoding `symbol()` and `decimals()` directly from that deployed contract and `balanceOf(selected account)`. User-submitted symbol/decimals are never authoritative. No asset can gain signing authority.
2. Bounded discovery reads at most 2048 recent blocks per scan and a capped number of logs and candidate contracts; it cannot promise historical completeness or detect silent token transfers. An indexed provider is required for full-history discovery. The user sees the bounded-scan qualification. ERC-721 holdings must pass `ownerOf(tokenId)` on the selected chain; old transfers do not establish ownership. ERC-1155 inventory and third-party image/metadata feeds are **not** asserted to be fully qualified without an authoritative indexer.
3. All settings and caches are scoped by **chain ID and account**. Native balances and token balances are independent of wallet spend authority; a visible balance on a watch-only or unqualified SmartAccount remains non-executable. Pending popup transactions are counted separately and do not cause fabricated deductions. Provider failure produces **unavailable** (not spendable) amounts and explicitly stale historical data.
4. The user must deliberately configure an HTTPS quote endpoint per account and chain. The endpoint must echo the canonical chain, exact asset, fiat currency, decimal quote, and timestamp; invalid, stale (>5 min), future, mismatched, unavailable or offline quotes do not produce fiat valuations. Cached prices retain timestamps and provenance; no old quote is treated as a current valuation. User-configured providers are not automatically oracle-certified.
5. Explicit token hiding, suspected spam suppression and manual visibility changes are local UI/account preferences. Dangerous external NFT images, URLs, unknown remote content and arbitrary HTML are never rendered.
