# W15.6-M5 — Browser extension Send/Receive and transaction lifecycle

**Status: PARTIAL IMPLEMENTATION — NOT PHASE QUALIFIED.** This record intentionally does not claim a live or production-ready send lifecycle.

## Implemented on the W15.6-M5 feature branch
- Submission vs confirmation is correctly distinguished in extension Send and activity.
- Canonical receipts are read against the selected verified network, with two confirmations required and second receipt check; record **pending, submitted, included, confirmed, reverted, reorganized**.
- Unknown or absent receipts cannot be used as proof of dropped, replaced or cancelled transactions.
- Submitted hash is preserved when a post-submission chain context check fails; sending must not be automatically retried.
- Chain-scoped encrypted-key-independent local address book with trusted popup mutations, validation and bounded storage.
- Exact full-precision **Max** for verified spendable ERC-20 balances; native Max is intentionally blocked until account-abstraction gas cost can be proven.
- Locally generated address-only Receive QR for the current chain-verified EVM address, rendered without third-party endpoints, using a vendored MIT-licensed QR encoder; network/chain warnings remain visible.
- Regression coverage in `w15-6-m5-extension-transaction.test.js`, `w15-6-m5-address-book.test.js`, `w15-6-m5-max-amount.test.js` and `w15-6-m5-receive-qr.test.js`.

## Still required before W15.6-M5 can be called complete
1. ENS and canonical 420Names integration, deployment identity checks, resolved address revalidation at execution and explicit user acceptance.
2. Complete independent scanner-based QR decoding parity checks in Chromium (offline QR generation and the same address as Copy are implemented).
3. Verified native Max calculation, accurate ERC-4337 fee exposure, adjustable fees, payment/sponsorship contingencies and transaction simulation preview **before** final user confirmation.
4. ERC-20 allowance/approval risk presentation when required by the particular execution path.
5. Durable tracking of both popup and approved dApp-origin sends, including submission identifiers and UserOperation hash vs transaction hash.
6. Correct, independently tested EOA replacements (same chain/sender/nonce with fee bump) and ERC-4337 replacement/cancellation (EntryPoint version, sender, nonce key/sequence, signature scope, bundler policy); no EOA logic copied to AA.
7. Dropped/replaced/cancelled status only with corroborated network/nonce/replacement evidence, never a timer.
8. Error-recovery/reconciliation after extension worker suspension, network outages, chain change and transaction reorgs.
9. Full CI, manual Chromium UX/accessibility, security qualification and live-testnet integration once the approved testnet is available.

## Security non-negotiables
- Never send imported EOA keys or passkey secrets to any RPC, website, backend or analytics endpoint.
- Wrong-chain, stale epoch, missing contract and no verified execution authority fail closed.
- A pending transaction or UserOperation must never be silently rebroadcast.
- No production-ready or completed-phase signoff until independent qualified evidence exists.
