# W15.6-M5 — Send, Receive and transaction lifecycle

## Authoritative implementation

- `wallet/web/core/extension-transactions.js`: recipient and address-book validation, ENS namehash, canonical ENS resolver, explicit fee bounds, exact Max calculations, balance/fee checks, chain/epoch-bound simulation preview, receipt/confirmation/reorganization state machine and EOA/ERC-4337 replacement policies.
- `wallet/web/core/names-client.js` and `names-send.js`: existing canonical contract-identity and expiry checks for independently configured 420Names; no resolver address is fabricated.
- `wallet/extension/service-worker.js`: trusted popup-only `prepare-send`, `send`, `max-amount`, `resolve-recipient`, `refresh-transactions`, address-book management and periodic receipt monitoring through verified same-chain RPC endpoints.
- `wallet/extension/popup.js`, `popup.html`: on-chain simulated Send review, adjustable EIP-1559 caps, gas reserve, Max, verified recipient and account context, address book, local offline QR Receive, explicit confirmation and transaction activity status/receipt checks.
- `wallet/web/core/extension-local-authority.js`: account-specific passkey execution maintains owner-controller authority separation; packed ERC-4337 gasFees use verified current base fee and user-approved fee caps, revalidated before signing. Existing owner nonce lane-zero rechecks are preserved.
- `wallet/extension/vendor/qrcode.min.js`: pinned MIT-licensed QR Code rendering implementation by davidshimjs. Address is encoded entirely in the extension, without remote QR or image services. Accompanying license: `vendor/QRCODE-LICENSE.md`.

## Acceptance and security

1. Direct EVM recipients are nonzero and syntactically validated. ENS is restricted to verified Ethereum mainnet EIP-155 registry/resolver calls, rechecking chain identity. 420Names requires independently verified deployed chain manifest configuration and existing canonical identity, expiry and resolver validation. Names are resolved again before transaction authorization; changed records invalidate the preview.
2. A preview is issued only for a verified deployed SmartAccount420 and matching account/chain, with a known verified token and actual on-chain balance. `eth_call` simulation, `eth_estimateGas`, EIP-1559 base fee, priority/cap, maximum reserve and account/asset sufficient funds are required. A prepared preview has a 45-second validity, is bound to chain ID, monotonic epoch, controller, resolved recipient, amount, fee and asset, and is single-use. Simulation is repeated at authorization. Custom gas is carried into the signed ERC-4337 UserOperation fee fields; final SmartAccount nonce, passkey identity and EntryPoint simulation remain separate authority checks.
3. The service worker never submits EOA transactions using RPC impersonation or sends private keys to a remote host. An imported EOA or watch-only account cannot use a SmartAccount passkey signing route. The current extension has no qualified EOA/hardware signing transport for execution, so those Send actions remain disabled.
4. A returned transaction hash is **submitted**, not confirmed. Verified canonical receipts and confirmation depth classify included/confirmed/reverted; a displaced canonical block hash identifies reorganization. RPC outages and missing receipts do **not** invent dropped, replaced or cancelled outcomes. Pessimistic pending state is retained on uncertain authority failure. The one-minute alarm checks receipts against the transaction's chain only. Activity entries preserve account/chain provenance.
5. EOA replacement requires the same sender/nonce and both cap/tip fee bumps; ERC-4337 requires the same EntryPoint nonce key/sequence and a distinct signed canonical UserOperation hash with independently raised gas fee fields. The two models are never interchanged. **Live speed-up/cancellation remains disabled** until the applicable signer, replacement submission, bundler nonce and independent on-chain evidence have been deployed/qualified. Status labels alone do not count as replacement execution.
6. QR generation and address-book storage remain local. No external QR endpoint receives the user's receive address. Address books are per account, and all website signing grants remain scoped to chain and account.

## Local tests and external boundaries

- `wallet/web/test/w15-6-m5-transaction-lifecycle.test.js`: direct/ENS/420Names input acceptance, address-book validation, exact BigInt Max, fee boundaries, chain/epoch preview invalidation, receipt confirmation depth/reverts/reorg, replacement models, canonical ENS resolver and fail-closed UI/worker boundaries.
- Packaged Chromium extension qualification verifies local QR and read-only account cannot prepare a send. Existing Web/Core, extension security and accessibility tests retained, not bypassed.
- Official 420Integrated testnet, 420Names deployment, authoritative fee oracle/bundler, real signer transport and live receipt/reorganization scenarios remain unavailable per canonical inventory `readyForLiveTestnet=false`. End-to-end transaction submission, live ERC-4337 replacements, dropped/replaced/cancelled provenance and real network confirmations cannot truthfully be claimed as qualified without that external infrastructure.
