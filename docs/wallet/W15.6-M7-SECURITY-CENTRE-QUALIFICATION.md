# W15.6-M7 — Security Centre and permissions qualification

**Scope:** Phase 7 — Security Centre and permissions, critical. Offline implementation and test record; no live on-chain revocation or production certification is asserted.

**Integration:** This change is stacked on Phase 6 (PR #1139), itself stacked on Phase 5 (PR #1137), both still unmerged at implementation time. Merge order must preserve the existing parent work and its qualified release gates.

## Original security-management requirements

- **Connected sites, accounts and permissions:** existing origin-scoped account/chain grants appear in the Security Centre with exact origin, selected account, last grant time, risk flags, and Disconnect control. Disconnect removes **local browser permission only** and emits account changes. It never modifies ERC-20 token allowances, CapabilityRegistry grants, session keys or passkeys.
- **Signature history and alerts:** successful EIP-191/EIP-712 signatures through this extension are recorded locally with origin, account, chain, time and heuristic risk flags; no key, mnemonic, raw signature or signed message is stored. Heuristics flag punycode domains, suspicious brand words, IP addresses, insecure origins, opaque personal messages, EIP-712 permits, unlimited values and chain/domain mismatch; a warning is not a threat-intelligence verdict.
- **Token allowances:** verify exact token bytecode and allowance(owner,spender) on the selected chain. Manually watch any token/spender; discover recent standard Approval events in a bounded 4,096-block window covering up to eight verified tokens and 20 spenders, then re-read the actual allowance. This is deliberately not a complete all-time approval inventory; old and nonstandard approvals need exact inspection.
- **On-chain allowance revocation:** submit the token-specific approve(spender,0) with verified EOA owner or eligible approved SmartAccount passkey execution. Review target, exact calldata, amount, gas, nonce, chain and fees before approving, and require separate confirmation. The UI reports **submitted** rather than revoked until canonical allowance/receipt evidence exists.
- **Smart Account capability grants:** inspect exact grant through independently verified CapabilityRegistry420 with account component-ID binding. Revoke via canonical SmartAccount420 owner-only revokeCapabilityGrant(bytes32), not by clearing browser permissions. Foreign, absent, revoked, or unverified grants are blocked.
- **Session key epoch and expiry:** inspect SmartAccount420 sessionEpoch; key is active only when its stored epoch matches authorizationEpoch. Bound capability-grant validUntil and revocation are distinct. On-chain revokeKey(address) requires the current owner; local watch removal does not change any grant. Expired epochs cannot be resurrected from browser state.
- **Passkeys and recovery:** deduplicate local passkey credential references, verify isPasskeyActive on chain, and provide on-chain revokePasskey(bytes32) only through current owner authority. Show SmartAccount recoveryAuthority, pendingRecoveryOwner and executableAt, owner, epoch and policy version. Recovery management is a separate canonical authority, never coupled to site Disconnect.
- **Wrong-chain/offline behavior:** permit local site/permission/signature inspection and watch removal while RPC is unavailable; do not display on-chain authority as verified. All sensitive revocations fail closed.
- **Review integrity:** popup-origin trusted sender, short-lived random review IDs stored in extension session, explicit acknowledgement, fresh simulation and comparison of exact target, data, owner, allowance, epoch, nonce, fees, block and chain before local signing. No direct RPC signing fallback or server-side custody.

## Implementation

Wallet browser UI: wallet/extension/popup.html, popup.css, popup.js.

Canonical service-worker guards, local history and scoped watch records: wallet/extension/service-worker.js.

Pure authority and detection components: wallet/web/core/extension-security-centre.js and wallet/web/core/extension-security-actions.js. Existing canonical capability-management, session-management, signing and transaction-lifecycle helpers are reused; unsupported execution models remain fail-closed.

**Canonical contract restriction:** SmartAccount420 revokeCapabilityGrant, revokeKey and revokePasskey are onlyOwner methods, not arbitrary EntryPoint execution methods. Their execution requires a locally available verified EOA owner; the interface does not claim that an unrelated passkey UserOperation can call them. ERC-20 allowances owned by a SmartAccount use its own token-call execution path, not the EOA's approval.
