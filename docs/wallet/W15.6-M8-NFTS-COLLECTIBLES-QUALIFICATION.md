## Critical security invariants

1. **Ownership is exclusive to the current selected-chain contract:** ERC-721 `ownerOf` and ERC-1155 `balanceOf`. Both require verified interface/code. Cached event records are stale until refreshed; a spoofed log or JSON `owner` cannot produce a spendable asset.
2. **Approval safety:** ERC-721 `approve(address(0), tokenId)` is a true token-specific revocation, not another approval to the old operator. ERC-721/1155 `setApprovalForAll(operator,false)` is collection-wide revocation. The current exact operator is checked before revoking.
3. **No implicit signing:** the popup sends only typed NFT action parameters. The service worker rebuilds calldata, verifies owner, amount and chain, quotes correct EOA or UserOperation gas, and records a 128-bit random short-lived review ID in `chrome.storage.session`.
4. **Explicit confirmation and TOCTOU:** changed account, epoch, ownership quantity, operator, calldata, nonce, block hash or fee invalidates review. The existing local authority signs only the revalidated transaction. There is no website-facing direct raw transaction bypass.
5. **Submission is not finality:** activity records submitted/pending; the portfolio must refresh and independently verify a new on-chain balance/owner or operator approval. No browser-spam preference or local Disconnect implies an on-chain revocation.
6. **Metadata isolation:** no HTML injection, no iframe, no live images, limited text and user-consented remote JSON fetch. IPFS URLs resolve through a fixed HTTPS gateway and no metadata URL establishes an asset's value, authenticity, license or ownership.
