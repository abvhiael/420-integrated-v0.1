# W15.6-M9 — Ledger / Trezor hardware signing candidate

**Priority:** High. **Software implementation candidate; physical device and testnet acceptance still outstanding.** Branch: `feat/w15-6-m9-hardware-wallets-20261113`, PR #1142. Do not claim production or hardware-qualified status on mocked transports.

## Repository implementation

- **Ledger:** explicit Chromium WebHID selection, Ethereum app EIP-44 derivation path checks, HID channel/sequence/length framing, device-displayed address retrieval, cryptographic public-key/address equality, bounded EIP-1559 unsigned-transaction APDU streaming (`0xe0/0x04`) and signature recovery. EIP-712 hashing and hash-based device APDU (`0xe0/0x0c`) require a separate explicit blind/hash-only display acknowledgment and cryptographic EIP-712 signature recovery; no silent clear-signing claim. Personal signing on Ledger remains unsupported, fail-closed. Physical firmware support for type-2 and hashed structured data is unverified.
- **Trezor Connect 10:** pinned `@trezor/connect-webextension@10.0.1` MV3 SDK with locally bundled dependencies (esbuild), Trezor Suite Web `externally_connectable` origin, trusted extension UI -> service-worker message bridge, required developer application identity, user-confirmed EVM address and derivation, EIP-1559 transaction signing, EIP-712-v4 signing and personal signing. Strict result status, chain and signature recovery. The bridge does not inject remote JS into websites or delegate raw signing to an RPC.
- **Unified signed intent:** the selected chain/account/path are rechecked, EIP-1559 nonce and fee cap are revalidated, unsigned transaction construction and recovered signer must match the approved exact fields, and signed raw broadcasts must match the approved envelope. Origin approval and account switching remain checked. Hardware signer authority lives only in trusted extension pages; websites cannot call signing transport methods directly.
- **Existing transaction lifecycle:** hardware EOA accounts enter the same native/ERC-20 preflight, gas quotation, explicit wallet/website review, EOA-typed raw transaction recording, submission, receipt reconciliation, and same-nonce fee-bump/speed-up/cancel pathways. Browser settings, watch-only accounts and passkey SmartAccounts cannot impersonate a hardware EOA signer. Never convert a hardware signature to a software-key fallback.
- **Balances:** native and tracked ERC-20 balances use verified chain-bound RPC reads and never rely on device metadata as chain authority.
- **Automated security tests:** bounded paths, Ledger APDU framing/replay/truncation and fake WebHID signatures, EIP-1559 raw-envelope reconstruction, wrong signer, wrong chain, malformed or mismatched EIP-712 typed data, Trezor errors and simulated signing, stale fees and nonces. Dedicated build CI requires a local Trezor Connect 10 bundle.

Record exact SHA, tested device/firmware/browser, transaction hashes and independent receipts. Verify Trezor host/suite integration against its real `externally_connectable` lifecycle.
- **W15.10-M9:** independent security/code review of SDK dependency/supply chain, WebHID/APDU transport, MV3 external messaging origin control, blind/hash-only Ledger EIP-712 limitations, phishing and device display semantics, approved metadata/cross-origin validation, release packaging and final acceptance.

A passing unit test, emulator, GitHub workflow or unsigned fake device interaction does **not** constitute proof that physical Ledger/Trezor hardware signed. Disclose unavailable clear-signing support and refuse unsupported firmware/methods. Physical test failures must be fixed before production enablement.
