# W15.8 — 420Integrated Ecosystem Integration

**Goal:** Keep 420Wallet the account, signing and authorization interface for canonical Genesis applications. **Status:** repository-side integration; live deployed service acceptance remains W15.9; independent review remains W15.10. Physical Android/iOS acceptance remains deferred to testnet.

## Authoritative sources and reused code

- `contracts/src/libraries/ServiceIds420.sol` defines the Genesis identifiers; `wallet/web/core/genesis-app-catalog.js` already reconciles the Wallet-visible subset and documents unresolved **420Exchange**, **420Commerce** and **420Grow** product identities without inventing Registry service IDs. `wallet/web/test/genesis-app-catalog.test.js` independently compares those IDs to Solidity.
- `contracts/src/apps/ProtocolRegistry.sol` exposes `getService(bytes32)`: implementation, runtime code hash, metadata hash, published revision, activation time, and active status. `wallet/web/core/genesis-wallet-integration420.js` hashes canonical service IDs, verifies that exact on-chain tuple and actual Registry/implementation bytecode against a chain-specific pinned deployment. Revoked, unpublished, wrong-chain, stale version, spoofed name/origin or mismatched runtime code **must not produce an enabled app entry**. No test fixture or locally set `approved:true` flag alone makes a service verified.
- `wallet/extension/service-worker.js` reads the existing trusted extension configuration `420-wallet-extension-config-v1`, only probes services on the currently verified chain and selected account, checks network epoch, and re-verifies Registry state on user-requested app launch. `wallet/extension/popup.js` delegates that launch to the trusted worker; no `eth_requestAccounts`, `wallet_requestPermissions`, capability grant, EIP-712 signature or transaction is created by navigation.

## Release-controlled configuration (not a sample production deployment)

The trusted wallet extension configuration may provide `ecosystemRegistry:{chainId,address,codeHash}` and `ecosystemServices:[{id,name,serviceId,approved,chainId,version,origin,url,implementation,codeHash,metadataHash}]`. For example, `serviceId:'420/service/swap/v1'`, `id:'swap'`, `name:'420 Swap'`. All addresses and hashes **must come from an independently approved exact-chain runtime manifest and the active ProtocolRegistry publication**. The real chain-specific values are deliberately not supplied here. A signed/approved manifest plus matching live Registry code, version, active state, contract implementation, code hash, metadata hash and exact HTTPS origin are required; URL integrity and manifest signer provenance must be independently qualified as part of the official deployment and W15.9 testnet acceptance. Do not trust arbitrary local storage as a substitute for that publication.

The directory is **opt-in** via existing M11 `serviceDiscovery` privacy control and defaults empty. It is read-only for unconfigured/testnet-inactive services. Navigating to an authorized HTTPS URL opens a new tab but does **not** establish site connection, reveal `eth_accounts` or approve spending.
