# GEN-SVC-3.11.7 — verified business claims and independent review

Status: **PostgreSQL claim review foundation implemented; live Identity, Registry, Verify and reviewer authorization integration NOT qualified.**

`SQLClaimRepository` implements the existing `ClaimRepository` used by the opt-in authenticated claim submission handler. Supply a separately configured PostgreSQL `*sql.DB`, apply `migrations/003_travel_claims.sql` as a migration role, and inject an independently trusted `ClaimProvenance` and `ClaimReviewerAuthorizer`. The default `Handler()` and `cmd/420travel` do not enable this flow. No browser-supplied evidence reference, registry ID or claimant assertion proves entitlement: `ClaimProvenance` must check current Identity organization authority, the published canonical Location place-to-organization binding, matching Registry records, and Verify provenance (including current revocation and conflicting claims). Its absence or negative verdict blocks submission and approval.

On submission, the verified session supplies claimant_id and all new claims are PENDING; database uniqueness prevents concurrent duplicate active claims for the same claimant/place. `GetOwned` uses claimant_id in SQL so foreign claim IDs are indistinguishable from nonexistent ones. Decisions are server-side only, require independently authenticated and operation-authorized reviewer identity, prohibit self-review, lock the row, enforce PENDING -> APPROVED/REJECTED or APPROVED -> REVOKED, recheck upstream provenance for approval, and record a decision row in the same transaction. The default HTTP handler exposes no review or grant endpoint. Review status alone never transfers canonical Location ownership, grants place editing or changes Registry, Verify or Reputation.

Runtime DB grants should allow only the necessary DML on the claim and audit tables, plus sequence use for audit IDs. Prevent runtime updates/deletes to `travel_business_claim_decisions` through a restricted role; the service issues inserts only. Audit rows contain reviewer IDs and remain private, with explicit retention/access policy. Database migrations use a separate privileged role. Do not put evidence or claimant IDs in public pages or logs.

Before production: implement and inspect actual signed/authenticated service-to-service Identity/Registry/Verify/Location adapters; verify reviewer role, scope, audience and revocation against a deployed authority; add immutable audit and independent review UI with CSRF, rate limiting and observability; run migration and two-instance concurrent submission/decision and rollback tests against PostgreSQL; verify revoked provenance and conflicting claims; validate recovery/backup and authorizations under upstream outage. Real review grants, if required, must be separate narrowly scoped upstream permissions with live revocation checks. A passing Go CI run does not demonstrate those integrations or production database readiness.
