# GEN-SVC-3.11.2 — Durable, owner-scoped Trips repository

Status: **single-instance persistence implemented on the Travel feature branch; multi-instance production storage and live 420Identity verification remain unqualified**.

`durable_trips.go` implements `TripRepository` using an explicit 0700, non-symlinked pre-existing directory, a lifetime exclusive `trips.lock`, a 0600 JSON snapshot, temporary-file fsync, same-directory atomic rename, and directory fsync. The process must call `Close` on shutdown. Never publish this data directory through static file serving, place it on a shared-access mount, or use a filesystem without the required locking/rename/fsync behavior. Locking uses Linux/Unix syscall facilities; this implementation is intended for the Linux CI/deployment target and must be replaced or ported before use on other operating systems. It refuses a second writer and corrupt/unsafe snapshots; its 8 MiB snapshot limit is an intentional staging cap, not a scalable database.

The private disk codec in `durable_trips_codec.go` persists the trusted owner separately from the public-facing `Trip` JSON representation (`Trip.OwnerID` remains hidden from ordinary JSON). `Create`, `GetOwned`, `ListOwned`, `Replace`, and `Delete` compare owners inside the repository and do not allow a browser-supplied `OwnerID` to determine ownership. Missing and other users' IDs both return `ErrTripNotFound`; private and unlisted trips are excluded from `ListPublic`. Public trip references are not automatically publishable: a future public index must freshly resolve every referenced place and event against canonical public projection and revocation rules.

`durable_trips_test.go` covers restart survival, owner forgery, cross-user reads/edits/deletes, private/unlisted exclusion, concurrent writes in one process, exclusive writer lock, corrupt snapshot rejection, disk permissions and HTTP creation using the authenticated subject. This demonstrates local durability and owner isolation in deterministic tests. It is NOT a deployed 420Identity integration test; the HTTP fixture uses a controlled test session. Neither the default `Handler()` nor `cmd/420travel` enables authenticated Trips or opens a persistent store without a trusted composition root.

**Remaining release gates:** real Identity session verifier, TLS ingress and cookie lifecycle, expiry/revocation and CSRF acceptance tests, backups/restore and filesystem-failure injection, scale-out tenant database with migrations and transaction isolation, monitoring, key management where required, public-index revocation qualification, and privacy/security review. Treat failures to sync/rename or exhausted storage as uncertain-commit operational incidents; do not automatically retry non-idempotent creates with a new ID. No storage credentials, test subjects, or private trip contents belong in logs. Do not merge PR #356 as a production-complete Travel release solely because its CI passes.
