# GEN-SVC-3.11.1 — Identity-backed Trips session boundary

Status: **implemented as an injectable integration boundary; live Identity and durable Trips deployment NOT qualified.**

`identity_session.go` provides `IdentityCookieAdapter` and `NewIdentityBoundTravelHandler`. It accepts only an opaque `__Host-420travel-session` cookie on a TLS request, rejects ambiguous duplicate/malformed session cookies, and requires an independently authenticated `IdentitySessionVerifier` verdict for **each** request. The verdict must carry a nonempty immutable subject, the exact `420travel` audience, an unexpired/recent expiry, a non-revoked state and a session-bound unpredictable CSRF token. Travel does not decode an unverified token, trust browser-supplied account headers, create Identity sessions or infer identity from a wallet address.

The identity service/ingress owns login, logout, session issuance and cookie setup. A deployment must set its host-only cookie with `Secure`, `HttpOnly`, `Path=/` and appropriate `SameSite` policy, ensure authenticated server-to-server transport for session verification and validate issuer, session token binding, audience, expiry and revocation before reporting a positive verdict. The adapter's `r.TLS` requirement means an HTTPS-terminating reverse proxy must provide an explicitly trusted internal TLS hop or a separately reviewed authenticated ingress adapter; **do not blindly trust `X-Forwarded-Proto`, `X-User-ID`, or `X-Identity` from the internet.** Configure no token-in-query transport, no client-controlled verifier URL and no unverified JWT payload fallback.

`NewIdentityBoundTravelHandler(reader, verifier, trips, claims)` composes existing owner-scoped Trips and claims HTTP handlers. A missing verifier or repository leaves those routes disabled. The default development `Handler()` and `cmd/420travel` do **not** install an Identity adapter, and in-memory `TripStore`/`ClaimStore` remain development-only. Identity authentication alone does not make the deployment production-ready: use durable tenant-scoped Trips storage with crash/restart and cross-user isolation tests, real claim provenance and authorizer integration, TLS and cookie policy, login/logout/revocation acceptance tests, CSRF and cross-origin checks, monitoring and privacy review.

`identity_session_test.go` tests valid, missing, duplicate, malformed/forged-header, plaintext, wrong-audience, expired, revoked and upstream-failure decisions; identity-bound trip creation, CSRF failure, per-request revocation, cross-owner isolation, absence from public index and disabled default routes. Those tests use a deliberately controlled verifier and an in-memory TripStore. **They do not prove a deployed 420Identity API is available.** The exact production Identity session verification endpoint/transport must be confirmed from the Identity service repository/deployment before implementation; do not invent one.
