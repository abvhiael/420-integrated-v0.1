# GEN-SVC-3.11.4 — PostgreSQL Trips storage

Status: **PostgreSQL repository and migration implemented; deployed multi-instance acceptance NOT qualified.**

`sql_trips.go` adds `SQLTripRepository` backed by `database/sql` and PostgreSQL positional parameters. Provision PostgreSQL, apply `migrations/001_travel_trips.sql` with a migration role, provide a separately managed `*sql.DB` created using an explicitly selected and configured PostgreSQL driver, and inject the resulting repository into `NewIdentityBoundTravelHandler`. The Go root module intentionally has no PostgreSQL driver dependency; this change does not silently install a driver, open a DSN or enable private routes in `cmd/420travel`. No connection credentials belong in repository files. Runtime privileges should be restricted to SELECT/INSERT/UPDATE/DELETE on `travel_trips`, with schema changes reserved to a migration role. Configure TLS, pooling, statement and connection timeouts, backups, and metrics in the host deployment.

The migration declares globally unique trip IDs, owner_id, title/visibility checks, JSON arrays for public-reference IDs, creation/update timestamps, owner lookup and public-only indexes. SQL creates a trip with `INSERT ... ON CONFLICT DO NOTHING RETURNING`; reads, edits and deletes bind `owner_id` directly in their WHERE clauses. Cross-owner reads and mutations return the same not-found result as missing IDs. `Replace` requires an `UpdatedAt` version and returns not-found for a stale version or missing/foreign trip; the HTTP handler does not expose editing yet. The query's timestamp equality is a concurrency guard, not a full conflict-versus-not-found disclosure. Public listing is candidate metadata only: live publication/withdrawal status of every referenced place/event must still be checked by the presentation service before showing it.

CI currently tests Go compilation and SQL query/authorization contracts with a deterministic database/sql driver, not PostgreSQL itself. **Required before production qualification:** run the migration on a dedicated PostgreSQL instance; run create/list/update/delete and global-ID collision tests from two independent Travel processes against one database; test concurrent updates and stale timestamp rejection, cross-owner non-disclosure, migration idempotence and rollback policy, connection loss and failed transaction handling, replica lag if used, restore-from-backup and permission-restricted runtime credentials. The exact real 420Identity session verification endpoint is still unverified; the default Travel handler remains fail-closed. `DurableTripStore` remains an independent single-instance staging option, not a distributed database migration source. Do not treat a green Go CI run as a demonstrated live two-instance database or Identity integration.
