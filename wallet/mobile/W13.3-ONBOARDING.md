# 420 Wallet — W13.3 Onboarding and First-Run Experience

W13.3 adds the branded first-run shell for the native Android and iOS wallets. It does not create a second wallet authority and does not pretend that account deployment has occurred before Wallet Core and the configured 420 network confirm it.

## First-run paths

The native clients present three explicit paths:

- Set up a new wallet
- Find an existing wallet
- Recover a wallet

Each path explains what Wallet Core and the canonical SmartAccount authority will do. The presentation layer does not mint, discover, recover, sign for, or otherwise control a SmartAccount by itself.

## Security education

The first-run experience explains that:

- the SmartAccount is the canonical account;
- the phone is a secure local client, not an independent account authority;
- passkeys remain local and device-backed where supported;
- biometrics prove local presence only;
- public RPC remains transport/read-only and never signing authority;
- recovery follows canonical recovery policy and timelock semantics;
- dApp permissions are scoped, revocable, and revalidated.

## Request handling during onboarding

Push references, verified links, and dApp handoffs are not presented for approval while onboarding is active. After onboarding completes, the existing canonical rehydration/revalidation flow resumes. No request is pre-authorized by onboarding.

## Completion state

The native clients store only a local boolean indicating that onboarding presentation has been completed. That state does not grant a capability, create a session key, change recovery authority, authorize a transaction, or replace Wallet Core state.

## Qualification

`test/w13-onboarding.test.js` statically verifies cross-platform onboarding paths, authority language, pre-completion request blocking, and the absence of private-key/remote-signer fallbacks.

Production Play/TestFlight readiness remains blocked until genuine physical Android and iPhone evidence makes `npm run device:closeout` pass.
